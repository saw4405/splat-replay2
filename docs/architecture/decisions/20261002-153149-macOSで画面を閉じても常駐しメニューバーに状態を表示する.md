# macOSで画面を閉じても常駐しメニューバーに状態を表示する

- ID: 20261002-153149
- 状態: accepted
- 日時: 2026-10-02T15:31:49+09:00
- 判断者: 共同（ユーザーが対応範囲を承認し、メインエージェントが実現方式を確定）

## 目的・問題

macOS でも、ウィンドウを閉じた後に自動録画と後処理を継続し、状態を確認して画面を再表示し、安全に終了できるようにする。親セッションの調査報告では、macOS はウィンドウを閉じると終了し、状態アイコンの実装も Windows のみだった。Windows と同等の常駐・状態確認を求めるユーザーの質問を受け、macOS 向けの不足を埋める判断が確定した。

## 前提・制約

- 先行する macOS 対応方針の対象は Apple Silicon である。本判断もその対象内で適用する。
- 既存の常駐・安全終了の Windows 判断を macOS に適用する際、既存の状態判定、処理完了条件、正常終了経路を再利用する。
- `DesktopSignals` と `describe_tray_status()` は共通状態・信号を持ち、現在の状態分類は `recording`、`processing`、`attention`、`starting`、`waiting` の5種である。`DesktopMaintenance` は既存の処理完了条件を扱う。
- 設計記録時点では実装中であり、配布アプリを使った実機確認は未完了である。コードの存在やビルドだけで実機での表示・終了成功を認定しない。
- AppKit の UI 操作はメインスレッドで行う。メニューバーの項目は空き幅の制約で隠れる場合がある。

## 判断

1. macOS では、ウィンドウの閉じる操作をウィンドウの非表示として扱う。ウィンドウを隠している間も backend の録画・後処理を継続する。
2. `NSStatusItem` を使ってメニューバーに状態項目を置く。既存 `describe_tray_status()` の5状態と優先順位を保ち、項目とそのメニューで状態および日本語の説明を提示する。状態の分類・業務判断は OS 固有実装へ複製しない。
3. メニューバーのメニューから画面を再表示し、完全終了できるようにする。Dock アイコンは表示したままにし、Dock からの再オープンも画面再表示へつなぐ。
4. `Cmd+Q`、アプリメニューの終了、メニューバーの完全終了は共通の `quit` 要求へ送る。ネイティブ delegate 内で backend の完了を同期的に待たず、共通制御ループと `DesktopMaintenance` に既存の完了判定を行わせる。完了後は Python の通常終了・`finally` 経路へ戻り、WebView を破棄する。
5. 常駐の有効化を Windows の IPC インスタンス存在に結び付けない。共通制御ループの外部コマンド取得 `take` と状態返却 `state` は任意とし、macOS 用の空の `DesktopControl` 実装や新しい IPC は追加しない。`DesktopSignals`、状態説明、制御ループ、`DesktopMaintenance` を再利用する。
6. `NSStatusItem` の作成・更新・破棄は AppKit のメインスレッドで行い、表示内容が変わった場合だけ更新する。項目を初期化できない場合も、メインウィンドウを表示したまま再表示・終了の操作手段を保つ。

## 検討した選択肢と棄却理由

| 選択肢 | 採否と理由 |
| --- | --- |
| 現状どおり閉じる操作で macOS アプリを終了する | 不採用。ユーザーが求めた、画面を閉じても録画を続け状態を確認する動作を満たさない。 |
| Windows の共有状態・終了制御を macOS に接続し、`NSStatusItem` を追加する | 採用。既存の状態分類と処理完了条件を維持し、OS ごとの差をメニューバー表示とネイティブイベントの接続に限る。 |
| `NSDockTile.badgeLabel` だけで状態を示す | 今回は採用しない。承認されたメニューバーでの状態確認・再表示・終了を提供せず、追加の Dock バッジも今回の判断範囲ではない。 |
| macOS 専用の空 `DesktopControl` や独自 IPC を作る | 不採用。常駐に Windows の IPC 所有者は必要なく、既存制御の任意コマンド・状態接続で足りる。 |
| Dock を隠してメニューバーだけで操作する | 不採用。メニューバー項目が幅の都合で隠れる場合にも再表示経路を残す必要がある。 |

## 適用範囲

Apple Silicon の macOS デスクトップ版における、閉じる操作後の常駐、メニューバー状態項目、画面再表示、完全終了のイベント接続、および既存の共通状態・終了制御への接続。

## 適用しない範囲

- Windows の常駐・状態表示・終了動作の変更。
- Dock バッジの追加、Dock アイコンの非表示、ログイン時自動起動。
- 状態分類や日本語説明の新設、状態 API・IPC・外部依存の追加。
- 処理完了前の強制終了、終了待ちの期限追加、録画・後処理の既存条件変更。
- 実機・配布版での動作保証。これらは検証結果を別途確認する。

## 期待する効果

画面を閉じても自動録画と後処理を続け、メニューバーで現在の状態を把握して画面を戻せる。各終了操作は一つの安全な終了経路を通るため、状態表示と終了条件の OS 間の重複実装を避けられる。

## 受け入れる欠点・リスク

- メニューバーに空きがない場合、`NSStatusItem` が表示領域から隠れることがある。このため Dock アイコンを残し、Dock からの再表示を維持する。
- pywebview の Cocoa delegate や AppKit の挙動は、依存ライブラリまたは macOS の更新で変わる可能性がある。更新時に状態項目、再表示、終了経路を再確認する。
- `NSStatusItem` の初期化に失敗した場合、状態表示は使えない。ウィンドウを表示したままにして、再表示と終了の操作手段を失わせない。
- 完全終了は既存の処理完了条件を守るため、録画・後処理などが完了するまで待つ。同期的な delegate 待機や強制終了は追加しない。
- 設計時点では実機確認が未完了であり、配布版の AppKit/PyObjC 組合せで期待どおり動くかは未確認である。

## 再検討条件

- メニューバーの幅制約や初期化失敗で状態確認・操作が利用者に届かず、別の常時表示手段が必要になった場合。
- macOS または pywebview の更新で delegate、Dock 再表示、`NSStatusItem` の動作が変わった場合。
- Dock バッジ、Dock 非表示、ログイン時自動起動、終了待ち期限など、今回対象外の要件が明示された場合。
- 実機検証で閉じた後の backend 継続、5状態の表示、再表示、正常終了のいずれかが成立しない場合。

## ユーザー発言の原文

先行する macOS 対応範囲:

> 全機能を同等に対応
> Apple Silicon のみ

今回の質問と対応要求（親トランスクリプト ordinal 23405、23453）:

> アプリを常駐にできてる？ Windows と同じように 状態を バッジ 表示できてる？

> 対応として

「対応として」の直前に、メインエージェントは次のように不足を報告した（ordinal 23446）。この文脈を受諾対象として併記する。

> **まだWindowsと同等にはできていません。**
>
> - **自動録画の待機処理**：動作しています。現在もSwitch ONを待機中です。ただし、macOSではウィンドウを閉じると終了し、常駐を続ける機能は未対応です。
> - **OS上の状態アイコン・バッジ**：未対応です。待機中・録画中・編集中などを表示する実装は、現在Windows専用です。
>
> この2点は、macOS対応の残項目です。

ユーザーの要求を具体化したメインエージェントの応答:

> ウィンドウを閉じても動作を続け、macOSのメニューバーから状態確認・画面再表示・終了ができるように対応します。既存のWindows実装と終了処理を調べ、Luna／xhighへ完了条件付きで委譲した後、私がコードと実機動作を確認します。

> 既存のWindows版には、閉じる操作で画面だけを隠し、処理完了を待って完全終了する仕組みがあります。macOSにもこの仕組みを接続し、状態表示はメニューバーのアイコンとして追加する方針で設計助言を受けます。

> 状態判定と安全な終了条件はWindows版と共通化します。macOSではメニューバーに状態を表示し、閉じるボタンは非表示、完全終了は処理完了を待つ動作にします。
