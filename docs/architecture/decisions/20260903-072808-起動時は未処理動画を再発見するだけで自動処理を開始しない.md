# 起動時は未処理動画を再発見するだけで自動処理を開始しない

- ID: 20260903-072808
- 状態: accepted
- 日時: 2026-09-03T07:28:08+09:00
- 判断者: ユーザー

## 目的・問題

アプリ起動の主目的は、これからゲームを開始して録画することである。起動時に残存する録画済み・編集済み動画の編集・アップロードまで自動開始すると、録画準備または録画と CPU、GPU、ディスク、ネットワーク等の資源が競合し、主目的を妨げる可能性がある。

一方、通知の取りこぼしや異常終了後にも未処理動画を再発見する回復性は維持する必要がある。したがって、起動時の「未処理データの発見」と「処理の開始」を分離する。

## 前提・制約

- `recorded/` と `edited/` の一覧走査を、未処理作業を再発見する根拠として維持する。
- 起動時の編集・アップロードが実際に録画開始を失敗させるか、または録画品質をどの程度低下させるかは未確認である。ただし、同時実行時の資源競合を現行の保証では排除できないというリスクを判断対象とする。
- Switch 電源 OFF 確定後の自動処理には、既存の `edit_after_power_off` 設定と 15 秒の開始猶予を適用する。
- ユーザーの手動開始は、起動時の自動開始禁止に影響されない。
- 編集・アップロードは単一 worker で直列実行し、多重起動させない既存保証を維持する。
- 成功を確認できない処理では、再試行・確認に必要なローカル入力を削除しない。
- 外部アップロードの成否不明時に無条件な自動再送を行わない既存方針を維持する。

## 判断

1. アプリ起動時は `recorded/` と `edited/` を走査し、未処理動画を再発見して保持するが、その発見を編集・アップロードの開始要求にしない。
2. 編集・アップロードを開始できる契機を次の二つに限定する。
   - Switch 電源 OFF の確定後。`edit_after_power_off` が有効な場合に、既存の 15 秒猶予を経て開始する。
   - ユーザーによる明示的な手動開始。
3. 起動時走査、後処理要求時・処理完了時の再走査、処理中に生じた要求を失わない仕組み、単一 worker、実行開始時 snapshot、成功確認後だけ入力を削除するデータ保全は維持する。
4. 失敗、キャンセル、外部処理の成否不明時は入力を保持し、後続の Switch 電源 OFF 確定または手動開始から再度扱える状態にする。

## 検討した選択肢と棄却理由

### 起動時にも設定判定と 15 秒猶予を適用して自動処理する

当初、`edit_after_power_off` を自動処理全体の許可設定へ広げ、起動時に未処理動画があれば 15 秒後に処理する案を提示した。しかし、アプリ起動の主目的がこれから録画を始めることであり、起動直後の編集・アップロードが録画準備または録画と資源競合する懸念に反するため棄却した。

### 起動時の走査も行わない

起動時の作業を最小化できる一方、通知の取りこぼし、異常終了、アプリ再起動前から残る未処理動画を再発見する回復性を失う。問題は走査ではなく処理の自動開始なので棄却した。

### 起動後の処理をすべて手動開始だけにする

起動時の競合は避けられるが、Switch 電源 OFF 後に編集・アップロードを継続する既存の利用目的まで損なう。電源 OFF 確定後の自動処理は `edit_after_power_off` と 15 秒猶予を適用して維持する。

## 適用範囲

- アプリ起動時に `recorded/` または `edited/` の未処理動画を発見した場合の開始条件。
- Switch 電源 OFF 確定後と手動操作による編集・アップロード開始条件。
- 未処理動画の再発見、保持、再走査、および失敗・キャンセル・成否不明時のデータ保全。
- 単一 worker と実行開始時 snapshot による既存の直列処理保証。

## 適用しない範囲

- Switch 電源 ON/OFF の判定方法や閾値。
- 録画、編集、アップロード自体のアルゴリズム。
- UI の表示構造や新しい設定項目の追加。
- 外部アップロードの完全な exactly-once 保証。
- アプリ終了後も処理を継続する OS サービス化。
- 複数 worker による並列処理。

## 期待する効果

- アプリ起動直後は録画準備を優先し、残存動画の自動編集・アップロードによる資源競合を避ける。
- 起動時の一覧走査は残るため、異常終了や通知欠落後の未処理動画を見失わない。
- Switch 電源 OFF 後の既存自動処理とユーザーの手動開始を維持する。
- 失敗、キャンセル、成否不明時の入力を保持し、データ消失を防ぐ。

## 受け入れる欠点・リスク

- 起動時に再発見した未処理動画は、次の Switch 電源 OFF 確定または手動開始まで処理されず、滞留時間が長くなる場合がある。
- 起動時走査と処理開始を分離するため、未処理ファイルの存在だけで worker を起動しない状態管理が必要になる。
- 資源競合による録画失敗・品質低下の程度は未確認であり、本判断は競合を実測して許容するのではなく、録画開始を優先して競合経路を避ける選択である。

## 再検討条件

- ユーザーが、録画準備よりも起動時の未処理動画の即時処理を優先すると明示した場合。
- 録画と編集・アップロードの同時実行を資源隔離またはスケジューリングによって安全に保証でき、起動時自動処理への明確な需要が生じた場合。
- アプリ起動の主目的が録画開始ではなくなった場合。
- 未処理動画の滞留が許容できず、電源 OFF または手動開始以外の明示的な開始契機が必要になった場合。

## ユーザー発言の原文

起動時自動処理の当初案に対し、利用目的と懸念を示した原文:

> アプリを起動するのは、基本的にこれからゲームを開始して録画をするためです。その時に編集・アップロードが開始してしまうと、録画ができなくならないですか？

旧 ADR の判断帰属を訂正した原文:

> そんな判断をした覚えはありません

この指摘を受けてメインエージェントが提示した修正版仕様の原文:

> 現在明示された利用目的を優先すると、仕様は次が自然です。
>
> - 起動時は未処理ファイルを走査・表示するだけ
> - 起動時には編集・アップロードを自動開始しない
> - Switch電源OFF確定後、または手動操作時に開始する
> - 未処理ファイルは削除せず、回収可能な状態で保持する
>
> これなら、異常終了後の未処理データを見失わず、アプリ起動直後は録画準備を最優先にできます。まだファイルやADRの変更は行っていません。

上記の修正版仕様を受諾したユーザー原文:

> その仕様で実装してください。

比較対象となった当初提案の原文:

> `edit_after_power_off` を「自動編集・アップロード全体の許可設定」へ広げ、起動時にも同じ判定と15秒猶予を適用します。
>
> 起動時のディレクトリ走査は設定に関係なく必ず実行します。現在の回復性設計は維持し、自動実行だけを設定で制御します。
