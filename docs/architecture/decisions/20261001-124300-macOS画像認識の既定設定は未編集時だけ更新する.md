# macOS 画像認識の既定設定は未編集時だけ更新する

- ID: 20261001-124300
- 状態: accepted
- 日時: 2026-10-01T12:43:00+09:00
- 判断者: 共同

## 目的・問題

今回のXマッチ画面では、OCR自体は XP「1985.1」を読み取れましたが、その前段の画面判定が既定の明るさ条件230では少し暗い画面を見逃していました。条件を220に下げても既存画面の判定が維持されることを確認したため、この変更を画像認識設定の新しい既定値として届ける方法を決めます。

macOS 配布版は初回に認識設定を保存し、その後は保存済み設定を使います。配布物の既定値を更新するだけでは既存利用者の設定に変更が届きません。一方、保存済み設定を常に置換すると利用者の編集を失うため、どの設定を未編集の既定値と認定するか、誰がどの時点で比較するかを決める必要があります。

## 前提・制約

- 対象は macOS の frozen 配布アプリが暗黙の runtime 設定パスを使う場合です。明示的な設定パスや開発実行は今回の実装範囲に含めません。
- 既存挙動では設定ファイルが存在しない場合にだけ初回コピーし、以降は保存済みファイルを保持します。
- 利用者が設定ファイルを編集した場合は、その変更を保護します。対象項目以外を変更した場合も同様です。
- 記録時のメインエージェント報告では、今回の Mac の runtime 設定が修正前の同梱設定と全バイト一致することを再確認した後、`image_matching.yaml.baseline` を排他的作成モードで seed し、利用者設定自体は変更していません。この確認は当該 Mac の個別移行根拠であり、他の既存インストールを未変更と認定する根拠にはなりません。
- 本 ADR 記録時点で実装は進行中です。メインエージェントは対象 runtime-path テスト18件の通過を報告しましたが、記録役はその結果を独立確認していません。ネイティブアプリでの既定更新も未確認です。設計判断は記録しますが、実装完了や配布アプリでの動作確認は主張しません。

## 判断

1. Xマッチ画面判定の明るさ条件を230から220へ更新した既定設定を配布します。
2. macOS 配布アプリは、起動時に現在の利用者設定を「そのMacで最後に導入した配布既定設定」の全バイトと比較します。完全一致した場合だけ、今回の同梱既定設定へ更新します。ファイル内容が異なる場合は編集済みとして、利用者設定と比較元の両方を保持します。
3. 比較元には、そのMacで最後に導入した配布既定設定の内容を利用者設定と別に `image_matching.yaml.baseline` として保存します。この方法で履歴上のすべての旧版のハッシュを保持する必要はありません。比較はデプロイスクリプトではなく、利用者の Mac でアプリを起動したときに行います。アプリ更新を複数回飛ばした場合も、そのMacに保存されている比較元一つと現在の同梱設定を比較します。
4. 処理順序は次のとおりです。
   - 現在の利用者設定が新しい同梱設定と全バイト一致する場合、利用者設定は変更せず、比較元を新しい同梱設定で原子的に同期します。初回の比較元作成と、前回の比較元保存失敗からの回復に使います。
   - 現在の利用者設定が保存済み比較元と全バイト一致する場合、新しい同梱 YAML を既存ローダーで検証します。検証に成功した場合だけ利用者設定を原子的に置き換え、その成功後に比較元を原子的に新しい同梱設定へ更新します。
   - それ以外は両方を保持します。比較元がない、読めない、または新しい YAML の検証に失敗した場合も、未編集とは認定せず利用者設定を変更しません。
5. 比較元の保存に失敗しても、同じ同梱版で再起動すれば、利用者設定と同梱設定の全バイト一致から比較元を同期できます。失敗後、同期する前にさらに別版へ更新された場合は比較元と一致しないため、その回の自動更新を停止し設定を保護します。
6. 今回の Mac に限り、修正前の同梱設定と保存済み設定の全バイト一致を確認した結果を使い、旧版の比較元を個別に seed します。記録時のメインエージェント報告では、runtime 設定と修正前 Git HEAD の同梱設定が全バイト一致することを再確認してから `image_matching.yaml.baseline` を排他的作成モード (`xb`) で作成し、runtime 設定は変更していません。製品コードは、比較元のない未知の旧版設定を旧既定として自動認定しません。

## 検討した選択肢と棄却理由

### 今回の Mac だけを旧版ハッシュと比較する

今回の Mac で保存設定が旧同梱設定と一致することを確認すれば、一度の移行は可能です。しかし、この旧版ハッシュだけでは次の配布更新を判定できず、恒久的な更新方針になりません。今回の Mac は個別 seed の根拠として確認結果を使い、製品の恒久処理は起動時比較にします。

### デプロイスクリプトに全旧版のハッシュ一覧を持たせる

旧版ごとの比較値を列挙し続ける必要があり、ユーザーが懸念したとおり履歴管理が必要になります。また、デプロイ側だけでは各利用者の保存済み設定が編集されたかをその場で判定できません。各 Mac にそのMacで最後に導入した配布既定の比較元を持たせ、起動時にその Mac 上の設定と比較する方式を採用します。

### 対象の明るさ値が230なら220へ置き換える

対象値だけでは、230を意図して設定した利用者と未編集の既定設定を区別できません。H/S、ROIなど別項目の編集も検出できず、設定全体の編集意図を損なう可能性があるため採用しません。

### 常に新しい同梱設定で置き換える

配布更新は常に反映されますが、利用者が編集した値や調整を失うため採用しません。

### 同梱既定値と利用者差分を分離し、差分をマージする

既定値の更新と利用者の変更を細かく両立できますが、今回のために設定の保存・読込契約を変更する必要があります。全ファイル一致時だけ更新し、異なる場合は保持する既存設定方式で要件を満たすため、スキーマ変更や差分マージは導入しません。

## 適用範囲

- macOS frozen 配布アプリの暗黙の runtime 認識設定パス。
- そのMacで最後に導入した配布既定を保存する比較元ファイル `image_matching.yaml.baseline`。
- 既定のXマッチ画面判定の明るさ条件230から220への更新。
- 利用者設定とそのMacで最後に導入した配布既定設定の全バイト比較、未編集時の更新、編集済み設定の保護。
- 比較元の作成、更新順序、比較元保存失敗後の同版再起動時の回復。

## 適用しない範囲

- 明示的に指定された設定パス、開発実行、Windowsやその他OS。
- 比較元のない既存利用者すべての自動移行保証。
- 利用者設定と既定値の項目単位のマージ、または対象値だけの自動補正。
- 他の画像認識閾値や認識方式の変更。
- アプリ起動中に別プロセスが同時編集した設定を完全に保護する保証。

## 期待する効果

- 旧版の既定設定と完全一致する macOS 利用者には、更新した220の条件がアプリ起動時に届きます。
- ファイル全体が異なる利用者設定はそのまま残り、対象値以外のカスタマイズも保護されます。
- 各利用者環境がそのMacで最後に導入した配布既定設定一つを比較元として保持するため、アプリ側で過去すべての配布版のハッシュを管理せずに更新できます。途中の配布版を飛ばして更新する場合も、保存済みの比較元一つで判定します。
- 今回の Mac は確認済みの旧同梱設定と全バイト一致したため、記録時のメインエージェント報告では個別移行の比較元を作成済みです。これは他の既存環境の状態を示しません。

## 受け入れる欠点・リスク

- 比較元のない既存環境で現在設定が新同梱版とも一致しない場合、未編集かどうか判定できないため、自動更新しません。その環境では新しい220の既定値が自動適用されない可能性があります。
- ファイル全バイト一致を条件にするため、コメント、空白、キー順などに差があれば、意味上同じ設定でも更新しません。保護を優先する保守的な扱いです。
- 利用者設定が一度比較元と異なると、後続版でも自動更新を適用しない場合があります。比較元は編集済み設定に合わせて進めず、最後に確認された配布既定設定を保持します。
- 現在設定を更新した後に比較元の保存が失敗すると、同版で再起動するまでは比較状態が不完全です。次の同梱版まで再起動しなかった場合は自動更新を停止しますが、利用者設定を上書きしません。
- YAML の置換は原子的に行いますが、比較後に別プロセスが設定を変更する競合までは保証できません。置換直前の再確認は助言された安全策ですが、実装状況は未確認です。
- 既存 YAML の検証や原子的置換を含む処理は、記録時点では実装中であり、失敗時の実動作は未確認です。

## 再検討条件

- 比較元のない既存利用者にも、この変更を自動適用する必要が生じた場合。
- 別項目を編集した利用者にも、未編集項目の既定更新を届ける必要が生じ、差分マージを検討する場合。
- 全バイト一致条件により更新されない設定が多く、より細かい移行が必要だと確認された場合。
- 比較元保存失敗、YAML 検証失敗、原子的置換失敗、同時編集時の保護について実装・検証結果がこの判断の前提を満たさない場合。

この場合は、移行対象と編集済み設定の保護への影響を示したうえで、更新条件の再判断を行います。

## ユーザー発言の原文

### 変更候補と保存設定の質問（ordinal 20212）

メインエージェントの質問と選択肢:

> Xマッチ判定の明るさ条件を230→220に補正すると、今回の画像からXP 1985.1を取得できます。既存画面の判定も維持できました。ただ、macOS版は認識設定を初回だけ保存するため、更新だけでは古い条件が残ります。保存設定が旧既定版と完全一致する場合だけ新版へ更新し、編集済み設定は保護する方式でよいですか？ 保存設定の扱いが変わるため、AGENTS.mdと設計助言に従って確認しています。
> - 未変更の旧既定設定だけ更新する（推奨）
> - 保存済み設定は自動更新しない

### 条件付きの賛同と比較方法への質問（ordinal 20340）

> 画像の認識設定はそのようにできるといいです。ただし、旧規定版から変わっていないことをどうやって確認する？

### 初回 SHA-256 案への質問（ordinal 20358 を受けた ordinal 20374）

メインエージェントの説明:

> 旧既定版の**ファイル全体のSHA-256**と比較します。一部の値だけで判定せず、コメントや空白を含めて一致した場合だけ更新します。違えば利用者が編集した可能性があるため保持します。
>
> このMacの保存設定は、修正前の同梱設定と完全一致していることを確認済みです。更新時は一時ファイルへ書いてから置き換え、書き込み失敗時は元の設定を残します。

ユーザーの質問:

> 誰がどのように比較する？今回だけ特別対応としてあなたが確認する？それとも恒久仕様としてデプロイスクリプトで確認する？デプロイスクリプトなら旧規定版全てのハッシュを残しておかないといけないのでは？

### 継続指示と、それを受けた修正案（ordinal 20385、20390）

ユーザー:

> 続けて

メインエージェントの回答:

> 比較するのは、利用者のMacで起動するアプリです。前の案は今回の旧版ハッシュだけを使う限定対応で、恒久仕様としての説明が不足していました。
>
> 恒久仕様では「前回配布した既定設定」を保存設定と別に残し、起動時に両者を比較します。一致すれば新版へ更新し、違えば編集済みとして保持します。これなら過去全版のハッシュ一覧は不要です。比較元が残っていない既存環境は自動更新せず、今回のMacは私が確認した結果を使って移行する方針を整理します。
