# Switch電源サイクルをまたぐ連続自動処理をバックエンド常駐サービスと永続未処理キューで実現する

- ID: 20260813-200649
- 状態: accepted
- 日時: 2026-08-13T20:06:49+09:00
- 判断者: 共同

## 目的・問題

アプリを起動したまま利用する限り、Switch の電源 ON/OFF を何度繰り返しても、各プレイの録画と、電源 OFF 後の編集・アップロードを継続できるようにする。

現行では、Switch 電源 OFF の連続検出で自動録画ループが終了し、編集・アップロード後の録画再有効化はブラウザ上の完了ダイアログ操作に依存している。Switch ON を継続待機する状態もなく、失敗時やブラウザ不在時には次回の録画へ復帰できない。

同時に、既存設計が持つ「`recorded/` と `edited/` を一覧走査し、通知の取りこぼし、エラー終了、アプリ再起動後にも未処理ファイルを再発見する」という回復性を失ってはならない。

## 前提・制約

- アプリプロセスが起動している間の継続動作を対象とする。アプリ終了後も動く OS サービス化は行わない。
- Switch 電源監視、録画、編集、アップロードは、ブラウザの生存、通知タイマー、完了ダイアログ操作から独立させる。
- ファイルシステム上に残る確定済み成果物を、未処理作業を再発見する永続的な根拠とする。
- 編集・アップロードは単一 worker で直列実行し、多重起動させない。一方、Switch 監視と次回録画は編集・アップロードの失敗や実行中状態で停止させない。
- 成功を確認できない処理では、再試行・確認に必要なローカル入力を削除しない。
- YouTube API 等の外部アップロード先が冪等性キーや確実な照合手段を提供しない場合、外部副作用の完全な exactly-once は保証できない。
- Switch ON/OFF の具体的な連続観測回数と間隔は、実映像 fixture または実機確認で確定する。推測で閾値を固定しない。
- Clean Architecture の依存方向 `interface → application → domain` を維持する。

## 判断

1. アプリ lifespan と同じ寿命を持つバックエンド常駐サービスを、自動処理ライフサイクルの単一所有者にする。サービスは Switch 電源状態、録画監視、編集・アップロードの再走査要求を所有する。フロントエンドは状態表示、明示的な開始・停止、キャンセル要求だけを担当する。
2. Switch 電源状態に少なくとも `unknown`、`armed`、`waiting_for_power_on`、`stopped` を設ける。OFF 確定は自動録画ループの終了ではなく `waiting_for_power_on` への遷移とし、ON を連続観測で確定したら `armed` へ戻して録画待受を再開する。同じ OFF 状態の継続で後処理要求を重複発行しない。
3. `recorded/` の確定済み動画を未編集キュー、`edited/` の確定済み動画を未アップロードキューとして扱い、これらの一覧走査を処理対象の SSoT として維持する。イベント、`cycle_id`、`batch_id` は wake-up、診断、表示に使えるが、処理対象の唯一の根拠にはしない。
4. アプリ起動時、後処理要求時、各処理の完了時にディレクトリを再走査する。編集・アップロードは実行開始時点の一覧を snapshot として扱い、実行中に追加されたファイルを現在の処理へ混入させず、次回 snapshot で処理する。
5. 処理中に新しい OFF 遷移や録画保存が生じても再走査要求を失わないよう、単調増加する generation または同等の lost-wakeup 防止機構を使う。worker は idle へ移る直前に再走査し、観測済み generation と現在値が一致し、未処理ファイルも存在しない場合だけ待機する。
6. 各入力は成功確定後にだけ削除する。録画保存、編集成果物一式の `edited/` への commit、アップロード成功の各境界を明示し、失敗・キャンセル・成否不明時は入力を残す。編集成果物確定後・元録画削除前の異常終了では、安定した入力識別子または commit manifest により、再起動後のデータ消失と重複編集を防ぐ。
7. 外部アップロード成功後・ローカル成功記録前に終了した場合は成否不明として扱う。無条件な自動再送で重複を増やさず、ローカル未処理ファイルの漏れ防止を優先する。

## 検討した選択肢と棄却理由

### 現行のフロントエンド依存フローを維持する

編集・アップロード成功後に完了ダイアログを閉じた操作で自動録画を再有効化する案。ブラウザ不在、ダイアログ未操作、アップロード失敗時に復帰せず、Switch OFF 中に再有効化しても ON を待機し続けず停止するため、目的を満たさない。

### 既存の録画ループだけを終了しないようにする

OFF 検出時の終了を待機へ変えるだけの案。電源状態が明示されないままでは OFF フレーム継続による後処理要求の重複を防げず、編集・アップロード中の通知も現行の排他処理で捨てられるため不十分である。

### OFF 時点の cycle/batch を処理対象の唯一の根拠にする

OFF 確定時に対象ファイルを固定し、その batch だけを処理する当初案。通知を受信できなかった場合、異常終了時、起動前から残るファイルを再発見する既存の回復性を弱めるため棄却した。cycle/batch は補助情報に限定し、ディレクトリ走査を権威として残す。

### イベントや Boolean の pending フラグだけで再実行を管理する

イベントは失われ得て、処理終了と新規要求が競合すると Boolean の確認・クリア間で lost-wakeup が生じ得る。generation と終了直前の再走査で要求と実在ファイルの両方を確認する案を採用した。

### 外部アップロードも無条件再試行で exactly-once を目指す

外部成功後・ローカル記録前の異常終了では成否をローカルだけで判定できず、外部側の冪等性・照合契約がなければ完全な exactly-once を保証できない。無条件再送は重複を増やすため、成否不明を区別し、ローカル漏れ防止を優先する。

## 適用範囲

- Switch 電源 OFF 後も存続し、ON を待って録画待受へ復帰するバックエンド監視ライフサイクル。
- アプリ lifespan と明示停止に連動する常駐タスクの開始・停止。
- OFF 遷移ごとの編集・アップロード開始要求、開始猶予、キャンセル。
- `recorded/` と `edited/` の起動時・要求時・完了時走査。
- snapshot、generation 等による処理中追加と再走査要求の取りこぼし防止。
- 録画保存、編集成果物 commit、元入力削除、再起動回復の順序と冪等性。
- UI 依存の開始・再有効化トリガーの撤去と、バックエンド状態の表示。

## 適用しない範囲

- 外部 API に十分な冪等性・照合手段がない場合のアップロード完全 exactly-once。
- ディスク破損、利用者による手動削除、保存先容量不足からの自動復旧。
- PC、OBS、キャプチャーデバイス自体の電源制御。
- アプリ終了後も処理を継続する OS サービス化。
- 複数編集 worker による並列処理。
- 既存動画の形式やメタデータ形式の一括移行。
- 無関係な録画認識精度、OCR、UI デザインの変更。

## 期待する効果

- Switch の ON/OFF とプレイを何度繰り返しても、同一アプリプロセスで録画、OFF 後処理、ON 待機、録画復帰を継続できる。
- ブラウザを閉じていても、完了ダイアログを操作しなくても、編集・アップロードと録画復帰が進む。
- 通知の欠落や異常終了があっても、ローカルの未処理ファイルを次回走査または再起動時に再発見できる。
- 処理中に追加された録画を現在の snapshot に混入させず、次回走査へ漏れなく送れる。
- 保存・編集・アップロードの失敗境界で、成功未確認の入力を消失させない。

## 受け入れる欠点・リスク

- 常駐状態機械、単一 worker、generation、成果物 commit を調整するため、現行の UI 起点直列フローより実装と状態観測が複雑になる。
- ファイルシステムを SSoT とするため、手動削除、破損、同名衝突等は別途扱いが必要である。
- 外部アップロードの成否不明時は自動処理が確認待ちとなり、利用者の確認またはリモート照合が必要になる可能性がある。
- Switch ON/OFF の誤判定を防ぐ閾値は実映像に依存し、fixture または実機による検証が必要である。
- 編集とアップロードを単一 worker で直列化するため、並列化より処理待ち時間が長くなる場合がある。

## 再検討条件

- 外部アップロード API が冪等性キーまたは確実なリモート照合契約を提供し、成否不明を機械的に解消できるようになった場合。
- 未処理件数や処理時間が単一 worker の許容範囲を超え、並列処理が必要になった場合。
- ファイルシステム走査だけでは大量ファイル時の性能または一貫性要件を満たせず、永続 DB 等の導入を検討する場合。
- 実映像から Switch ON と「OFF ではないが有効信号でもない状態」を安定して区別できない場合。
- アプリ終了後も処理継続が必要というユーザー要件へ変更された場合。

## ユーザー発言の原文

> Switchの電源がoffになったら、編集・アップロードするようになっています。次にSwitchの電源onを検知したら、自動録画機能が動作するようになっていますか？

> 達成したいことは、アプリを起動したままなら、何回スプラトゥーンで遊んでも何回Switch電源on/offがあっても、録画・編集・アップロードができることです。
>
> 電源offの状態で自動録画を再開したら、電源offだから待機状態になって、Switch電源onされたら自動録画機能が動作する訳ではない？

> ファイルを一覧取得して処理することで、全ての動画を漏れなく対応し、エラー終了していた時にも未対応の動画を対応できるような設計としていました。
> 新しい設計でも問題なく動作することが保証されていますか？

> 目的・目標・方針・対象範囲・範囲外・受入条件・マイルストーンを永続化してから作業に着手してください。

修正版の設計を示したメインエージェントの原文:

> `list_recordings()`／`list_edited()`による一覧取得は廃止せず、ディレクトリを永続的な未処理キューとして維持します。

> SwitchのON/OFFサイクルIDは診断・画面表示にだけ使い、処理対象を決める唯一の情報にはしません。ファイルが残っていることを未処理の根拠にします。

> したがって、新設計は「一覧取得を置き換える」のではなく、「一覧取得による回復性を中核に残し、常駐監視・再走査・原子的確定・冪等性を追加する」設計に修正すべきです。これなら現在意図されている未処理動画の回収保証を維持できます。

実装契約の保存と採用方針を確認したメインエージェントの原文:

> 承知しました。まず実装契約として「目的・目標・方針・対象範囲・範囲外・受入条件・マイルストーン」をリポジトリへ保存し、そのファイルを基準に実装を開始します。
>
> 方針は、既存の「ディレクトリ一覧による未処理動画の再発見」を維持し、バックエンド常駐監視・処理後の再走査・安全な成果物確定を追加するものとします。アップロード先との完全なexactly-once保証は範囲外とし、現行の漏れ防止優先を維持します。テスト判断には`test-ops`、確定した重要設計の記録には`design_steward`のRECORD契約を使います。
