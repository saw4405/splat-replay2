# 初回セットアップ完了後にバックグラウンド自動録画を開始する

- ID: 20261012-112028
- 状態: accepted
- 日時: 2026-10-12T11:20:28+09:00
- 判断者: ユーザー

## 目的・問題

新規 macOS VM の初回セットアップ中、セットアップ完了前に常駐自動録画が OBS の初期化・起動を試みるコード経路が確認されました。初回導入と自動録画の初期化が同時に進む干渉を避け、セットアップ完了後はアプリを再起動せず自動録画を開始する開始条件を定めます。

VM の OBS 終了時には DistroAV の NDI 出力停止処理で SIGSEGV が観測されました。これは別の観測事実です。初回セットアップ中の自動起動がそのクラッシュを起こした、または待機によって解消するという因果関係は未確認です。

## 前提・制約

- 対象は Windows・macOS 共通のデスクトップ版および Web 版です。
- 既存の `SetupService.is_installation_completed()` が返す永続化済みの初回セットアップ完了状態を開始許可条件にします。新しい永続フラグ、スキーマ、API 通知は追加しません。
- セットアップ完了状態は、通常の `SetupService.proceed_to_next_step()` の最終経路と `/setup/complete` の両方から保存されます。待機側は特定の API 呼び出しではなく、この既存状態を観測します。
- 自動処理ライフサイクルはバックエンド常駐サービスが所有する既存判断を維持します。
- FastAPI lifespan の `yield` 前に完了待ちを置くとセットアップ API を受け付けられなくなるため、待機はバックグラウンドタスク内で行います。
- desktop activation による既存の開始制御と、アプリ終了時の task cancellation・回収を維持します。
- 待機間隔と状態読取の I/O 方式は未確定です。読取例外で待機 worker が黙って終了しないことは要件とします。
- セットアップ完了は OBS の接続成功を保証しません。完了後の OBS 初期化・再試行は既存の自動録画処理に委ねます。

## 判断

1. Windows・macOS のデスクトップ版および Web 版では、自動録画の開始だけを初回セットアップ完了までバックグラウンドで待機させます。既存の完了状態を観測した後、同じアプリプロセス内で自動録画を一度だけ開始します。
2. 完了判定には既存の `SetupService.is_installation_completed()` を使い、`proceed_to_next_step()` の最終経路と `/setup/complete` の双方で保存された状態を認識します。完了状態を別途保存したり、片方の経路だけに通知を追加したりしません。
3. 待機は lifespan の開始・`yield` を塞がないバックグラウンドタスクで行います。desktop activation と、終了時の待機タスクのキャンセル・回収を維持します。状態読取の例外を黙って握りつぶして worker を終了させないようにします。
4. 後処理サービス、CLI の `auto` コマンド、すでに自動録画が稼働した後のセットアップ再実行は、現在の開始・実行挙動を維持します。

## 検討した選択肢と棄却理由

| 選択肢 | 採否と理由 |
| --- | --- |
| 起動時から自動録画を初期化する | 不採用。セットアップ未完了でも OBS 起動・接続を試みるコード経路が確認されており、初回セットアップとの干渉を避けられません。 |
| 起動時に一度だけ完了状態を確認し、未完了なら終了する | 不採用。同じプロセスでセットアップが完了しても自動録画が開始されません。 |
| `/setup/complete` など特定の API だけから開始通知を送る | 不採用。`proceed_to_next_step()` の最終経路も完了状態を保存するため、片方だけの通知では完了経路を取りこぼします。全経路への通知を新設する必要もありません。 |
| 完了待ちを lifespan の `yield` 前で行う | 不採用。lifespan の開始が完了するまでリクエストを受け付けないため、セットアップ API 自体が使えなくなります。 |
| frontend の画面遷移から自動録画を開始する | 不採用。ブラウザや UI がバックエンド常駐サービスの開始所有者となり、既存の責務境界と合いません。 |
| 後処理サービス、CLI `auto`、稼働後の再セットアップも待機対象にする | 不採用。OBS 初期化を初回セットアップ中に行わない目的からは導けず、ユーザーが指定した維持範囲を超えます。 |
| 既存完了状態を worker 内で待つ | 採用。永続状態を使うため完了 API の違いを吸収し、既存サービス・常駐タスクを利用して同じプロセスで一度だけ開始できます。 |

## 適用範囲

- Windows・macOS のデスクトップ版および Web 版における、自動録画の初回開始条件。
- 初回セットアップ未完了の間のバックグラウンド待機と、完了後の同一プロセス内での一度だけの開始。
- 既存セットアップ完了状態を通じて、両方の完了保存経路を認識すること。
- desktop activation とアプリ終了時の待機 task のキャンセル・回収。

## 適用しない範囲

- 後処理サービスの開始条件。
- CLI `auto` の開始条件。
- 自動録画がすでに稼働した後にセットアップを再実行した場合の挙動。
- 新しい完了フラグ、永続スキーマ、API 通知の導入。
- OBS、DistroAV、NDI Runtime の終了時 SIGSEGV の修正または原因確定。
- セットアップ完了後の OBS 起動成功や録画成功の保証。
- 待機間隔、状態読取 I/O 方式など未確定の実装詳細。

## 期待する効果

- 初回セットアップ完了前の自動録画初期化を保留し、初回導入との干渉を減らせます。
- セットアップ完了後はアプリを再起動せず、同一プロセスで自動録画へ移行できます。
- UI の特定経路に依存せず、既存の永続状態を使って完了を認識できます。
- 後処理、CLI `auto`、稼働開始後の再セットアップには影響範囲を広げません。

## 受け入れる欠点・リスク

- 完了状態を観測するまで自動録画は開始せず、状態を定期確認する場合は確認間隔分の開始遅延が生じます。間隔は未確定です。
- セットアップが完了しない場合、自動録画も開始しません。
- 状態ファイル等の読取失敗時に待機 worker が終了すると、完了後も開始できない可能性があります。例外時に worker が黙って停止しないことを保ち、具体的な回復方法は実装時に定めます。
- セットアップ完了状態は OBS の準備完了を示しません。OBS 起動失敗や既存の再試行結果は別途扱います。
- VM で観測した DistroAV の `ndi_output_stop` における SIGSEGV と本判断の因果は未確認です。本判断をクラッシュ修正として扱いません。
- 本 ADR の記録時点では実装中であり、実装完了または VM での開始条件検証成功を主張しません。

## 再検討条件

- セットアップ完了状態の保存経路が変わり、既存状態の確認だけでは全経路を認識できなくなった場合。
- 永続状態の読取失敗が継続し、バックグラウンド待機だけでは完了後の開始を保証できない場合。
- CLI `auto`、後処理サービス、または稼働後の再セットアップにも開始・停止条件を適用する要件が追加された場合。
- DistroAV の終了時クラッシュについて、再現条件と原因が別途確定し、本開始条件との関係を評価する必要が生じた場合。
