# macOS の OBS 音声検査は指定 CoreAudio 入力を一意に解決してから行う

- ID: 20261001-222419
- 状態: accepted
- 日時: 2026-10-01T22:24:19+09:00
- 判断者: 共同

## 目的・問題

ユーザーから「OBS では音声入力されているのに無音と誤判定し、OBS を再起動する」と報告がありました。対象は macOS の OBS 音声 readiness 検査で、録画時に音声が取れているのに誤った OBS 入力のメーターを読んで復旧処理へ進むことを防ぎます。

親トランスクリプトの診断では、約 3 秒間に 57 件届いた OBS のメーターイベントで、映像入力 MiraBox（kind: macos-avcapture、device_name: MiraBox Capture）の inputLevelsMul は空配列でした。一方、別の coreaudio_input_capture 入力「音声入力キャプチャ」は、同じ MiraBox Capture を選択しており、2 チャンネルの非ゼロレベルを返しました。別の「マイク」は device_id が default で、ミュート状態でした。

この観測から、音声自体が無音だったのではなく、音声健全性検査が映像入力の空メーターを先に対象にしたことが誤判定の原因と判断しました。以前の入力名一致だけに頼る解決では、映像入力を音声入力として選び得ます。修正対象はメーター値の意味ではなく、メーターを読む前の検査対象解決です。

## 前提・制約

- ユーザーは音声復旧を目的とする既存の OBS 自動再起動を維持する判断をしています。
- macOS の設定ではキャプチャ機器を表示名で扱います。同名機器に対する全体の設定・選択挙動は変更しません。
- 空の inputLevelsMul は、検査対象として正しく特定された音声入力に対してのみ、既存 ADR の定義どおり silent とします。対象が特定できない状態は silent に読み替えません。
- device_id は設定値全体を識別子として照合します。内部の区切りや構成要素を仮定しません。
- 音声の曖昧判定は fail-open とし、復旧の自動実行へ進めません。既存 ADR の実録画中操作禁止、OBS 実行ファイルの一意な照合、二回連続 silent の確認などの安全条件を維持します。
- 実機診断で確認できたのは一つの macOS / OBS 構成です。全機種・全 OBS バージョンの同じ入力構成を保証する証拠ではありません。

## 判断

1. macOS の検査では、まず OBS 入力一覧から kind が coreaudio_input_capture の入力だけを候補にします。macos-avcapture の映像入力は音声健全性の対象にしません。
2. 各候補の GetInputSettings で現在の device_id を取得し、GetInputPropertiesListPropertyItems に propertyName=device_id を指定して OBS が提示する動的デバイス一覧を読みます。現在値が default の候補は、指定された名前付きキャプチャ機器の一致候補にしません。
3. 一覧の itemValue が現在の device_id と完全一致し、同じ一覧項目の itemName がアプリ設定のキャプチャ機器表示名と完全一致するものを対応付けます。対応する一覧項目と CoreAudio 入力の組が全体で一意な場合だけ、その入力のメーターを検査します。UID の文字列を分割・解釈して表示名を推定しません。
4. 入力設定・プロパティ一覧の取得失敗、応答不正、対象の不在、同名デバイスの重複、または複数の CoreAudio 入力が対象に一致する場合は unknown とします。映像入力、最初の候補、部分一致へのフォールバックは禁止し、自動再起動の silent 条件へ流しません。
5. 一意に解決した入力に限り、既存の mute、音声トラック、active 状態、メーターの検査を適用します。その入力の inputLevelsMul が空配列なら silent のままとし、既存の二回連続 silent と安全ゲートを通った場合だけ既存の音声復旧・自動再起動を実行できます。
6. Windows の dshow 入力解決、ほかのプラットフォームの既存動作、録画中は操作しない条件、readiness の実行タイミング、および同名キャプチャ機器に関するアプリ全体の扱いは変更しません。device_id を永続化せず、設定項目・スキーマ・依存も追加しません。

## 検討した選択肢と棄却理由

### 入力名または機器名だけで、種類を問わず最初に一致した入力を使う

今回の診断で映像入力の名前と機器表示名が対応していても、映像入力のメーターは空で、CoreAudio 音声入力には実レベルがありました。入力名の一致だけでは映像と音声を区別できないため棄却します。

### 空メーターをすべて unknown とし、自動復旧を止める

一時案として検討・提案されましたが、確認済み音声入力の空レベルまで無音判定から外すと、既存 ADR 20260903-065610 の silent 契約を変更し、音声復旧を必要とするユーザー判断にも反します。対象解決の修正を選び、この一律変更案は撤回しました。コードの最終状態と全検証の完了は、本記録時点では未確認です。

### CoreAudio の device_id を分割して表示名を取り出す

OBS の公式実装は default を特別扱いし、それ以外の device_id 全体を CoreAudio UID として検索します。UID の内部形式を解析する公開契約は確認できないため棄却します。

### 音声異常による OBS 自動再起動を停止する

誤判定の再起動を避けられますが、ユーザーは音声復旧のための自動再起動を維持すると回答しています。誤りの原因である対象解決を直し、正しく特定した音声入力での既存復旧は残します。

### 表示名と OBS の実選択値を実行時に一意照合する

OBS が提供する入力種別、現在の選択値、動的プロパティ一覧の値と表示名を照合します。新しい永続設定や UID 推測規則を必要とせず、映像入力の空メーターを無音と誤認する経路を塞ぐため採用します。曖昧さは unknown に隔離します。

## 適用範囲

- macOS における OBS の音声 readiness 検査前の CoreAudio 入力解決。
- coreaudio_input_capture の現在 device_id と OBS の device_id 一覧の itemValue / itemName による実行時照合。
- 一意に解決した後の既存 mute・track・active・meter 検査、および既存の silent 復旧経路。
- 取得失敗または曖昧さを unknown とし、OBS 自動再起動をしない境界。

## 適用しない範囲

- macOS のキャプチャ機器選択 UI、保存形式、表示名で扱う既存ポリシー、または同名機器の全体挙動の変更。
- Windows dshow の解決方法や Windows での取得形式・動作保証の変更。
- 正しく解決した CoreAudio 入力について、空メーターを unknown に変更すること。
- macos-avcapture が音声を提供する構成の解決。OBS 実装には条件付き音声出力経路がありますが、この経路だけで音声健全性を判定できるかは未確認です。その構成しかない場合、本 ADR の解決では unknown とします。
- 曖昧な入力の推測選択、OBS の音声設定変更、音声処理、device_id の永続保存、新しい設定・スキーマ・依存の追加。
- OBS の全バージョン・全 CoreAudio 機器についての動作保証。

## 期待する効果

- 実音声のある CoreAudio 入力ではなく、空メーターを返す映像入力を見て OBS を再起動する誤判定を防ぎます。
- 正しく解決された入力が実際に無音の場合は、既存の silent 検査と復旧を維持します。
- 名前や入力候補が曖昧なときに誤った入力を silent と決めつけず、OBS を誤操作しません。

## 受け入れる欠点・リスク

- 取得失敗、同名デバイス、複数候補、default、またはバージョン差で一意照合できない場合は復旧しません。その状態で音声異常が実在すると、音声のないまま録画へ進む可能性があります。
- OBS と obs-websocket の入力一覧・プロパティ一覧の対応はバージョンに依存します。親実機では照合に成功しましたが、ほかの対応バージョンでの利用可否は確認していません。
- macos-avcapture の音声経路だけを使う構成がある場合、その音声は現在の照合・計測対象になりません。

## 再検討条件

- 対応対象の OBS / obs-websocket バージョンで device_id の一覧 API が使えない、または一覧値と設定値の対応が安定して得られないことが確認された場合。
- 実際の macOS 利用機器で同名デバイス、複数の CoreAudio 候補、default しかない構成、または macos-avcapture の音声だけの構成が現れた場合。
- 誤った再起動が続く、あるいは曖昧判定によって実際の音声異常が見逃される事例が確認された場合。
- 既存の音声復旧安全ゲートまたはユーザーの自動再起動方針を変更するとき。旧 ADR の空レベル意味を変える場合は、別途判断を明示します。

## ユーザー発言の原文

今回の誤判定報告:

> OBSから音声入力されているのに、されいないと誤判定してOBSを再起動してしまっている

自動再起動の扱いについての質問と回答:

> OBS の音声が無音のとき、アプリによる OBS の自動再起動を止めますか？ 今回のログでは、起動後の無音検出が終了・再起動を繰り返した原因です。以前は音声復旧のための再起動を許可いただいていました。

> 音声復旧のための自動再起動を維持する

同名キャプチャ機器の既存挙動に関するユーザーの発言:

> 同名キャプチャ機器があってもそのまま継続でいいです

この発言はアプリ全体の機器選択設定を変更する要望として再解釈せず、音声健全性検査が曖昧な場合だけ unknown とする本判断の範囲を定めるために引用しています。
