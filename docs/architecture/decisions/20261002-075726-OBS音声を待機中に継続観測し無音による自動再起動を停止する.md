# OBS音声を待機中に継続観測し無音による自動再起動を停止する

- ID: 20261002-075726
- 状態: accepted
- 日時: 2026-10-02T07:57:26+09:00
- 判断者: 共同

## 目的・問題

既存の音声 readiness は短い観測窓を開閉してレベルを調べ、2 回連続で `silent` なら条件付きで OBS を再起動する。ユーザーは誤検知による再起動が続き、短い観測では無音判定が早いと報告した。継続観測が可能と説明された後、ユーザーはマッチング開始まで確認を続け、無音でも再起動しないこと、Windows と macOS で共通の仕様にすることを明示した。

後続の訂正で、初回確認を Switch 電源 ON の検出時に限り、その初回一窓が `silent` の場合だけ継続観測すること、正常確認後は待機へ戻っても再開しないことを確定した。

音量値だけでは、長い静寂と入力故障を区別できない。そのため本判断は無音を修復原因として扱わず、待機中の音声ヘルスを観測して既存通知へ反映する。音声そのものを録音・保存する判断は含めない。

## 前提・制約

- 監視対象は、アプリが `ARMED` と認識し、既存 `SessionPhase.STANDBY` にある間の OBS 音声メーターである。
- 実際の入力解決は既存の OS 別方式を維持する。macOS は `20261001-222419` の一意な CoreAudio 入力解決を使い、Windows の入力解決も変更しない。
- 既存の入力選択結果、音量閾値、音声ヘルス通知、設定スキーマを変更しない。イベント未着の `unknown` と、イベントが届いて空レベルを示す `silent` の区別も維持する。
- `silent` であることを理由に OBS を自動再起動しない。これは自動再起動一般の廃止判断ではなく、無音判定を起点にする既存復旧経路だけを対象とする。
- 音声レベルの生波形を記録・保存しない。各観測窓の集計値のみを既存通知へ使う。
- 観測窓の完了、OBS 接続の切断、メーターイベントを待つために、録画状態、マッチング認識、描画フレーム、録画開始を遅らせない。接続終了待ちを無期限に行わない。
- 仕様としては採用済みだが、親セッション時点で実装中である。親エージェントの確認と実機での動作は未完了。

## 判断

1. Switch の電源 ON を検出して `ARMED` へ遷移した時に、既存の初回一窓音声確認を行う。初回の結果が `silent` の場合だけ、既存 `SessionPhase.STANDBY` 中のメーター購読を続ける。アプリ起動そのものは初回確認の契機としない。
2. 初回または継続窓の結果が `ok`、`unknown`、`muted` など `silent` 以外なら観測を終了する。正常な音声を確認した後は、同じ `ARMED` 期間内に `SessionPhase.STANDBY` へ戻っても観測を再開しない。
3. `silent` のままマッチング開始を認識したら観測を止める。直近の判定が `silent` のまま `STANDBY` へ戻った場合に限り観測を再開する。Switch OFF またはキャプチャー切断は現在の稼働期間を終了し、それらの後に再び `ARMED` になった場合は新しい稼働として初回確認状態をリセットする。
4. 観測の寿命と `ARMED` / `SessionPhase.STANDBY` の開始・終了ゲートは既存 `UseCase` が所有する。application service / session は設定を取得し、既存 domain event を発行してポートへ委譲する。
5. infrastructure は既存の OS 別入力解決を行い、OBS 音量メーターの購読と約 1 秒単位の有界集計を担う。約 1 秒は継続観測中の内部更新周期であり、ユーザー指定の値ではない。各窓の結果で既存の音声ヘルス通知を更新し、入力解決、閾値、`unknown` / `silent` の意味は既存契約のままにする。
6. 無音を検出しても OBS を再起動しない。監視の停止・切断処理が録画開始を待たせないようにし、録画状態、マッチング認識、描画フレームの進行にも観測待ちを持ち込まない。
7. Windows と macOS では初回確認、継続、終了、再開条件と無音時の振る舞いを共通にする。OS ごとの入力解決方法は各既存方式のままとする。
8. 音声波形の保存、新しい公開設定項目・設定 schema・domain event は追加しない。

## 検討した選択肢と棄却理由

### 短時間の観測窓を個別に開閉する既存方式を維持する

既存方式を保てるが、ユーザーが求めた「マッチング開始まで継続的に確認」を満たさないため採用しない。

### 継続観測後、長時間の無音を条件に OBS を再起動する

長い静寂と入力故障を音量だけで区別できず、ユーザーの「無音だとしても再起動しない」という明示に反するため採用しない。

### 待機へ戻るたび毎回購読を再開する

当初の説明では待機へ戻ったら再開するとしていたが、ユーザーは無音と判定されている場合だけに限定するよう訂正した。初回または直近の状態が `silent` である場合だけ再開する。

### Switch ON 時の初回確認が `silent` の場合だけ購読し、無音でも再起動しない

ユーザーの訂正後の意図を満たす。Switch 電源 ON を検出した時の既存初回窓で `silent` の場合に限り継続し、`silent` 以外の結果では観測を終了する。継続中に正常な音声を確認した後は同じ稼働期間内で再開せず、無音を理由に OBS を再起動しないため採用する。

## 適用範囲

- Windows および macOS の live session における、`ARMED` かつ `SessionPhase.STANDBY` 中の OBS 音声メーター観測。
- Switch 電源 ON 検出時の初回確認が `silent` の場合に限る継続購読、および既存音声ヘルス通知の約 1 秒ごとの有界更新。
- `silent` を理由にした OBS の自動再起動を停止する変更。
- マッチング開始、Switch OFF、キャプチャー切断、session 終了で購読を止めるライフサイクル。マッチング後の待機復帰では直近の状態が `silent` の場合だけ再開し、OFF / 切断後の新たな ARMED 遷移では初回確認から始める。

## 適用しない範囲

- Switch 電源 ON 検出前のアプリ起動を初回確認の契機にすること。
- 初回確認または直近の結果が `ok`、`unknown`、`muted` など `silent` 以外の場合の継続観測。
- `silent` が解消した後、同じ稼働期間で `STANDBY` に戻ったことだけを理由に観測を再開すること。
- マッチング開始後、録画中、Switch OFF、キャプチャー未接続、または session 終了後の継続観測。
- OBS 音声の録音・保存、波形履歴、設定可能な観測周期・閾値の追加。
- Windows または macOS の入力機器選択・解決方法、既存閾値、ヘルス通知 schema の変更。
- `unknown` と `silent` の意味変更、音声不良を理由とした録画拒否、無音以外の自動復旧方式の変更。
- `RecordingSessionService.start()` へ録画開始直前の音声検査を追加すること。この ADR は録画開始直前に音声検査があると断定せず、音声以外の既存録画開始ガードは変更しない。
- 録画状態、マッチング認識、描画フレーム、録画開始をメーター観測や購読終了の待ち状態に連動させること。
- 新しい設計指針の追加。この一回の判断を、全ての購読や監視へ一般化しない。

## 期待する効果

- 短時間の静寂を理由に OBS を再起動しなくなる。
- Switch 電源 ON 検出時に無音だった場合だけ、マッチング開始まで音声レベルと既存のヘルス通知を継続して確認できる。
- 音声を正常確認した後に待機へ戻っても不要な再購読を行わない。Switch OFF または切断後に再び ON が検出された場合は、新しい稼働として初回確認を行う。
- Windows と macOS で待機中の開始・停止と無音時の動作を揃えられる。
- 波形や音声そのものを保存せず、既存の入力解決と公開設定契約を維持できる。

## 受け入れる欠点・リスク

- 長い静寂と音声入力の故障を音量値だけで区別できない。無音でも再起動しないため、実際に入力が故障していても音声なしの録画へ進む可能性がある。
- 待機状態が続く間、OBS メーター購読を維持する。負荷および長時間接続の安定性は未計測である。
- 既存閾値は維持するため、静かな場面で `silent` の通知が続くことはあり得る。
- 初回窓で `silent` 以外だった場合は待機中の購読を続けないため、その後同じ `ARMED` 期間中に音声入力が故障しても継続通知では検出しない。
- 録画開始直前の音声検査を本判断では追加しない。旧 ADR がその入口を記録する一方、現行 `RecordingSessionService.start()` に音声検査の呼び出しはなく、文書ドリフトは未解決である。
- 実装と実機確認が未完了であり、通知更新、phase 遷移、購読終了が実機で意図どおり行われることは未確認である。

## 再検討条件

- 待機中の購読が OBS 接続の安定性やアプリの負荷に問題を生じることが実機で確認された場合。
- 無音時に再起動しない仕様と、音声なし録画を避ける要件との優先関係をユーザーが変更した場合。
- `ARMED` / `SessionPhase.STANDBY` とマッチング認識の対応が変わった場合。
- ユーザーが述べた経験と異なり、正常確認後にも音声がアプリ利用中に再び `silent` になる事例が確認され、継続監視範囲を見直す必要が生じた場合。
- OBS または obs-websocket の変更で、メーターイベントや長時間購読の契約が変わった場合。
- 入力解決、閾値、公開設定 schema を変更する別判断が必要になった場合。

- `2026-10-02` のユーザー訂正により、本 ADR 内の「待機へ戻れば再開する」という当初の記述を「直近の状態が `silent` の場合だけ再開する」へ狭める。初回確認の契機も Switch 電源 ON 検出に限定する。
- 上記の既存 accepted ADR 本文は直接変更しない。本 ADR が矛盾する範囲を後続判断として限定し、旧 ADR の残りの判断を維持する。

## 調査した根拠

### 指定された親トランスクリプト

- 音声監視の判断に関係する発言を指定された親トランスクリプトから読み直した。別セッションは探索していない。
- ユーザーは誤検知再起動と短い無音判定への懸念を報告した。親応答では当時の観測が 0.35 秒と 1 秒の二窓で、連続した長時間無音を確認していないこと、観測値の原因は未確認と説明していた。
- 続く説明では OBS の音量メーターを WebSocket で受信し、接続を維持すれば継続観測でき、音声データを保存せず最新レベルだけ扱えると述べていた。同時に、長い静寂と故障は音量だけでは区別できないと説明していた。
- 入力解決に関する親応答では、macOS はアプリ設定の機器表示名と OBS の CoreAudio 入力 device UID を OBS 提供一覧で照合し、一意に一致する入力を選び、既定マイクや別機器を除外すると説明していた。詳細な macOS 契約は `20261001-222419` を参照し、本 ADR では変更しない。
- 親エージェントの確定指示では、UseCase が購読寿命と `ARMED` / `SessionPhase.STANDBY` の開始・終了ゲートを所有する。application service / session は設定取得、既存 domain event の発行、ポート委譲を担当し、infrastructure は入力解決・購読・窓集計を担当する。録画開始時に観測窓や無期限の切断待ちを課さない。これらは設計判断の確定内容であり、完了済み実装の観測事実とは扱わない。
- 親エージェントの確定整理では、マッチングで購読を止めた後は直近判定が `silent` の場合だけ `STANDBY` 復帰で再開し、Switch OFF / キャプチャー切断後に改めて `ARMED` になった場合は初回一窓の状態をリセットする。これは受諾済み仕様だが、実機確認済みの挙動ではない。
- 親エージェントから、実装は進行中であり、親による確認と実機確認は未完了と報告された。

## ユーザー発言の原文

### 誤検知と現在の条件への質問

> まだ誤検知による再起動が発生している\
> 無音だと判断するのが早い気がする\
> どうゆう条件で無音だと判断して再起動している？

> どうゆうふうに観測してるんだっけ？\
> 観測し続けることできるの？

### 継続確認と無音再起動停止の確定

> マッチング開始されるまでは継続的に確認してほしい\
> 無音だとしても再起動しないようにして\
> (windowsとも共通仕様)\
>
> 正しい「音声入力キャプチャ」をどのように判定している？

### 観測再開条件と初回確認契機の訂正

訂正対象となった親エージェントの説明:

> 待機へ戻れば再開します

これを受けたユーザーの原文:

> 無音と判定されている時だけでいい\
> なぜなら、無音なのはSwitchオンしてアプリを使い始める時だけだったから。継続してアプリ使っている間は無音になることなかった。

親エージェントが受諾内容を説明した原文:

> 最初の確認で無音だった場合だけ、マッチング開始まで確認を続けます。音声を確認できたら観測を終了し、待機へ戻っても正常確認済みなら再開しません。実装中のサブエージェントへ反映します。

初回確認の契機を確認したユーザーの原文:

> 最初って、Switchの電源オンを検出した時ね

親エージェントの受諾:

> 「最初」は、Switchの電源ONを検出した時ですね。その時に確認を開始し、無音の場合だけマッチング開始まで続ける仕様にします。

### 変更対象となる以前の判断

以前の選択に対する質問:

> OBS の音声が無音のとき、アプリによる OBS の自動再起動を止めますか？ 今回のログでは、起動後の無音検出が終了・再起動を繰り返した原因です。以前は音声復旧のための再起動を許可いただいていました。

その時点でのユーザーの回答:

> 音声復旧のための自動再起動を維持する

この以前の回答は音声復旧方針の当時の採用内容であり、今回ユーザーが無音での自動再起動を明示的に停止したため、本 ADR の範囲では置き換える。

## 記録時セルフレビュー

- 保存直前に指定された親トランスクリプトの対象箇所を再走査し、無関係なセッションを探索していない。
- 最新のユーザー発言を原文どおり保存した。以前の単独選択回答には、受諾対象だった質問も併記した。
- 「待機へ戻れば再開します」の訂正、Switch ON 検出を初回契機とする原文、親エージェントの受諾説明を追加し、初回・再開条件を判断節とカバレッジへ反映した。
- 過去の自動再起動維持と今回の明示変更の時間的関係を記録し、曖昧な矛盾として再確認を求めていない。
- 既存入力解決・閾値・通知・`unknown` / `silent`・公開 schema を変更しない範囲を明記した。
- `20260902-123051` の常駐監視禁止と `20260902-212127` の二入口限定にも関係するため、本 ADR の置換・追補関係で該当節だけの部分変更を示した。既存 ADR 本文は変更していない。
- 1 秒窓は内部周期としてのみ記録し、ユーザー指定値に読み替えていない。
- 録画状態、マッチング、描画フレーム、録画開始を観測窓や切断待ちで遅らせないと記録した。
- 実装中、親確認待ち、実機未確認を事実として区別し、根拠を捏造していない。
- 現行 `RecordingSessionService.start()` に音声検査がないことと、旧 ADR に録画直前検査があるとの記録を分け、音声以外の録画開始ガードだけが本判断の対象外であるとした。
- 同一 ADR の判断更新として原文、置換・追補関係、カバレッジを更新し、既存 ID と作成日時を維持した。
- 登録済みの設計指針がないため、新しい指針を追加していない。
- 対象原文に機密情報、認証情報、個人の機微情報は含まれていない。
- 書き込みは本 ADR 一件のみで、他の ADR、指針、コード、テスト、AGENTS、Git に触れていない。
