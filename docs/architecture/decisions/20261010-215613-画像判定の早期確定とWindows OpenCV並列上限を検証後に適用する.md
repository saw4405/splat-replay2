# 画像判定の早期確定とWindows OpenCV並列上限を検証後に適用する

- ID: 20261010-215613
- 状態: accepted
- 日時: 2026-10-10T21:56:13+09:00
- 判断者: ユーザー（検証完了を条件とする適用許可）・メインエージェント（条件達成を確認後の採用判断）

## 目的・問題

自動録画で使う画像判定と結果解析の処理時間を改善するため、次の2案が提示された。

1. 共通 `MatchExpression` の OR / AND 評価で結果が確定した時点で、残りの画像判定を省略する。
2. Windows 起動時に OpenCV 内部の並列数を最大4にする。

ユーザーは、全てが正常に動作することを条件に適用を許可した。提案時点では両案とも未適用だった。その後、両 OS の logic 198件・performance 28件が pass し、既存の回帰・静的検証も確認された。Windows では Spectre の AC 接続・Normal 条件で正式 performance gate 28件すべてが pass した。メインエージェントはこの検証を根拠に元の2案を採用した。Mac 配布反映は録画中保護のため待機中であり、採用判断と正規版・起動中アプリへの反映は区別する。

## 前提・制約

- 1案目は Windows と Mac に共通する変更であり、自動録画で複数の画像条件を組み合わせる共通処理に及ぶ。
- 1案目の例は「黒画面である OR 電源OFF画像と一致する」である。黒画面で結果が確定した場合、後続のテンプレート照合を省略する。
- 1案目は電源OFFだけでなく、マッチ選択、試合中断、通信エラー、試合終了、勝敗画面、ロード、リザルトの複合判定にも及ぶ。
- 2案目の初期測定は Spectre の参考測定であり、結果解析は約3.77秒から約2.78秒となり、認識結果は一致したと説明された。この値は後続の正式 Windows 性能検査を通過したことを意味しない。
- 追加変更前の正式 Windows 性能検査では `extract_session_result` の5試行平均が既存の3,000 ms上限を超えた。後続候補の battery 条件でも性能基準3項目が未達だった。詳細は「現在の実装・検証状況」に記録する。
- 2026-10-11 の AC 接続・Normal 条件の Windows 正式性能検査では28件 pass・0件 fail/error/skipだった。これは Spectre での1回の正式 gate 実行であり、battery/Normal と他 Windows 端末は未確認である。
- 提案では画質、解像度、設定 FPS、判定閾値を変えない。変化し得るものとして説明されたのは処理時間と CPU 負荷である。
- 提案時の測定結果とコード上の影響範囲は親会話での報告であり、本記録役がコードや当時の元計測データを独立再検証したものではない。後続候補の検証レポートは「調査した根拠」に列挙する。

## 判断

ユーザーは、提示された2案を「全てが正常に動作するなら」適用してよいとした。検証後、メインエージェントは、両 OS の logic 198件・performance 28件、既存の回帰・静的検証、および Windows の正式 gate を確認し、この条件の範囲で元の2案を採用した。Windows の AC 接続・Normal 条件で行った正式 gate は28件 pass・0件 fail/error/skipで、`extract_session_result` の5試行平均は `2814.67796 ms`、既存上限 `3000 ms` 以下だった。実行時は source 433 hash が一致し、実 Tesseract、OpenCV helper 8→4 threads、Python Normal、TaskPriority 4 を確認した。old_score / ROI plugin は使っていない。

採用判断は Spectre の AC 接続・Normal 条件で確認した範囲に限る。正式 gate は1回であり、battery/Normal、他 Windows PC、すべての画像・実行条件での正常動作を保証しない。これ以前の battery 条件の正式性能結果25件 pass・3件 failと、局所コピー削減の旧・現行を比較した3ノード限定 ABBA 診断は履歴として保持し、AC・priority・他負荷それぞれの寄与は未分離とする。Mac対応着手前の Windows 実機と同条件で直接比較した記録は未確認であり、この ADR から Mac 対応全体が Windows 性能を変化させたとは結論しない。

記録上の最古の Windows 結果解析値は `3520.23634 ms` だが、DummyOCR 条件であり実 Tesseract の測定と直接比較できない。`3015.8963 ms` は局所コピー削減前の直近の正式 Windows 性能結果であり、Mac対応着手前の Windows 基準値とは確定していない。したがって Windows 結果解析が「最初から約3秒だった」と全期間に一般化しない。採用と配布反映も別の状態であり、Mac 配布反映は録画中保護のため待機し、commit・push も行っていない。

後続の AC/Normal 正式性能 gate は、Spectre での初回1回の実行として28件 pass・0件 fail/error/skipだった。`extract_session_result` の5試行は `[2770.7077, 2886.9054, 2772.8285, 2722.0965, 2920.8517] ms`、平均 `2814.67796 ms` で、既存上限 `3000 ms` 以下だった。source 433 hash一致、実 Tesseract、OpenCV helper 8→4 threads、TaskPriority 4、Python Normal、old_score / ROI plugin 未使用を親レビューで確認した。これは元の2案を採用する判断根拠の一部であり、battery/Normal や他 Windows PC での合格を意味しない。

計測の時系列と対象は区別する。記録上の最古の結果解析平均 `3520.23634 ms` は DummyOCR 条件であり、実 Tesseract と直接比較できない。`3015.8963 ms` は局所コピー削減前の直近の正式 Windows 結果で、Mac対応着手前の同条件実機 baseline とは確認されていない。上記 ABBA は局所コピー削減の old_score/current 比較であり、Mac対応全体の前後比較ではない。Mac対応着手前の Windows 実機と直接比較した記録は未確認のため、Mac対応全体による性能変化や「最初から約3秒」と全期間へ一般化する因果は確定できない。

追加の診断として、Astra は OpenCV 4 threads に固定したときの同時刻 CPU 状態と `_score` の処理内訳を固定条件で5回測る案を示した。この診断は完了したが、正式性能ゲートの代替ではない。診断結果を受けた新たな製品最適化には、別途ユーザー判断が必要である。

## 検討した選択肢と棄却理由

### 1. 結果確定後に残りの画像判定を省略する

結果が確定してもすべての条件を評価する現状に対し、OR / AND の結果が確定した後の評価を省略する案である。検証画像では認識結果が一致したと説明された。一方、実行されなくなる判定で発生するはずだったエラーも出なくなる可能性があるため、確認が求められた。結果が確定しない通常画像では順に評価するため遅くなる場合があり、Mac の参考測定で約25 msから約28 msになった例が説明された。

### 2. Windows の OpenCV 内部並列数を最大4にする

並列処理の過剰な負荷を抑える案である。Spectre の初期参考測定では結果解析が約3.77秒から約2.78秒となり、認識結果は一致したと説明された。局所コピー削減前の直近の正式 Windows 性能検査では、`extract_session_result` の5試行平均が3,015.8963 msとなり、既存の3,000 ms上限を超えた。その後、Spectre の AC/Normal 条件で行った正式 gate は28件 passし、同項目は平均2,814.67796 msだった。同じアプリ内の OpenCV 処理全体に及ぶため、ゲーム画面の判定、ブキ・表彰・OCR 前処理、NDI 映像の色変換などが遅くなる可能性もある。別端末・battery/Normal での性能は未確認である。

会話では、これら以外の代替案や明示的な棄却理由は記録されていない。検証条件を満たさない場合に適用しないことは、メインエージェントが確認した進行条件である。

## 適用範囲

- OR / AND による複合画像判定を行う共通 `MatchExpression` の評価。
- Windows 起動時に設定する OpenCV 内部並列数の上限4。
- 実装後の認識結果、通常処理の失敗有無、性能の確認。

## 適用しない範囲

- macOS の OpenCV 並列数を最大4にすること。
- ROI 案の製品採用。本 ADR の判断対象へ追加しない。
- 画質、解像度、設定 FPS、画像判定閾値の変更。
- Spectre 以外の Windows PC でも同じ性能改善が得られるとの保証。
- 既存の OCR 候補順序や性能閾値の変更。

## 期待する効果

- 画像判定結果が確定した後の不要な画像照合を省き、該当する画面の判定時間を短縮する。
- Windows で OpenCV の並列処理による過剰な負荷を抑え、結果解析時間を短縮する。

これらは提案時の期待であり、一般の Windows 環境で確認済みの効果ではない。

## 受け入れる欠点・リスク

- 早期確定で省略される判定が、それまで発生させていたエラーも観測されなくなる可能性がある。
- 結果が確定しない画像では、条件を順に評価するため遅くなる場合がある。Mac の参考測定には約25 msから約28 msとなった例があるが、すべての画面や環境の傾向を示す値ではない。
- OpenCV の並列数上限は結果解析だけに限定されず、同一アプリ内の他の OpenCV 処理にも影響する。処理が遅くなれば、ゲーム画面の検出、ブキ・表彰・OCR 前処理、NDI 色変換を通じて入力更新が遅れる可能性がある。
- Windows の初期約3.77秒から約2.78秒という測定は Spectre の参考値であり、後続の正式検査では既存上限を超えた。いずれも別端末の性能を保証しない。
- 既存の認識結果が一致したという報告は、未確認の画像や実行条件まで同じ結果になることを保証しない。

## 再検討条件

- 検証画像または通常利用で認識結果の差、予期しないエラー、機能上の失敗が見つかった場合。
- 性能悪化が残る、または対象処理の性能改善を確認できない場合。
- Windows の正式性能検査で既存基準を満たさない場合、または別端末・battery/Normal で不具合や性能未達が確認された場合。追加変更前の正式結果27/1と局所コピー削減後の battery 結果25/3は履歴として保持し、Spectre AC/Normal の正式 gate 28/28 passとは測定条件を分ける。どの変更または環境条件が過去の差の原因かは未確認である。
- Spectre 以外の代表端末で並列数上限による処理遅延が確認された場合。
- 「全てが正常に動作する」ための検証対象・代表端末・許容性能差を実装判断に必要な精度で定められない場合。
