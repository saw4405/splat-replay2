# macOS 配布の署名を固定の自己署名証明書に切り替える

- ID: 20261009-174403
- 状態: accepted
- 日時: 2026-10-09T17:44:03+09:00
- 判断者: ユーザー

## 目的・問題

ユーザーから、アプリ起動ごとのカメラ許可画面とアップロードごとの Keychain パスワード入力が報告され、OS 許可・パスワード要求の頻度と一度で済ませる方法の調査が依頼された。調査資料では、カメラ要求が macOS の TCC 許可か WebView のサイト許可か、Keychain の項目許可か Keychain 自体のロック解除かは特定できていない。

その調査で示された候補のうち、ユーザーは固定の自己署名証明書を選択した。本判断は、macOS アプリを再ビルド・更新しても同じコード署名 identity を維持し、OS や Keychain の許可継続性を支える土台とする。現在報告されている画面が必ず一度だけになる、または今回の原因が署名であるとは確定しない。

## 前提・制約

- 現行の macOS `.app` は ad hoc 署名で、公証されていない。`Taskfile.yml` の配布物検証も `Signature=adhoc` を期待し、`docs/DEVELOPMENT.md` は開発・検証用 ad hoc 署名として案内している。
- 先行 ADR は dmg 配布と初回 Gatekeeper 手動許可を選び、Developer ID 署名・公証を採用していない。本判断ではこの配布形式と初回案内を維持する。
- 固定 identity を維持するため、秘密鍵は macOS Keychain に保管し、ソース管理、コミット、配布アプリには含めない。再ビルド時に別の証明書を自動生成しない。
- 署名方式の移行時にカメラまたは Keychain の許可を一度求められる可能性がある。対象 Mac での実際の再許可動作は未確認である。
- 現在のカメラ画面が macOS のアプリ許可か WebView origin の許可かは未確認である。Keychain の毎回の画面も、項目アクセスの許可、Keychain のロック解除、その他のどれかは未確認である。
- 証明書の正確な名前・有効期間、どの Keychain に格納するか、鍵へのアクセス制御、紛失時の復旧・ローテーション手順、ビルド環境への安全な導入方法は未決定である。

## 判断

1. macOS 配布 `.app` のコード署名に、固定の自己署名証明書 identity を使用する。同じ証明書と秘密鍵を再ビルド・更新時にも使う。
2. 秘密鍵を Keychain に保管し、ソース管理・コミット・配布物へ含めない。再ビルド時に署名 identity を自動再生成しない。
3. dmg 配布、初回 Gatekeeper 手動許可の案内、公証なし、Developer ID 署名・公証を採用しない方針は維持する。
4. 署名 identity の継続を許可の引継ぎに役立てる意図はあるが、カメラ・WebView・Keychain の画面が一度だけになるとは保証しない。Keychain のロックや YouTube token 項目のアクセス許可も別に残る。

## 検討した選択肢と棄却理由

| 選択肢 | 判断と理由 |
| --- | --- |
| 現行 ad hoc 署名を維持する | 不採用。調査資料では ad hoc の署名 identity がビルドごとの hash に依存し、更新をまたぐ許可継続には制約があると整理された。ユーザーが固定の自己署名証明書を選択した。これが今回の画面の直接原因とは確認されていない。 |
| 固定の自己署名証明書を使う | 採用。ユーザーがこの候補を選択した。証明書・秘密鍵の保管と更新管理が必要で、初回 Gatekeeper 手動許可は残る。 |
| Developer ID 署名と公証を使う | 今回は採用しない。調査資料では配布時の Gatekeeper 体験を改善する候補として示された。ユーザーは固定の自己署名証明書を選択したが、費用、会員資格、その他の理由は明示していない。 |

## 適用範囲

- Apple Silicon 向け macOS アプリ `.app` のコード署名 identity。
- 同一の署名 identity を再ビルド・更新で維持すること、および秘密鍵を Keychain に保管すること。

## 適用しない範囲

- dmg 形式、初回 Gatekeeper 手動許可の案内、公証なしという配布判断。
- カメラ TCC、WebView の origin 許可、マイク・通知・LAN 等の個別 OS 許可の設定変更。
- YouTube OAuth token 項目の Keychain ACL、「常に許可」、Keychain 自体のロック解除。コード上の token 項目は `io.github.saw4405.splatreplay` / `youtube-oauth` であり、証明書秘密鍵とは別の Keychain 項目である。
- Windows、Intel Mac、その他の配布対象、ビルド・更新手順の実装詳細。

## 期待する効果

- 再ビルド後も同じコード署名 identity を維持し、OS が更新版を同一の署名元として扱える条件を整える。
- 署名 identity の変更に伴う許可再確認の可能性を減らすことを目指す。実際のカメラ・WebView・Keychain の許可継続は実機で確認するまで未確定とする。
- 秘密鍵をソース管理と配布物から分離する。

## 受け入れる欠点・リスク

- 自己署名証明書は Developer ID 署名や公証の代替にならない。初回起動では従来どおり Gatekeeper の手動許可を案内する。
- 秘密鍵を失う、または漏えいした場合は、同じ identity を維持した署名や安全な運用ができなくなる。紛失・侵害時の復旧と identity 変更手順は未決定である。
- 証明書の更新・交換や異なる秘密鍵でのビルドは identity を変え、OS・Keychain の再許可が必要になる可能性がある。具体的な許可への影響は未確認である。
- 固定 identity だけでは WebView origin の許可、Keychain 項目の ACL、Keychain のロック状態を変更しない。今回の繰り返し表示の直接原因も未確定である。
- 初回導入の Gatekeeper 手動許可、Keychain のロック解除、別の機能に対する OS 許可は引き続き発生し得る。

## 再検討条件

- 固定 identity に切り替えた後も同じ許可画面が繰り返され、その原因が署名 identity と関係することを追加観測で確認した場合。
- 秘密鍵の保護・利用・復旧を安全に維持できない場合、または鍵の漏えい・紛失が判明した場合。
- 配布時の初回手動許可をなくす必要が生じ、Developer ID 署名・公証への移行を検討する場合。条件と運用負担をユーザーへ示して再判断する。
- Apple の署名・公証要件または対象 macOS の対応範囲が変わった場合。

## ユーザー発言の原文

### 調査依頼（親トランスクリプト ordinal 32753）

> 起動する度にカメラの許可画面が表示される。アップロードの度にkeychainのパスワード入力画面が表示される。\
> osの許可やパスワードが必要な機能を洗い出し、どんな頻度で表示されるかを整理してください。そして一回で済む方法がないかを調査してください。

### 受諾対象となった候補（メインエージェントの調査報告、ordinal 33164）

ユーザーの回答は候補名だけのため、回答直前に提示された選択肢を併記する。

> - **現行方式を維持**：同じ版での反復確認を解消する。更新後の再許可は残り得る。
> - **固定の自己署名証明書**：署名の継続性を持たせる。秘密鍵管理が必要で、初回起動の警告は残る。
> - **Developer ID署名＋公証**：配布時の起動警告も改善できる。費用と署名運用の変更が必要。

### ユーザーの選択（親トランスクリプト ordinal 33173）

> 固定の自己署名証明書

### 選択後のメインエージェントの確認（親トランスクリプト ordinal 33178、ユーザー発言ではない）

> 固定の自己署名証明書を使う方針で進めます。秘密鍵をKeychainに保管し、再ビルド時も同じ証明書を使うよう、ビルド・更新手順を整えます。署名方式の移行時は、カメラやKeychainの再許可が一度必要になる可能性があります。
