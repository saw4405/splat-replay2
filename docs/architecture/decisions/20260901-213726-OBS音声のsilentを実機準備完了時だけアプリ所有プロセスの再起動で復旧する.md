# OBS音声のsilentを実機準備完了時だけアプリ所有プロセスの再起動で復旧する

- ID: 20260901-213726
- 状態: accepted
- 日時: 2026-09-01T21:37:26+09:00
- 判断者: メインエージェント

## 目的・問題

OBS の音声入力が設定済みで、キャプチャー映像を録画できる準備が整っているにもかかわらず、OBS から音声レベルを観測できない場合がある。実利用では OBS の再起動により復旧することが多いため、録画前に自動復旧したい。

一方、キャプチャーボード未接続、Switch 電源 OFF、ミュート、入力未設定など、音声が出ないこと自体が正当または別原因である状態では OBS を再起動してはならない。外部で起動された OBS や録画中の OBS をアプリが停止することも避ける必要がある。

## 前提・制約

- 自動復旧対象は音声検査結果の `silent` だけとする。mute、入力未設定・未検出、inactive、録音トラック未設定、unknown は既存の警告だけを維持する。
- Switch 電源状態の所有者は既存の `AutoRecordingUseCase` のままとし、音声復旧のための状態所有者や常駐ポーリングを追加しない。
- キャプチャー接続状態または Switch 電源状態を取得できない場合は、安全側として復旧しない。
- 録画開始を音声状態で拒否する外部挙動へ変更せず、復旧不能時も警告して録画を継続する。
- replay 実行プロファイルでは OBS を構築しない既存境界を維持する。
- Clean Architecture の依存方向を維持し、業務上の復旧可否と外部プロセス操作の責務を分ける。

## 判断

1. application 層の共有 `RecordingAudioHealthService` が、音声検査結果、Switch 電源状態、キャプチャー接続状態を基に復旧可否を判断する。`/prepare` と `RecordingSessionService.start()` の録画開始直前確認から同じサービスを再利用する。
2. 新しい状態所有者は作らない。Composition Root から `Callable[[], SwitchPowerState]` を渡し、既存 `AutoRecordingUseCase.power_status` を必要時に遅延参照する。
3. Switch 電源状態が `ARMED`、キャプチャー接続済み、かつ音声検査が 2 回連続で `silent` の場合だけ、自動復旧を許可する。状態取得・接続確認の失敗時は復旧しない。
4. 一つのサービス呼び出しで許可する復旧試行は一回だけとする。infrastructure 層の OBS アダプタが、プロセス所有権、接続、setup、再起動を一つの外部操作として扱う。
5. OBS operation lock 内で `GetRecordStatus` により実録画状態を再確認し、録画中なら再起動しない。アプリが起動して所有する OBS プロセスだけを再起動し、外部で起動された OBS は切断も終了もしない。
6. 再起動後は OBS の setup と音声再検査を一度だけ行う。未改善または復旧失敗でも、警告を残して録画開始を継続する。
7. replay では音声検査と復旧をともに `skipped` とし、OBS 依存を導入しない。

## 検討した選択肢と棄却理由

### `silent` を検出するたびに OBS を再起動する

キャプチャーボード未接続、Switch 電源 OFF、正当な無音、録画中、外部 OBS を区別できず、ユーザーが明示した誤作動防止を満たさないため棄却した。

### `RecordingPreparationService` が `AutoRecordingUseCase` 全体へ依存する

必要なのは現在の電源状態だけであり、依存範囲が過大になる。また、`/prepare` だけに閉じると録画開始直前の共有保証にならないため棄却した。

### `ARMED` 遷移時だけ復旧する

遷移後に発生した音声故障と、録画開始直前の再確認を扱えないため棄却した。

### `OBSRecorderController` が単独で復旧可否を判断する

OBS だけでは Switch 電源 OFF、キャプチャー未接続、正当な無音を区別できない。application の状態ポリシーを infrastructure へ持ち込むことにもなるため棄却した。

### 独立した `RecordingReadiness` 状態機械を新設する

音声、映像、デバイス、電源を統合する将来の理想案になり得るが、今回必要な録画直前の限定的復旧には状態所有と常駐処理を増やしすぎるため採用しない。

### application が安全条件を判断し、infrastructure が OBS 操作を担う

既存の Switch 状態所有権と live/replay 境界を維持しながら、プロセス所有権と実録画中ガードを OBS 操作の直前にも適用できるため採用した。

## 適用範囲

- live 実行プロファイルの録画準備と録画開始直前に行う OBS 音声検査。
- `silent` の連続確認、Switch `ARMED`、キャプチャー接続済みを組み合わせた復旧ゲート。
- アプリ所有かつ非録画中の OBS の一回限りの再起動、setup、再検査。
- 復旧不能時の警告と録画継続。

## 適用しない範囲

- mute、入力未設定・未検出、inactive、録音トラック未設定、unknown の自動修正。
- Switch 電源 OFF、キャプチャーボード未接続、状態確認失敗時の OBS 再起動。
- 外部で起動された OBS の切断、終了、再起動。
- 録画中の OBS の再起動。
- 常駐する音声監視、定期的な自己修復、新しい音声状態機械。
- replay の音声品質保証と OBS 統合。
- API/UI の外部レスポンス契約変更。
- 音声不良を理由に録画開始を拒否する動作。

## 期待する効果

- 実機録画の準備が整った状態で OBS だけが無音になった場合、録画前に既知の復旧手段を自動実行できる。
- 未接続、Switch 電源 OFF、別種の音声設定不良、録画中、外部 OBS では再起動を抑止できる。
- `/prepare` と実際の録画開始が同じ判定を使うため、入口ごとの復旧条件のずれを抑えられる。
- 復旧に失敗しても従来の録画継続と警告表示を維持できる。

## 受け入れる欠点・リスク

- 2 回の音声検査と必要時の OBS 再起動により、録画準備または開始までの待ち時間が増える。
- `ARMED` かつ接続済みでも、ゲーム側が正当に無音である場合は `silent` が連続し得る。連続確認と所有権・録画状態ガードで誤作動を減らすが、音量メーターだけで原因を完全には識別できない。
- 復旧は一呼び出し一回であり、別の準備・開始呼び出しでは再試行され得る。
- fail-open のため、復旧できない場合は音声なしの録画が作成される可能性を受け入れる。
- OBS 再起動自体が成功しても、デバイス、ドライバー、設定等が原因なら音声は改善しない。

## 再検討条件

- 正当な無音での再起動、外部 OBS の操作、録画中断などの誤作動が観測された場合。
- 一呼び出し一回の復旧でも再起動ループまたは許容できない開始遅延が生じた場合。
- OBS 再起動以外に、公式に保証された低侵襲の音声入力再初期化手段を採用できる場合。
- 音声不良時は録画を開始しないというユーザー要件へ変更された場合。
- 音声・映像・デバイスを横断する恒常的な readiness 管理が必要になり、独立状態機械の費用に見合う場合。
- OBS または obs-websocket の更新により、音量イベントまたは録画状態取得の契約が変わる場合。

## ユーザー発言の原文

ユーザーの目的と誤作動防止条件:

> obsが音声出力できていないとき、obsを再起動する等の対策を講じるようにしたい。基本的にはobs再起動したら音声出力される。再起動以外にも解決法があれば、それでもいいです。そもそもキャプチャボードが接続されていないとか、スイッチを起動してないとか、音声出力されない状況でも誤作動しないように気を付けてください。

設計助言を採用したメインエージェントの原文:

> `design_steward` の助言を採用します。復旧可否は application 層の小さな共有サービスに置き、OBS の所有権・実録画中ガード・再起動は infrastructure 層に閉じ込めます。既存の「警告して録画は継続」は維持し、復旧失敗で録画を止める仕様変更は行いません。これにより `/prepare` と録画開始直前で同じ安全判定を再利用できます。

安全条件を確定したメインエージェントの原文:

> 実装を接続しました。安全ゲートは、Switch が `ARMED`、キャプチャー接続済み、2回連続 `silent`、OBS が非録画中、かつアプリが起動した OBS であることです。再起動は1回だけ行い、直後に再検査します。ミュート・入力未設定・トラック未設定などは再起動対象にせず、従来どおり警告します。これから対象テストと型・依存方向を確認します。
