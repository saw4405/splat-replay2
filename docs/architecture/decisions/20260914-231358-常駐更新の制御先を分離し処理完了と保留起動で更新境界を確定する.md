# 常駐更新の制御先を分離し処理完了と保留起動で更新境界を確定する

- ID: 20260914-231358
- 状態: accepted
- 日時: 2026-09-14T23:13:58+09:00
- 判断者: メインエージェント

## 目的・問題

採用済みの「録画を優先して処理完了を待ち、正常終了して更新し、常駐へ戻る」を具体化する。別配置先や別ユーザーへの制御要求の混入、録画・後処理との終了競合、新版が処理を始めた後の自動復元による不整合を防ぐ。

## 前提・制約

- 常駐・データ保持は ADR `20260913-224011`、更新予約後の録画優先は `20260913-225609` に従う。
- 本 ADR の詳細は、ユーザーが個別に選択した技術として帰属させず、今回明示されたメインエージェントの実装判断として記録する。
- 過去の追加記録依頼は親トランスクリプトの一部が暗号化文字列であり取得不能だった。読めた設計助言とユーザー原文、今回の確定発言を用い、取得不能部分を推測復元しない。
- Android 認証方式の質問は未回答である。既存無認証運用の実装事実を、ユーザーの新しい承認済み方針へ昇格しない。

## 判断

1. 既存の pywin32 を利用し、正規化した配置先パスとユーザー SID、および `Local` セッション単位で分離した mutex／名前付きイベントを用いる。ユーザー限定 DACL を設定し、名前空間の分離だけをアクセス制御の代わりにしない。
2. 更新要求を LAN API として公開しない。同じ PC 上の対象インスタンスに限定して制御する。
3. 親子プロセス間の multiprocessing 信号を介し、frame 境界で Switch OFF、後処理の猶予・実行状態、未消化の PowerOff イベント、API 処理完了を確認してから受付を停止する。更新予約だけで新規録画を抑止する判断には変更しない。
4. 正常終了に失敗したら本体差し替えを中止する。mutex の消失だけで対象プロセスの正常終了を確認したことにはしない。
5. 新版を `hold` で起動し、API 応答と画面 load を確認した後で `resume` する。自動 rollback は resume 前の失敗に限る。resume 後は処理開始による副作用があり得るため、自動的に旧版へ戻さない。

## 検討した選択肢と棄却理由

| 選択肢 | 判断と理由 |
| --- | --- |
| 一つの所有者が画面・受付・終了状態を管理する | 助言で示された理想形。既存の層と所有者へ接続し、独自の並行制御基盤は追加しない。 |
| 名前付きパイプによる要求・応答 | 今回は不採用。要求 ID や詳細応答が必要になれば再検討する。 |
| mutex と名前付きイベント | 採用。既存依存で固定操作を扱える。個々の要求順序・応答を提供しない制約を受け入れる。 |
| `Local` の名前だけで制御対象を限定する | 不採用。セッション分離とアクセス制御は別であり、配置先・SID の分離と DACL を組み合わせる。 |
| 更新制御を LAN API に公開する | 不採用。今回の更新操作は PC 内で完結するため、ローカルの対象インスタンスへ限定する。 |
| 一時的な idle 判定だけで終了へ進む | 不採用。未消化イベント・後処理猶予・API 処理を残して終了する競合を防ぐため、frame 境界の完了条件へ集約する。 |
| 新版の処理再開後も自動 rollback する | 不採用。処理再開の前後を復元境界として分け、副作用発生後に機械的な旧版復元を行わない。 |

## 適用範囲

Windows 常駐デスクトップ版のローカル制御、更新予約から受付停止への遷移、正常終了確認、新版の保留起動・再開と自動復元の境界。

## 適用しない範囲

Android 認証、LAN 公開の新しい許可、OBS の起動由来・終了所有権の恒久変更、録画優先順位の変更、resume 後の手動復旧方法。今回の配布・OBS 終了・端末送信・スタートアップ登録という運用依頼も恒久ルールへ拡張しない。

## 期待する効果

制御要求を対象配置先・ユーザー・セッションへ限定し、処理完了確認と受付停止の間の競合を減らす。新版の起動確認を処理再開より前へ置き、復元可能な範囲を明確にする。

## 受け入れる欠点・リスク

- 名前付きイベントには要求ごとの応答や順序保証がない。更新状態を一つの所有者で扱い、古い準備完了通知を再利用しないことが必要である。
- Windows 固有の制御とプロセス間同期が必要になる。
- OFF・後処理・API の完了条件が成立しない間は更新が進まない。正常終了できない場合は更新を中止する。
- API と画面 load の成功だけで、実 OBS 録画や Android 端末まで含む通し動作を証明したことにはならない。
- resume 後の不具合は自動 rollback の対象外となる。本 RECORD 自体は実装・実機検証を追加実行していない。

## 再検討条件

固定操作では足りず要求 ID・詳細な応答が必要になった場合、別ユーザーやセッションをまたぐ制御が必要になった場合、処理完了条件が変わった場合、resume 後の復元に副作用の整合性を保証できる仕組みが導入された場合。Android 認証の回答は別判断として扱う。
