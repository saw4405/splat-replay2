# 設計判断の実行契約

本書は、設計助言役と設計記録役が設計判断を助言・記録するための Single Source of Truth です。
個別 ADR は判断の履歴と理由、設計指針は現在有効な抽象的判断基準を担います。

## 目的

- メインエージェントを実行に集中させながら、設計判断の意図と原文を失わずに蓄積する。
- 過去の事例と現在有効な設計指針を、将来の設計判断へ再利用する。
- 過去との矛盾を隠さず、必要な場合だけユーザーへ確認する。
- 指針を、上位目的から下位手段へ連なる抽象度の関係として段階的に整理する。

## 役割と呼び出し契約

設計判断の助言と記録は、権限と実行設定が異なる独立した役割へ分けます。
モデル、推論強度、sandbox の既定値は各実行環境の役割定義を Single Source of Truth とし、ここへ重複記載しません。

### Codex での呼び出し

- ADVISE は `.codex/agents/design_advisor.toml` の `design_advisor` を使います。
- RECORD は `.codex/agents/design_recorder.toml` の `design_recorder` を使います。
- 会話全体を継承せず、`fork_turns = "none"` とします。
- カスタムエージェント選択子 `agent_type` で役割を明示します。`task_name` は表示名にすぎません。
- 選択子を利用できない、または適用された役割を確認できない場合は、その処理の失敗として扱います。
- `sandbox_mode` は実行環境の設定で上書きされる場合があります。
- `workspace-write` はリポジトリ全体への書き込みを許すため、RECORD の書き込み先制限は sandbox だけでは強制されません。

### ADVISE

- 権限: 読み取り専用。ファイルを変更しない。
- 呼び出す時:
  - メインエージェントが新しい設計判断を行う前。
  - 選択肢に迷ったとき。
  - 既存の判断・指針と矛盾する可能性があるとき。
  - ユーザー価値、外部契約、永続データ、依存方向、層横断など重要なトレードオフがあるとき。
- 失敗時: メインエージェントがユーザーへ直接確認する。別の助言機構へフォールバックしない。

### RECORD

- 権限: `docs/architecture/decisions/**` と `docs/architecture/principles/**` だけを書き込み可能。
- 呼び出す時: ユーザーまたはメインエージェントが、後述の記録基準を満たす設計判断を確定した後。
- 失敗時: メインエージェントは保存できなかったことだけを通知し、元の作業を続ける。
  キュー、別形式の保存、重複実装は行わない。
- Git のステージ、コミット、プッシュは行わない。

## 設計判断の記録基準

次のいずれかを満たす、一つの整合した判断パッケージを一つの ADR にします。

- 責務、依存方向、状態・データ・外部契約の境界を定める。
- 有意なトレードオフを選択する。
- 今後の複数の変更に影響する。
- 既存の設計判断を変更、部分変更、廃止、または置換する。
- ユーザーが明示的に記録を求める。

次は通常、記録しません。

- 既存指針をそのまま機械的に適用しただけの作業。
- 局所的で容易に取り消せる選択。
- 命名、整形、定型的な実装手順。
- 新しい判断を含まない、過去 ADR の単なる書き直し。

既存指針の適用でも、上記の記録基準を満たす重要な適用事例は ADR にします。
運用開始前の既存設計は、過去 ADR として遡及登録しません。ADR がないこと自体は運用の障害ではありません。

## 判断権限と矛盾

- ユーザー価値に関わる新しい原則、重要なトレードオフ、外部・データ・層横断の判断はユーザーが決めます。
- 適用可能な既存設計指針がある、低リスクかつ可逆な判断はメインエージェントが行えます。
- 過去 ADR との整合は証拠であり、絶対的な前例ではありません。現在の目的への適合を優先します。
- ユーザーの判断が過去判断と曖昧に矛盾する場合は、矛盾点と影響を示して確認します。
- ユーザーが「以前の判断を撤回する」「X ではなく Y」のように訂正を明示した場合は確認不要です。
  新しい ADR から置換・変更関係を明記します。

## ADVISE の調査と判断手順

### 1. 目的・制約・不明点

対象判断が解こうとしている目的、不可変な制約、未確認事項を分けます。

理想案でも維持するもの:

- プロダクトの目的と本質的なユーザーニーズ。
- 法令、安全、セキュリティ。
- 物理的または変更不能な外部制約。
- ユーザーが明示したスコープ。

理想案を考える段階では、後方互換性、現行コード、内部 API、移行費用、既投資、短期日程をいったん外します。

### 2. 調査

責務ごとの一次情報を確認します。

| 対象 | 主な一次情報 |
| --- | --- |
| 判断の履歴・理由 | 個別 ADR |
| 現在の抽象的判断基準 | `docs/architecture/principles/**` と、既存文書中で明示された設計指針 |
| 現在の構造 | `internal_design` 等の構造文書 |
| 外部契約 | 公式仕様、規格、公式ドキュメント |
| エージェントの常時ルール | `AGENTS.md` |
| 実際の挙動 | コード、テスト、ログ、実行結果 |

外部技術が関係する場合は公式仕様・規格・原典を確認します。
確立した学術分野が判断に関係する場合は、論文や体系化された学術的視点も確認します。
関係の薄い論文を形式的に探す必要はありません。

文書と実装が食い違う場合は文書ドリフトとして明示し、都合よく一方を正しいことにしません。

### 3. 候補

必要に応じて次を整理します。実質的に同じ案を三案に水増ししません。

1. 理想案: 上記の一時的制約を外し、一次情報と学術的知見から最も望ましい構造を考える。
2. 理想に近い現実的な案: 現在のプロダクトと変更可能な制約を踏まえ、理想へ近づける。
3. 現実案: 回避策ではなく、根本原因を解く最小の構成にする。
4. 反証・不利な条件: 各案が成立しない条件や重大な欠点を挙げる。

### 4. 比較

少なくとも次を比較します。

- 目的への適合。
- 設計指針への適合。
- 正しさと安全性。
- 保守性。
- 移行リスクと費用。
- 可逆性。
- 受け入れる欠点と反論。

### 5. 適用可能な設計指針

次をすべて満たす指針だけを、判断根拠として使えます。

- `accepted` かつ現在有効、または既存 SSoT で明示的に有効な設計指針である。
- 対象のスコープと前提が一致する。
- 候補を実質的に選別できる。
- 同等以上の指針との未解決な衝突がない。
- 競合する指針がある場合、より上位の目的によって優先関係を説明できる。

一次情報や学術的知見だけでは、プロジェクト固有の判断権限は生まれません。
それらは候補の発見・評価に使い、採否は適用可能な設計指針またはユーザー判断に委ねます。

### 6. 出力

ADVISE は次の順に返します。

1. 対象目的・制約・不明点。
2. 調査結果（プロジェクト一次情報、外部一次情報、該当する学術的視点）。
3. 候補（理想、理想に近い現実案、現実案、反証）。
4. トレードオフ比較。
5. 適用する設計指針、その参照、適用条件、衝突。
6. 結論、または `判断不能` とユーザーが決めるべき判断軸。

適用可能な設計指針が候補を選別できる場合だけ、推奨案を結論にします。
それ以外は無理に判断しません。

## RECORD の記録手順

### 1. 原文の取得

`SubagentStart` フックから渡された親トランスクリプトを設計記録役自身が読みます。
トランスクリプト形式は安定 API ではないため、読めない場合は推測せず RECORD 失敗として返します。
PC 内の他セッションを探索しません。
プロジェクトフックが未承認、未読込、または親トランスクリプトを渡さなかった場合も同じです。

対象判断に関係する次を抽出します。

- ユーザー発言の原文。
- 変更の目的。
- 判断に至る経緯。
- 検討した案、反論、採否理由。
- 明示された制約、リスク、再検討条件。

`はい`、`A`、`ok` など単独では意味が確定しない回答には、直前の受諾対象となる質問・提案の原文を併記します。
対象外の雑談や作業ログは保存しません。

機密情報、認証情報、個人の機微情報が含まれる場合は保存を停止し、匿名化した原文が必要だと返します。

### 2. 正規化と原文の併記

エージェントが整理した判断だけでなく、解釈を検証できる原文を必ず保存します。
事実が不明な欄は `未確認` とし、推測で埋めません。

### 3. カバレッジ点検

会話の各判断要素を ADR の節へ対応付ける「会話カバレッジ」表を作ります。
保存直前に対象原文を再走査し、次を点検します。

- 原文の重要箇所が漏れていない。
- 要約が原意を変更していない。
- 検討した案と棄却理由が失われていない。
- 矛盾、未確認事項、再検討条件が隠れていない。

## ADR の形式

### ID とファイル名

- ID: `YYYYMMDD-HHmmss`（Asia/Tokyo の作成日時）。
- ファイル名: `<ID>-<日本語の判断概要>.md`。
- 日本語概要から Windows で使用できない文字 `<>:"/\\|?*` と末尾の空白・ピリオドを除きます。

### 状態

- `proposed`: 提案中。
- `accepted`: 採用済み。
- `superseded`: 全体が後続 ADR に置換された。
- `rejected`: 検討したが採用されなかった。
- `deprecated`: 現在は推奨されないが、置換先が一意でない。

採用済み ADR の意味は変更しません。誤字やリンク修正だけを直接行えます。
判断変更は新しい ADR を作成し、全体または節単位の置換・追補関係を記録します。

### 必須項目

```markdown
# <判断概要>

- ID: <YYYYMMDD-HHmmss>
- 状態: <proposed|accepted|superseded|rejected|deprecated>
- 日時: <RFC 3339、Asia/Tokyo>
- 判断者: <ユーザー|メインエージェント|共同>

## 目的・問題
## 前提・制約
## 判断
## 検討した選択肢と棄却理由
## 適用範囲
## 適用しない範囲
## 期待する効果
## 受け入れる欠点・リスク
## 再検討条件
## 関連する設計指針
## 関連 ADR
## 置換・追補関係
## 調査した根拠
## ユーザー発言の原文
## 会話カバレッジ
## 記録時セルフレビュー
```

外部根拠は、公式仕様名・版・節・URL・参照日、または論文名・著者・年・DOI を可能な範囲で記録し、
判断への影響は自分の言葉で要約します。外部資料の全文は複製しません。
変化しうる根拠には再確認条件を付けます。リポジトリ内根拠はファイル・節、必要な場合だけコミットを示します。

## 設計指針

設計指針は、設計上の目的・価値・望ましい品質を、それを実現する手段へ結びつける再利用可能な規範です。
複数の設計判断で繰り返し候補を選別できる必要があります。

設計指針に含められる例:

- 責務・所有権の配置。
- 依存方向。
- 状態、データ、契約の境界。
- UX 上の優先順位。
- 品質特性の優先順位。
- 複数場面で再利用できる目的と手段の関係。

設計指針ではないもの:

- テスト判断基準。
- ビルド・リリースなどの手順、コマンド、使用ツール。
- 外部仕様・要件または現行コード構造の単なる事実。
- 一回限りの実装選択。

これらは制約や証拠にはなりますが、単独で ADVISE の最終判断を正当化しません。

### ADR から指針へ昇格する条件

次をすべて満たす場合だけ、ユーザーへ新しい設計指針を提案します。

- 独立した複数 ADR に共通する構造がある、またはユーザーが一般則として明示した。
- 個別案件の固有情報を除いても意味が残る。
- 適用条件と適用しない条件を示せる。
- 候補を実質的に選別できる。
- 上位目的から下位手段への関係を説明できる。
- ユーザーが指針化を承認した。

個別 ADR の言い換えにしかならない場合は、ADR のままにします。提案中の指針を量産しません。

### 段階的な階層整理

記録時はまず目的と手段を残し、最初から抽象度を無理に確定しません。
未整理の `accepted` ADR が 5 件たまった時点で整理を提案します。次の場合は 5 件未満でも提案できます。

- 同じ目的が重複して現れた。
- 既存の目的・手段へ接続できない孤立した判断がある。
- 指針同士の矛盾または循環がある。
- ユーザーが整理を求めた。

意味を変えないファイル分割、並べ替え、リンク更新は RECORD で実行できます。
新しい抽象概念、指針、適用範囲、意味の変更は ADVISE で提案し、ユーザー承認後に RECORD で反映します。

設計指針は一ファイルに集約せず、一指針一ファイルにします。
`docs/architecture/principles/README.md` は Why–How の関係図と索引だけを持ち、本文を複製しません。
各指針は安定 ID、状態、上位目的、実現手段、適用条件、非適用条件、根拠 ADR を持ち、複数の上位目的に仕えても構いません。

## 書き込み境界

RECORD が変更できるのは次だけです。

- `docs/architecture/decisions/**`
- `docs/architecture/principles/**`

他の SSoT に更新が必要な場合は、変更せずメインエージェントへ報告します。
ADVISE は一切のファイルを変更しません。
