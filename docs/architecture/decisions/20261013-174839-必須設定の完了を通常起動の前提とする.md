## 目的・問題

一時 VM の通常セットアップで、設定を残したままアプリを開始できる導線が提案されました。ユーザーは、アプリを使うために必須の設定をセットアップで済ませることを、通常起動の前提としました。

初回記録後、ユーザーが必須範囲、機器接続・PC要件の扱い、既存環境への適用を選択しました。前回までの追補ではその選択と判定条件を記録しました。今回の追補では、OBS 32.2.2 pinned WebSocket 設定の読み取りと旧 Windows の legacy 形式に関する実装・検証状態を更新します。最終候補 `20261013-132011` のビルド確認、WebSocket server OFF 時の起動 gate、設定修復後の同一プロセス復帰、および WebSocket 接続成功が確認されました。検証の範囲外と、映像の連続性など未確認の動作も明記します。

## 前提・制約

- 確認済みの判断は、必須設定をセットアップで設定してからアプリを通常起動することです。
- 親トランスクリプト ordinal `61628` の当時の報告では、YouTube 設定は非公開で保存されていました。一方、最終画面では「実機準備のスキップ」と「文字起こし設定」が未完了として挙がり、「使用しない」を選んだ文字起こしも未完了扱いになっていました。
- ordinal `61755` と `61821` の報告では、保存済みの「使用しない」を再確定した際に完了記録が抜ける問題は局所修正され、対象テスト 8 件が成功しました。修正は配布アプリに未反映と報告されています。この保存漏れの修正は、必須設定の範囲を定める判断とは別です。
- 既存 ADR [`20261012-112028`](20261012-112028-初回セットアップ完了後にバックグラウンド自動録画を開始する.md) は、初回セットアップ完了後に自動録画を開始する条件を定めています。本追補では同じ必須判定を自動録画 gate にも使い、初回セットアップ完了の既存条件も維持します。
- 既存 ADR [`20260928-081151`](20260928-081151-macOSのキャプチャ機器を表示名で扱う.md) は、Apple Silicon 向け macOS のサムネイルで独自フォントを必須としない判断を含みます。その判断の範囲は維持し、今回、必須項目の一覧へ一般化しません。
- 初回判断時点では対象プラットフォームが未確定でしたが、今回の実装報告では Windows と macOS の両方に checker が実装されています。今回の最終 VM 確認は macOS のみで、新しい起動 gate の Windows 実機確認は未実施です。NDI と WebSocket 以外の各必須設定・必要ソフトについて、この検証で確認していない個別動作は未確認のままです。
- NDI MainOutput の設定値は、OBS/DistroAV が実際に使う構成ルートにある保存設定を読み取り専用で確認します。checker は実装済みです。初回候補 `100706` では NDI 実 API の映像が赤→緑→赤と変化し、`MainOutput` OFF で既存完了履歴を保ったまま不足画面へ移動し、ON と再検査で同一 PID のアプリが通常画面へ戻ることを VM で確認しました。最終候補 `20261013-132011` では OBS 32.2.2 / DistroAV 6.2.1 / NDI Runtime 6.3.2.0 と `MainOutput` の有効な保存値を確認しましたが、NDI の OFF→不足画面→修復の負例導線は最終候補では実測していません。最終候補の復帰後のプレビューは赤く見えた後、数分後に黒くなりました。原因は未確認で、継続した映像出力を確認した扱いにはしません。ルートを特定できない、または読み取りに失敗した場合は「不足」と断定せず「確認不能」として通常起動を止めます。
- OBS の起動、NDI ライブ接続、録画 FPS・形式の厳密な適合確認は通常起動条件に追加しません。
- WebSocket のローカル検査対象は接続先が `localhost` または明示的な loopback IP の場合に限ります。任意ホスト名を DNS 解決してローカルと判定しません。リモート OBS にはローカル保存値の検査結果を適用せず、リモート設定を「確認済み」と表現しません。
- WebSocket の保存値だけでは OBS 実行時に CLI 等で上書きされた値を保証しません。公式 `obs-websocket` はポート・パスワードの起動引数上書きを持ちます。現在調査されたアプリの起動引数に WebSocket 上書きはありませんが、これは外部から起動された OBS の実効値を保証するものではありません。
- `OBSConfigurationChecker` の JSON / `global.ini` 読み取り、legacy 6 key 優先、4接続値の照合、空白・escape を含む legacy 値処理、および NDI checker は実装済みです。関連 backend logic / contract 8 ファイルの 129 件の検証（21.68 秒）、対象 Ruff、`git diff --check` が成功したと報告されています。最終候補を macOS VM で検証し、WS server OFF 時の gate と、設定を有効にした後の修復・同一プロセス復帰・WebSocket 接続成功を確認しました。native OAuth upload、Windows 実機の新 gate、USB 等の実機同等性、OS の初回認証/Gatekeeper は確認していません。
- 最終候補の正常終了後はアプリ PID がなく、OBS が稼働したまま残ることを確認したとメインエージェントから報告されています。最終候補の native VM 検証後、テスト VM 自体も終了しています。後処理 worker の最終 report と本 ADR への記録は同時点の状態として扱い、ホスト OBS が `RECORDING` だった前回の確認待ち状態とは区別します。
- OBS 32.2.2 の pinned obs-websocket module JSON は `Locations.Configuration` に追随せず、`GetAppConfigPath` が返す global / portable base を使います。NDI の `user.ini` は user configuration location に従うため、root resolver は platform default の解決だけを共用し、WebSocket と NDI の保存先を分けます。
- 旧 Windows 環境の最低 OBS 版を引き上げずに対応するため、`global.ini` の `[OBSWebSocket]` にある pinned 版の完全 legacy 形式も読み取り対象とします。legacy 形式が partial または不正なら `unverified` となり、旧環境をすべて通常起動可能にする保証はありません。
- legacy と JSON が共存する際は pinned 公式移行の優先順に従います。どちらの形式も読み取りのみで扱い、移行・書き込みは行いません。全 obs-websocket 版との互換性や起動引数 override 後の実効値は保証しません。
- final candidate VM では OBS WebSocket server ON / auth ON / port 4455 を使い、修復後の WebSocket 接続成功を確認しました。これは native OAuth や YouTube upload の成功、全機能の動作を保証しません。NDI `ndi_output_stop` に続く OBS shutdown crash は未解決の別問題で、この checker で修正されたものではありません。
- Tart VM の入力停止、黒画面、保存復帰時の `VZErrorDomain12` は VM 操作上の事象として報告され、アプリの checker の失敗・修正とは別に扱います。
- ユーザーが選んだ範囲外の任意機能一覧は未確定です。字幕を使用しない選択と独自フォントの OS 標準フォントへの fallback は必須不足にしません。
- 新しい永続 schema、既存環境の実稼働保証、アップロード成功の保証は承認されていません。

## 判断

1. 通常起動に必要な機能範囲は、録画・判定・編集・YouTube とします。その範囲の設定と必要ソフトを起動条件に含めます。初回の実機動作、PC の最低要件や利用者の自己申告は起動条件にしません。
2. 現在の設定と必要ソフトの充足を、application 層の stateless な共通必須判定で扱います。同じ判定を status、セットアップ完了 API、最終 navigation、初回自動録画の開始判定から利用します。必須不足または必須判定の未完了・失敗時は通常画面と自動録画を許可しません。検査結果のプロセス内 cache と同期は、application 層に状態を持ち込まず、専用 port と infrastructure 専用 adapter に置きます。設定ファイル・ソフトの読み取りも infrastructure 責務です。一時的なネットワーク障害自体は必須条件に含めず、通常画面を止める理由にしません。
3. 判定はチェックボックス履歴ではなく、保存済み設定と利用可能な必要ソフトを根拠にします。履歴は修復完了の証明に使わず、既存の完了履歴・導入日・その他の設定を保持したまま、不足項目だけを修復へ案内します。実設定が有効なら、古い履歴だけを理由に再設定を求めません。旧環境に完了履歴がなく通常の前後移動で不足箇所へ到達できない場合に備え、現在の不足一覧に含まれる `code` だけを受け付ける `POST /setup/repair/{code}` を設けます。application が `code` から移動先 step/substep を決め、既存 repository には `current_step` だけを保存します。修復選択自体は履歴・必須充足・通常起動許可を変更しません。未知または stale な `code` は拒否し、frontend は不足一覧を更新します。frontend は成功した正規 issue 応答を受けてから substep を保存し、対応カードへ移動します。status の読み取りが毎回先頭の不足項目へ戻さず、選択した修復先が引き続き不足なら維持します。汎用的な任意 step 移動 API は追加しません。
4. Switch が OFF、設定済み機器が一時的に未接続、PC 要件の自己申告、または一時的なネットワーク障害であることだけを理由に通常画面を止めません。ネットワーク疎通自体は必須条件として検査しません。機器や電源の稼働状態と、保存設定・必要ソフトの不足を区別します。
5. 字幕を「使用しない」とする設定を完了として扱い、独自フォントがなく OS 標準フォントで代替できる場合は不足にしません。YouTube は、読み取り可能な client 認証設定と有効な公開範囲設定を必須とします。起動ごとの OAuth 再認証や、アップロード成功までは必須条件にしません。
6. 重い検査はアプリ起動時に一度行い、設定保存・ソフト導入後に結果を無効化または更新し、完了判定時に再評価します。status のポーリングは保持済み判定結果を参照します。「未検査」と「検査済みで不足なし」を区別します。無効化より前に開始した検査の結果が、無効化後に遅れて完了しても現在の結果へ戻らないようにします。必須検査が未完了または失敗した状態を充足として扱いません。
7. NDI MainOutput の保存値は、読み取り専用の infrastructure checker で、標準・portable・`Locations.Configuration` により解決した OBS 構成ルートの `[NDIPlugin] MainOutputEnabled` を確認する方法を採用します。構成ルートが不明または読み取りに失敗した場合は、設定不足ではなく確認不能 issue として通常起動を止めます。OBS の起動・ライブ接続や録画 FPS・形式の厳密な制限は追加しません。checker は実装済みです。NDI MainOutput OFF 時の不足画面と、ON・再検査後の同一 process 復帰は初回候補 `100706` の VM で確認しました。最終候補 `20261013-132011` では NDI の有効な保存設定とバージョンを確認しましたが、NDI の OFF→修復負例は実測していません。最終候補での OFF 時の通常画面 block、ON 後の修復と WebSocket 接続成功は OBS WebSocket 検査の結果です。映像連続性は確認していません。
8. ローカル OBS WebSocket では、pinned OBS 32.2.2 obs-websocket の module JSON を `GetAppConfigPath` が返す global / portable base から読み、`Locations.Configuration` には追随させません。NDI `user.ini` とは保存先が異なるため、platform default の root 解決だけ共用し、保存先解決を混同しません。アプリに保存された host/port と OBS の `server_enabled`・有効な server port を照合し、server 無効または port 不一致は既存の WebSocket パスワード設定カードに不足 issue を示します。OBS 認証が有効な場合に限り、保存された server password とアプリ側 password を infrastructure 内で trim 等による正規化なしに完全一致比較します。認証情報や設定内容は外部へ返さず、判定状態だけを返します。`auth_required=true` 自体は新たな必須条件にしません。既存のアプリ側 password 必須条件は維持します。
9. 旧 Windows 環境の最低 OBS 版引上げを避けるため、`global.ini` の `[OBSWebSocket]` legacy 設定も読み取り対応します。pinned obs-websocket の公式移行キーは `FirstLoad`、`ServerEnabled`、`ServerPort`、`AlertsEnabled`、`AuthRequired`、`ServerPassword` の6個であり、いずれかの user value が存在する場合は legacy を JSON より優先します。判定用の接続4値 (`ServerEnabled` → `server_enabled`、`ServerPort` → `server_port`、`AuthRequired` → `auth_required`、`ServerPassword` → `server_password`) が全て型・値域とも妥当な場合だけ照合し、INI boolean は OBS と同じ解釈で扱います。legacy 判定が優先された場合、partial または不正な legacy 値を module JSON で補完せず `unverified` issue とします。legacy 移行・設定書込みは行いません。
10. 設定 root の解決失敗、読取失敗、不正形式、解釈できない版・型、legacy partial / 不正値は不足と断定せず `unverified` issue として通常起動を許可しません。欠落値を `false` と推定しません。OBS の既知 platform-default root 解決と共通判定 cache / 明示的再検査の経路を再利用しますが、NDI `user.ini` と WebSocket module JSON / legacy `global.ini` の保存場所は個別に解決します。OBS 側で保存した変更が検査に反映されるよう、既存の明示的な再検査導線を使います。WebSocket の live 接続、Keychain/OAuth、ネット疎通を startup 条件には追加しません。
11. 必須判定のための新しい永続データ schema、依存追加、build 設定変更や、現実の機器が接続・稼働することの保証は追加しません。

## 検討した選択肢と棄却理由

| 選択肢 | 採否と理由 |
| --- | --- |
| 未設定項目を残して通常画面へ進めるボタンを、最後の警告に表示する | 必須設定が未完了の場合の通常起動を認める案としては不採用です。ユーザーが必須設定の完了を通常起動の前提と決めたためです。任意項目だけを残す導線の可否は未決定です。 |
| 必須設定が完了するまで通常画面へ進めない | 採用です。ユーザーの明示した開始条件に一致します。 |
| 録画・判定・編集までを必須とし、YouTube は任意にする | 不採用です。ユーザーは YouTube までを必須に含める案を選びました。 |
| 保存設定・必要ソフトだけでなく、初回の実機動作や PC 最低要件も必須にする | 不採用です。ユーザーは設定・必要ソフトを必須とする案を選びました。Switch OFF や既設定機器の一時切断は通常画面を止めない条件とします。 |
| 既存のセットアップ完了済み環境を今回の検査対象外にする | 不採用です。ユーザーは既存環境にも不足項目だけ修復する案を選びました。 |
| 旧環境で履歴を補完する、または通常の前後移動だけで不足箇所へ進ませる | 不採用です。履歴を変えずに不足箇所を選べる `POST /setup/repair/{code}` を採用し、application が現在の不足 `code` だけを解決します。 |
| 任意 step に移動できる汎用 navigation API を追加する | 不採用です。修復 API は現在の不足一覧にある項目だけを扱います。 |
| アプリに WebSocket パスワードが保存されていることだけでローカル OBS WebSocket の必須条件を充足扱いにする | 不採用です。保存済み OBS server enabled・port とアプリ設定を確認し、認証が有効な場合はパスワードも比較します。 |
| OBS 認証を必ず有効にする、remote OBS の設定を local 構成から推定する、または live 接続を startup 条件にする | 不採用です。認証有効化は強制せず、local checker は loopback に限定し、live 接続・ネット疎通は条件にしません。 |
| 旧 Windows 環境の設定互換性のため最低 OBS 版を引き上げる | 不採用です。pinned 版が定める完全な legacy 値を読み取り対応します。ただし部分・不正形式まで起動可能と保証せず、`unverified` とします。 |
| legacy と module JSON を併合し、不足する legacy 値を JSON で補う | 不採用です。pinned 公式実装では6 migration key のいずれかが存在すると JSON 読込みが省略されるため、legacy 優先にし、partial 値を別形式で補完しません。 |

判定責務、cache の一貫性、限定された修復 API、NDI 保存値の読み取り方法は助言を採用した実装条件です。実装済みという報告と限定された検証結果は別途記録しますが、機器・アップロードの実稼働保証や、WebSocket checker を含む最終ビルド・VM 確認へ拡張しません。

## 適用範囲

- 必須設定が未完了の状態から、アプリの通常画面へ移行する開始条件。
- 録画・判定・編集・YouTube の設定と必要ソフトを確認し、セットアップ完了 API と最終 navigation を判定する条件。
- 同じ必須判定を通常画面と初回自動録画の gate で共有する条件。
- 既存セットアップ完了済み環境の保存設定・必要ソフトを検査し、不足項目のみ修復する条件。
- 必須判定を stateless な application 層に置き、process 内 cache・同期を専用 port / infrastructure adapter に置く責務境界。
- 既存履歴のない環境が、現在不足している項目だけを選んで修復へ進む API の契約。
- NDI MainOutput の保存値を、正しい OBS 構成ルートから読み取り専用で確認する条件。
- ローカル loopback OBS の保存済み WebSocket server/port と、認証有効時の password 一致を検査する条件。
- OBS 32.2.2 pinned module JSON と legacy `global.ini` の別個の保存先、および旧形式の読み取り専用互換条件。

初回判断時点では対象プラットフォームが未確定でしたが、今回の実装報告では Windows / macOS の両方に checker が実装されています。最終候補 `20261013-132011` の build と native VM 確認は完了しました。確認は macOS VM に限られ、Windows 実機での新 gate、全 macOS 機能、OAuth upload、USB 等の機器同等性、OS の初回認証 / Gatekeeper は未検証です。NDI と OBS WebSocket 以外の個別設定検査も今回の最終候補確認の対象外です。

## 適用しない範囲

- 選択した基本導線以外にある機能の必須・任意の分類。
- OBS を起動した状態での NDI ライブ接続、録画 FPS・形式の厳密な適合確認。
- remote OBS の構成検査、DNS 解決による任意 hostname の local 判定、OBS WebSocket の live 接続や runtime CLI override の保証。
- 全 obs-websocket 版との保存形式互換、legacy 部分設定を JSON 等で補完する migration、legacy 設定の書込み・修復。

- 任意 step へ自由に移動する汎用 navigation API。
- 自動録画 worker の所有者・待機 lifecycle の変更、および後処理 worker の開始条件変更。
- 新しい永続 schema、現実の機器・ネットワーク・YouTube の実稼働成功を保証する仕組み。

## 期待する効果

- 必須設定が済んでいない状態で通常画面へ進むことを防ぎます。
- セットアップを通常起動の前提にするというユーザー判断を、開始導線の基準として残します。
- ローカル OBS WebSocket では、アプリ側に認証情報があるだけで server 無効状態を見逃す判定の穴を補います。
- 完全 legacy 設定を読み取れる旧 Windows 環境に対して、最低 OBS 版を引き上げずに判定できる場合があります。ただし legacy の部分設定や不正値を `unverified` とするため、旧環境すべての利用継続を保証しません。
- 既存環境では過去のチェック履歴に頼らず現在の設定・ソフトの不足を確認し、不足項目だけの修復へ案内できます。
- 通常画面・完了処理・初回自動録画が同じ必須判定を利用し、判定の不一致を減らせます。

この ADR は方針と実装・検証状況の記録です。最終候補 `20261013-132011` の build / signature / DMG 検証と macOS VM での必須 gate・修復・WebSocket 接続確認は完了しました。関連 8 backend logic / contract ファイルの 129 件、対象 Ruff、`git diff --check` も成功しました。確認できた内容と未確認の機能範囲を以下に分けて記録します。

## 受け入れる欠点・リスク

- NDI MainOutput checker は実装済みです。初回候補 `100706` の macOS VM では保存値と OFF 時の不足 gate・修復を確認しました。最終候補 `20261013-132011` では DistroAV 6.2.1 / NDI Runtime 6.3.2.0 / OBS 32.2.2 の環境と NDI 有効保存値を確認しましたが、NDI の OFF 負例 gate・修復は確認していません。全構成の組合せや Windows 実機も網羅しておらず、誤った root を読む場合は別構成の状態を誤判定するおそれがあります。
- cache の無効化と並行する古い検査の完了順を誤ると、設定変更後の最新状態を失うおそれがあります。無効化後に古い結果を再登録しない条件が必要です。
- WebSocket の保存値確認は server が起動していることや runtime CLI override の不存在を証明しません。保存値だけで `ConnectionRefused` の原因を断定できません。unknown root/schema を誤って不足扱いしないよう、`unverified` と不足を区別する必要があります。
- 公式移行 marker を含む legacy 部分値は module JSON に有効な補足があっても `unverified` となり得ます。このため、既存 Windows 環境を一律に通す互換性は保証できません。完全 legacy 値だけを対象とした限定的な読み取り互換です。
- 実機動作や YouTube upload 成功を起動条件としないため、通常画面へ進めても現実の録画・アップロードが直ちに成功する保証はありません。
- 最終候補では Main READY の赤い test preview を確認しましたが、数分後に preview が黒くなり原因は未確認です。連続映像出力は検証済みとしません。NDI shutdown crash (`ndi_output_stop`) も未解決です。
- 最終 candidate gate は macOS VM の保存設定・修復フローに限る確認です。Windows 実機の新 gate、全 macOS 機能、native OAuth / upload、USB 同等性、OS 初回認証 / Gatekeeper は検証していません。
- Tart VM の input 不達、黒画面、復元時の `VZErrorDomain12` は VM 基盤側の事象として記録され、アプリ checker の結果に混同しません。
- 保存値・ソフトの検査が誤って不足を返すと、既存利用者も修復画面へ誘導されます。修復時には履歴・導入日・他の設定を保持し、不足項目だけを示す条件を守ります。
- 一時的な機器未接続やネットワーク障害を設定不足として扱わないため、設定値の妥当性と稼働状態の切り分けは検査ごとに必要です。
- 既存 ADR が定める初回セットアップ完了と今回の必須判定は別の条件として扱います。既存の完了記録だけでは現在の必須条件を満たす証明になりません。

> 既存のセットアップ完了済み環境にも、不足設定の検査を適用してよいですか？ 推奨案は実際の保存設定を検査し、不足がある項目だけ修復へ戻します。完了履歴や他の設定は消さず、チェック記録が古いだけなら実設定を優先します。AGENTS.mdの設計判断契約に従い、既存利用者への影響があるため確認しています。

- 既存環境も不足項目だけ修復する（推奨）
- 既存の完了済み環境は今回の検査対象にしない

ユーザー回答原文:

> 既存環境も不足項目だけ修復する（推奨）

回答は親トランスクリプト ordinal `62053` の入力です。各回答を直前の質問と対応付けて記録しました。
