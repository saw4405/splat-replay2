# OBS音声readinessの実検査入口をARMED遷移時と録画開始直前に限定する

- ID: 20260902-212127
- 状態: accepted
- 日時: 2026-09-02T21:21:27+09:00
- 判断者: 共同

## 目的・問題

OBS 音声 readiness の実検査が録画準備 API、Switch の `ARMED` 遷移時、録画開始直前の 3 入口にあり、録画準備 API と状態遷移で近接して同じ検査・復旧が走り得る。`20260902-123051` で定めた readiness ゲートと安全な復旧条件を維持しながら、準備処理の責務と音声検査の実行時点を簡素化する。

## 前提・制約

- readiness の確認順序は「キャプチャーボード接続 → Switch 電源状態 → OBS 音声」を維持する。
- 非 `ARMED`、キャプチャーボード未接続、または接続・電源状態の確認失敗では OBS 音声を実検査せず、`skipped/healthy` を通知して既存の音声警告を消す。
- `20260901-213726` の 2 回連続 `silent`、アプリ所有かつ非録画中の OBS だけを対象とする一回の再起動、setup 後の再検査、外部 OBS 非操作、replay `skipped`、fail-open を維持する。
- `20260902-123051` の Switch 状態所有権、`ARMED` 遷移時の検査、録画開始直前の安全網を維持する。
- 録画準備 API のレスポンス形は維持する。音声警告フィールドは `null` のまま返す。
- 実機での Switch ON、音声検査、必要時の OBS 復旧、録画開始までの一連の動作は未確認である。

## 判断

1. 録画準備 API は OBS の setup までを責務とし、OBS 音声 readiness の実検査と復旧を行わない。
2. OBS 音声の実検査入口は、Switch が `ARMED` へ遷移した時点と録画開始直前の 2 つに限定し、同じ共有音声ヘルス経路を利用する。
3. Switch 電源状態の遷移通知では共有経路を利用するが、非 `ARMED` 時は OBS へ問い合わせず `skipped/healthy` を発行する。したがって、非 `ARMED` 遷移は警告クリアの入口であり、OBS 音声の実検査入口には数えない。
4. `ARMED` 時の共有経路は「キャプチャーボード接続 → Switch 電源状態 → OBS 音声」の順に readiness を確認し、2 回連続 `silent` の場合だけ既存の安全条件で OBS を再起動し、復旧後に再検査する。
5. 状態遷移時と録画開始直前の検査・通知は引き続き fail-open とし、音声検査または復旧の失敗を理由に Switch 電源監視や録画開始を停止しない。

## 検討した選択肢と棄却理由

### 録画準備時・ARMED遷移時・録画開始直前の3入口を維持する

同じ共有経路で判定条件のずれは抑えられるが、準備直後に `ARMED` が成立する場合は同じ音声検査と復旧判断が近接して重複する。録画準備 API に音声 readiness の責務を残す必要性がなく、入口を増やす保守負担も残るため棄却した。

### ARMED遷移時と録画開始直前の2入口に限定する

Switch ON の成立時に早期警告・復旧する機会と、遷移後に発生した故障を録画直前に捉える安全網を両方維持できる。録画準備 API から重複責務を除けるため採用した。

### ARMED遷移時だけ検査する

遷移後から録画開始までに発生した音声故障を扱えず、`20260901-213726` と `20260902-123051` が維持した録画開始直前の安全網を失うため棄却した。

### 録画開始直前だけ検査する

Switch ON が確定した時点で音声を改めて確認するという既存要件を満たさず、録画前に警告・復旧する時間も失うため棄却した。

### 3入口を維持し、キャッシュや時刻で重複を抑止する

入口ごとの責務は減らず、キャッシュの有効期限と無効化条件という新しい状態判断が必要になる。今回の重複は準備 API から検査を外すことで根本から解消できるため採用しない。

## 適用範囲

- live 実行プロファイルの録画準備 API、Switch 電源状態遷移、録画開始直前の OBS 音声 readiness。
- 共有音声ヘルス経路の呼び出し時点と、実音声検査入口の限定。
- 非 `ARMED` 遷移時の `skipped/healthy` 通知と既存警告のクリア。
- 録画準備 API の既存レスポンス形と、音声警告フィールドを `null` とする契約。

## 適用しない範囲

- readiness の確認順序、キャプチャー接続判定、Switch 電源状態判定の変更。
- 2 回連続 `silent`、OBS プロセス所有権、録画中ガード、再起動回数、復旧後再検査、fail-open、live/replay 境界の変更。
- 音声不良を理由に録画開始を拒否する仕様変更。
- ponytail-review で同時に指摘された未使用 `config` 配線、転送専用メソッド、復旧結果の二重状態の局所的な簡素化。これらは本 ADR の設計判断には含めない。

## 期待する効果

- 録画準備 API と `ARMED` 遷移時の近接した重複検査をなくす。
- Switch ON 確定時の早期検査と録画開始直前の安全網を維持する。
- 音声 readiness の責務を、実機状態の成立を所有する状態遷移と実際の録画開始へ集約する。
- 非 `ARMED` 時には OBS を検査せず、古い警告だけを確実に消す。

## 受け入れる欠点・リスク

- 録画準備 API の完了時点では OBS 音声の実測結果を得られず、音声警告フィールドは `null` になる。
- `ARMED` 遷移が発生しない状態では、録画開始直前まで音声故障を検出しない。
- `ARMED` 遷移時と録画開始直前が近い場合、この 2 入口間では検査が近接して実行され得る。
- fail-open のため、検査または復旧に失敗した場合は音声なしの録画が作成される可能性を引き続き受け入れる。
- `skipped/healthy` は音声正常の実測ではなく、現在は評価対象外で警告しないことを意味する。

## 再検討条件

- 録画準備 API の利用者が、準備完了レスポンスで音声の実測結果を必要とする外部要件が生じた場合。
- `ARMED` 遷移が発生しない導線で、録画開始前の早期警告・復旧が必要と判明した場合。
- `ARMED` 遷移時と録画開始直前の 2 入口でも許容できない重複負荷または開始遅延が観測された場合。
- 実機確認で、Switch ON 後の検査、非 `ARMED` 時の警告クリア、OBS 復旧後の再検査、または録画開始の継続に問題が判明した場合。
- 音声・映像・デバイスを横断する恒常的な readiness 管理が必要になり、独立状態機械の費用に見合う場合。
