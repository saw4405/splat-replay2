# 終了通知でSSE配信を閉じ正常終了の循環待ちを解消する

- ID: 20260920-154021
- 状態: accepted
- 日時: 2026-09-20T15:40:21+09:00
- 判断者: メインエージェント

## 目的・問題

完全終了の要求を受理し、受付を停止しても、画面への SSE 常時接続が残って Uvicorn の lifespan 終了へ進めず、OBS とアプリのプロセスが残留する循環待ちを解消する。先行 ADR で扱った Switch 停止待ちの問題に加え、配布版の実確認で見つかった別の終了阻害要因である。

## 前提・制約

- 完全終了と更新予約の待機条件、録画・後処理・API の保護、OBS 所有権は既存判断を維持する。
- 今回は終了決定後の通知伝播を修復する。SSE 側で終了可否を新たに決めない。
- 親セッションでは配布版が 45 秒待っても終了せず、終了要求受理のログがあったと報告されている。今回の明示 RECORD 依頼では、専用 WebView 接続の解放直後に OBS が正常終了した実観測も根拠として示された。本 RECORD による独立した実機観測ではない。

## 判断

1. 既存の親 `shutdown_event` を、`webview_app.py` の `desktop_app` ラッパーから `app.state.desktop_shutdown_event` へ注入する。`desktop_signals` がなくても `shutdown_event` がある起動経路ではラッパーを使う。
2. `events.py` の progress と domain-events の両ジェネレータが、既存の poll ループで終了通知を確認し、通知済みなら配信を終了する。既存の空キュー時 0.1 秒待機を利用する。
3. domain-events の購読解除を行う `finally: sub.close()` を保持する。ストリーム終了後に Uvicorn が lifespan の後片付けへ進み、既存の監視・仮想カメラ・OBS の正常終了へ到達できるようにする。
4. この問題を強制 timeout やライブラリ内部状態の変更で処理しない。別の通知基盤や新しい並行制御基盤も追加しない。

## 検討した選択肢と棄却理由

| 選択肢 | 採否と理由 |
| --- | --- |
| サーバーと全ストリームが共有する終了通知 | 助言の理想形。今回の既存 `shutdown_event` の注入で実現する。 |
| 既存イベントを両 SSE へ注入し poll から確認する | 採用。終了条件の所有者を変えず、既存の仕組みで通知を届けられる。 |
| 別の終了通知基盤を追加する | 不採用。既存イベントで足りるため。 |
| ライブラリ内部状態を書き換える、強制 timeout で終了を進める | 不採用。今回確定した方針は、配信自身の正常終了と購読 cleanup により循環待ちを解消するものである。 |
| `desktop_signals` がある経路だけ注入する | 不採用。終了イベントだけを持つ起動経路にも同じ通知が必要である。 |

## 適用範囲

デスクトップ起動経路の終了イベント注入と、progress／domain-events SSE 配信の終了通知・購読解除。

## 適用しない範囲

録画・後処理の終了条件、更新予約の録画優先、OBS 所有権、外部接続の認証、ソケット送信停止時の終了上限、運用上の旧版プロセス終了許可。今回の配布操作に関する個別承認を恒久ルールへ拡張しない。

## 期待する効果

画面が SSE を購読したままでも、親の終了通知からストリーム終了、lifespan 完了へ進める。画面接続を手動で切ることを完全終了の前提にしない。

## 受け入れる欠点・リスク

- 0.1 秒は空キュー時の確認周期であり、ソケット送信自体が停止した場合の終了時間の上限ではない。
- イベント注入を欠くデスクトップ起動経路では同じ問題が残り得るため、`desktop_signals` の有無と注入条件を混同しない。
- 親からは実 TCP の 2 本の SSE 接続を維持した回帰と関連 11 件の成功が報告されたが、追加修正済み配布版の実機通し確認は記録時点で未確認である。

## 再検討条件

新しい常時接続経路を追加した場合、通知後もストリーム終了が進まない場合、ソケット送信の停止が観測された場合、Uvicorn／sse-starlette の終了契約が変わった場合。送信停止に対する timeout は今回承認したものではなく、その時点で別途判断する。

## 関連する設計指針

`backend/src/splat_replay/interface/AGENTS.md` の「長時間接続の cleanup とエラーハンドリングを必ず実装」と、ルート `AGENTS.md` の最小変更・層の責務を適用する。終了可否の判断は application 側に残し、interface 側は決定済みの終了通知で接続を閉じる。独立した新しい設計指針は作成しない。

## 調査した根拠

- フック指定の親トランスクリプト `rollout-2026-09-13T21-50-44-01a09ad1-eddd-7563-85fb-b0a0e316cf83.jsonl`（セッション ID `01a09ad1-eddd-7563-85fb-b0a0e316cf83`）を自身で取得した。行番号は記録時点のもの。
- 1674 行の当初要求、2046・2060 行の確認継続、2098 行の実配布での未終了、2136 行の原因報告、2161 行の `shutdown_advice`、2189 行の回帰結果を確認した。
- `backend/src/splat_replay/interface/gui/webview_app.py` の `desktop_app` とラッパー選択条件、`backend/src/splat_replay/interface/web/routers/events.py` の両ジェネレータと購読 cleanup を読み、今回の判断との対応を確認した。コード編集は行っていない。
- 助言は導入済み Uvicorn の「接続・タスク完了後に lifespan 終了」という順序と、sse-starlette の ContextVar 内通知の限界を根拠としている。本 RECORD では依存ライブラリの原典を再取得していないため、版・該当節は未確認。依存更新時は再確認する。
- 学術資料を新しい採否根拠として追加していない。既存契約・関連 ADR・interface 層 AGENTS.md を確認した。

## ユーザー発言の原文

当初の不具合報告（1674 行から対象部分）:

> タスクトレイのアイコンから完全終了を選択したのに終了されなかった。

再開要求の対象説明（メインエージェント、2046 行）:

> デスクトップ版の更新が完了し、設定・動画など5,237ファイルのハッシュ一致を確認しました。続いて、OBSがトレイ起動した状態で、配布版の完全終了と再起動を確認します。

ユーザーの確認継続要求（2060 行）:

> 続けて

配布版での追加不具合（メインエージェント、2098 行）:

> OBSのトレイ起動は確認できましたが、配布版の完全終了は45秒待っても完了しませんでした。終了要求の受理はログに残っているため、後段の待機条件か監視処理に別の問題があります。ここを追って修正します。

原因報告（メインエージェント、2136 行）:

> 追加の原因が分かりました。終了要求は通っていますが、画面への常時イベント配信（SSE）が接続されたままで、サーバーが後片付けに進めず待ち続けています。終了通知で配信も閉じ、録画監視・OBSの正常終了へ進めるようにします。

助言（2161 行の採否・候補・条件・限界から原文抜粋）:

> 提示案を推奨します。終了条件の判断を変えず、終了決定後の通知を SSE まで届ける修復です。
>
> - **候補比較**：理想はサーバーと全ストリームが共有する終了通知です。今回は既存 `shutdown_event` の注入で実現でき、別通知基盤やライブラリ内部変更は不要です。
>
> - **実装条件**：両ジェネレータで通知を確認し、`finally: sub.close()` を維持してください。`shutdown_event` がある起動経路には、`desktop_signals` の有無によらず注入が必要です。
> - **限界**：0.1 秒は空キュー時の確認周期であり、ソケット送信自体が停止した場合の終了上限ではありません。今回の原因修復と、その別問題を区別してください。

今回の確定判断と記録依頼（メインエージェント、本 RECORD 呼び出し全文）:

> RECORD追補。実配布でquit受理し受付停止後もOBS/プロセス残留を観測。原因はSSE常時接続でUvicornがlifespan終了に入れない循環待ち。今回メイン判断として、既存親shutdown_eventをdesktop_app経由app.state.desktop_shutdown_eventへ注入（desktop_signalsがなくてもshutdown_eventがあればwrapper使用）。events.pyのprogress/domain両ジェネレータで既存0.1秒pollループから終了通知を確認しreturnし、購読finallycloseを保持。強制timeoutやライブラリ内部状態変更しない。ADVISE shutdown_advice済み。実TCPの2本SSE接続維持した回帰で親通知→stream終了→lifespan完了を確認、関連11件成功。旧版は専用WebView接続を解放した直後にOBS正常終了し、この診断の実根拠あり。現在再ビルド中。既存ADR追補関係で原文を保持、コードは触らない。
