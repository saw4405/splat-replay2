# デスクトップ起動を二段表示しbackend準備と並行させる

- ID: 20260909-201235
- 状態: accepted
- 日時: 2026-09-09T20:12:35+09:00
- 判断者: 共同

## 目的・問題

Windows の配布用実行ファイルを起動したとき、コマンドプロンプトを表示せず、アプリが起動処理を受け付けたことを早く利用者へ示す。

従来は別プロセスの backend が health check に成功してから pywebview ウィンドウを作っていたため、それまでアプリ固有の画面が表示されなかった。ユーザーは実行から画面表示までを努力目標 1 秒、目標 3 秒以内とし、困難ならスプラッシュ画面を検討するよう求めた。

## 前提・制約

- Windows 配布物は PyInstaller の `onedir` 形式と pywebview を使う。
- FastAPI/uvicorn backend の別プロセス所有と、アプリ終了時の process cleanup を維持する。
- 追加依存を導入せず、既存の `backend/assets/icon.png`、PyInstaller、pywebview の機能を使う。
- スプラッシュの初回表示は起動受付の見える応答であり、本画面が操作可能になったこととは区別する。
- 変更後の計測は replay profile で行った。live profile の変更後コールド起動時間と、本画面の操作可能時刻は未確認である。

## 判断

1. PyInstaller の EXE は `console=False` とし、Windows GUI サブシステムで実行する。標準ストリームが存在しない前提でも起動とエラー記録が成立するようにする。
2. 起動直後は既存の `icon.png` を PyInstaller bootloader splash として表示する。pywebview の Window `shown` 後に bootloader splash を閉じる。
3. pywebview は backend ready を待つ前に、インライン HTML の起動画面を持つ Window を作る。GUI 開始コールバック内で別プロセス backend の health 待機を並行実行し、ready 後に同じ Window を frontend URL へ切り替える。
4. 起動中の Window close は health 待機を cancel し、閉じた Window を更新しない。backend の早期終了、timeout、または起動コールバック例外では backend を終了し、同じ Window を起動エラー画面へ切り替える。既存の終了時 process cleanup は維持する。
5. 起動性能の報告は、少なくとも「実行開始から初回表示」「backend ready」「本画面操作可能」を分離する。スプラッシュが 3 秒以内に表示されても、本画面の 3 秒目標を達成したとは扱わない。
6. backend 初期化の大規模な遅延ロード、backend の同一プロセス化または thread 化は今回行わない。

## 検討した選択肢と棄却理由

### frontend の軽量な実アプリシェルを backend readiness から分離する

知覚上の応答だけでなく、操作可能時間も短縮できる理想案である。ただし、API 接続前の機能制御、失敗・再試行、静的配信境界を再設計する必要があり、今回の最小変更を超えるため採用しなかった。

### backend ready 前に frontend URL を直接開く

接続エラー表示や初回 API 失敗による誤った画面分岐が残り得る。ready 後だけ frontend を読み込む境界を維持できないため採用しなかった。

### pywebview のインライン起動画面だけを先に表示する

backend の直列待機による無表示は解消するため、最初に採用して実測した。しかしコールド起動で pywebview の初回表示自体に 7.976 秒を要し、3 秒以内の見える応答を満たさなかった。この結果を受け、より前段の PyInstaller bootloader splash を追加した。

### PyInstaller bootloader splash と pywebview 起動画面をつなぐ

既存アイコンと同梱済み機能だけで、Python と UI runtime の読み込み中から見える応答を出し、その後の backend 待機を同一 pywebview Window へつなげられる。replay profile の実測で初回表示が 1.44 秒となったため採用した。

### backend を同一プロセスまたは thread で起動する

spawn 費用を減らす可能性はあるが、uvicorn shutdown、event loop、グローバル状態、障害分離、process cleanup の所有境界を変える。spawn が支配的原因であるとの証拠がなく、変更費用とリスクが大きいため採用しなかった。

### backend 初期化を大規模に遅延ロードする

本画面の到達時間を短縮し得るが、初期化順序と各機能の ready 契約を広く変更する。今回は無表示時間を解消する最小の起動表示境界に限定し、別判断へ留保した。

## 適用範囲

- Windows の PyInstaller 配布用 EXE のサブシステムと bootloader splash。
- pywebview Window の初期表示、backend health 待機、本画面遷移、起動失敗表示。
- 起動中 close と backend process の終了・cleanup 境界。
- デスクトップ起動性能の指標の意味。

## 適用しない範囲

- backend の業務機能、初期化内容、サービス開始順序の再設計。
- backend の同一プロセス化または thread 化。
- frontend の軽量アプリシェル化と、backend 未接続時にも使える操作の設計。
- live/replay の Composition Root や実行プロファイルの意味変更。
- macOS/Linux の native GUI、配布形式、スプラッシュ契約。
- 本画面を 3 秒以内に操作可能にする保証。

## 期待する効果

- Windows 起動時にコマンドプロンプトが表示されない。
- Python と UI runtime の読み込み中も、利用者は早期にアプリの起動受付を確認できる。
- backend 起動待ちが GUI 初回表示を直列に遅らせず、ready 後は同じ Window で本画面へ移れる。
- 起動失敗や利用者による close で、待機 thread や backend process が不要に残りにくい。
- 見える応答と本画面の操作可能時間を混同せず、次の性能改善対象を判断できる。

## 受け入れる欠点・リスク

- bootloader splash は起動時間そのものを短縮せず、初回の見える応答を早める。backend ready と本画面到達の遅さは残る。
- 変更後の replay profile でも backend ready は 9.123 秒であり、本画面 3 秒目標は未達である。
- 変更後の `mainInteractiveSeconds` は UI Automation がセットアップ画面の要素を公開しなかったため取得できず、ログ上の画面用 API 到達を操作可能の証明とは扱わない。
- PyInstaller 6.16 の splash は公式文書上 experimental であり、将来の PyInstaller 更新で再確認が必要である。
- bootloader splash と pywebview 起動画面の二段表示に、外観や切替の差が見える可能性がある。
- `console=False` では標準出力・標準エラーが利用できないため、起動失敗の診断をファイルログと GUI 表示に依存する。

## 再検討条件

- 初回表示が代表的な Windows 端末のコールド起動で 3 秒を超える場合。
- 本画面を 3 秒以内に操作可能にすることが、努力目標ではなく必須要件になった場合。
- backend ready または本画面到達の遅さが利用継続を妨げ、初期化区間の計測から特定の処理が支配的と確認された場合。
- backend のプロセス境界を変える別の目的が生じ、起動時間だけでなく shutdown、障害分離、状態所有を合わせて再設計する場合。
- PyInstaller の splash API、pywebview の start callback・Window event 契約を更新する場合。
- bootloader splash から pywebview 起動画面への切替で、ちらつき、残留、アクセシビリティ上の問題が確認された場合。

## ユーザー発言の原文

目的、性能目標、許容する fallback を示した原文:

> アプリ起動時、コマンドプロンプトを非表示にしてください。なお、実行ファイルを実行してからアプリ画面が表示されるまでに時間がかかっています。努力目標1秒、目標3秒以内に画面が表示されるように改善してください。ただ、もし厳しいようなら、スプラッシュ画面を表示することを検討してください。

この発言はスプラッシュを必須指定したものではなく、3 秒以内の本画面表示が厳しい場合に検討できる fallback として保存した。

ADVISE 後、メインエージェントが安全条件を含めて実装へ進むと確定した原文:

> `design_steward` の助言でも、この構成は条件付き採用が妥当でした。条件は、スプラッシュ時間と操作可能時間を分けて報告すること、バックエンド早期終了・起動中のウィンドウ閉鎖・コールバック例外を安全に処理することです。これらを含めて最小実装します。

pywebview 起動画面だけの実測を受け、bootloader splash を追加すると確定した原文:

> 実 EXE の外部計測では、コールド起動でスプラッシュ表示が約8.0秒、バックエンド準備が約13.9秒、本画面操作可能が約14.5秒でした。現状の pywebview 内スプラッシュだけでは目標未達です。起動前半は Python/UI ランタイム読込なので、ここだけは PyInstaller のブートローダースプラッシュを先に出す必要があります。まず既存アイコン資産で追加依存なしの最小構成を試します。

変更後の実測と目標の扱いを確定した原文:

> 再分析の結果、計測自体は成功しており、初回表示は **1.44秒**、backend 準備完了は **9.12秒**でした。セットアップ画面は UI Automation に要素を公開しないため、本画面判定値だけ取れませんでしたが、ログ上は同時刻に画面用 API まで到達しています。目標3秒はスプラッシュ表示で達成、努力目標1秒は未達です。ここで計測方式の再試行は止め、成果物検証と一時物の撤去へ進みます。

上記メインエージェント原文の「目標3秒はスプラッシュ表示で達成」は見える応答についての報告であり、本 ADR の正規化では ADVISE の計測契約に従い、本画面操作可能 3 秒の達成とは扱わない。
