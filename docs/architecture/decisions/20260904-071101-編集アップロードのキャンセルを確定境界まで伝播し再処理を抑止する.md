# 編集アップロードのキャンセルを確定境界まで伝播し再処理を抑止する

- ID: 20260904-071101
- 状態: accepted
- 日時: 2026-09-04T07:11:01+09:00
- 判断者: 共同

## 目的・問題

編集・アップロード実行中のキャンセル要求を、UI 上の表示変更や要求受付だけで終わらせず、実際の編集処理と YouTube resumable upload まで伝播させる。同時に、キャンセルと成果物の確定が競合しても、再試行に必要な入力を失わず、確定済み成果物を不要に破棄せず、キャンセルされた実行が自分自身を再起動しない状態遷移を定める。

従来の ADR は「成功確認後だけ入力を削除する」「キャンセル時は入力を保持する」という安全側の原則を定めているが、編集成果物の commit 前後、アップロード成功確認の前後、処理中追加ファイルの再走査、および UI の停止確認という競合境界は具体化していなかった。

## 前提・制約

- 編集成果物一式が再利用可能な状態で確定した時点を、編集成果物の commit 境界とする。具体的なファイル形式や commit 実装は本 ADR では固定しない。
- commit 前の一時成果物は未完成であり、再処理の入力として扱わない。
- YouTube resumable upload では、送信済みチャンクとキャンセル観測の間に競合があり得る。外部成功を確認した後に、その一件をローカル都合で未完了へ巻き戻さない。
- 外部アップロードの完全な exactly-once は保証しない。成功確認前に外部側で成功していた場合の成否不明問題は既存 ADR の範囲外を維持する。
- キャンセル確認の粒度はアップロードのチャンク境界とし、チャンクサイズはユーザーが明示した `16 MiB` とする。
- キャンセルされた実行からの自動再開だけを禁止する。後続の独立した Switch 電源 OFF 確定またはユーザーの明示的な手動開始による新しい実行は、ADR `20260903-072808` の開始条件に従う。
- 実際の停止処理から完了通知までをバックエンドが所有し、UI はその状態を表示する。

## 判断

1. 編集済みファイルを正常に生成し、編集成果物を commit できた場合は、元録画を削除してよい。元録画を常に保持すること自体は目的にせず、再試行可能な確定済み入力を少なくとも一つ保持する。
2. 編集中・アップロード中のキャンセル要求は、実行中の編集処理およびアップロード処理へ実際に伝播させる。要求受付だけで成功応答または完了表示にしない。
3. 編集成果物 commit 前にキャンセルを確認した場合は、一時成果物だけを除去し、元録画を保持する。確定済み編集成果物がないため、元録画を次回実行の入力として残す。
4. 編集成果物 commit 後にキャンセルを確認した場合は、元録画の cleanup を完了してよい。確定済み編集済みファイルは保持し、同じ実行ではアップロードへ進まない。
5. YouTube resumable upload はチャンク間でキャンセルを確認する。チャンクサイズは `16 MiB` とする。アップロード成功確認前にキャンセルを確認した場合は編集済みファイルを保持する。成功確認後にキャンセルを観測した場合は、その一件を完了扱いとし、通常の成功確定後処理へ進める。
6. キャンセルされた実行は、終了処理や残存ファイルの検出を理由に自分自身を再開しない。特に、その実行中に検出した `added_during_run` を根拠とする再走査要求を発火しない。
7. UI はキャンセル要求の受付時点で完了表示にせず、ダイアログも即座に閉じない。バックエンドが実処理の停止と必要な cleanup を確認し、キャンセル完了状態を返した後にだけ完了として扱う。

## 検討した選択肢と棄却理由

### キャンセル要求を受け付けた時点で UI を閉じ、処理は安全な終了点まで継続する

利用者には停止済みに見える一方、編集またはアップロードが継続し得る。表示と実状態が不一致になり、処理中のファイル操作や外部副作用を利用者が誤認するため棄却した。

### キャンセル時は編集成果物の確定前後を問わず元録画を保持する

データ保全には安全だが、commit 済み編集成果物と元録画の双方が残り、次回走査で重複編集を招き得る。commit 済み成果物が再試行入力として成立するため、元録画の無条件保持は採用しない。

### キャンセル時は編集成果物の確定前後を問わず元録画を削除する

commit 前に元録画まで削除すると、再試行可能な入力が失われる。データ消失につながるため棄却した。

### アップロードは動画一件の完了時にだけキャンセルを確認する

大きな動画ではキャンセル要求から停止までの待ち時間が長くなり、実処理へ伝播するという目的を満たしにくい。resumable upload のチャンク間確認を採用した。

### より小さいチャンクで停止応答性を最大化する

停止確認は細かくなるが、リクエスト回数とプロトコル処理が増える。今回の応答性とオーバーヘッドの具体的な選択として、ユーザーが `16 MiB` を選択した。

### キャンセルを通常の失敗または成功として扱い、終了時の再走査に任せる

残存ファイルまたは `added_during_run` により、利用者が停止した直後に同じ実行系列が再開し得る。キャンセルという制御結果を独立して保持し、その実行からの再走査発火を抑止する案を採用した。

## 適用範囲

- 自動・手動の編集アップロード実行に対するキャンセル要求と停止完了通知。
- 編集処理の一時成果物、commit 済み編集成果物、元録画 cleanup の順序。
- YouTube resumable upload のチャンク間キャンセル確認と成功確認境界。
- キャンセルされた worker 実行の終了処理、`added_during_run`、再走査要求。
- キャンセル要求後から停止確認までの進捗 UI。

## 適用しない範囲

- 編集アルゴリズム、エンコーダー、動画形式の選択。
- YouTube 以外のアップロード先におけるチャンク仕様。
- 外部成功後・ローカル成功記録前のプロセス異常終了に対する完全な exactly-once。
- キャンセル後に開始条件を満たした別実行を恒久的に禁止すること。
- Switch 電源 OFF 後または手動操作という処理開始条件そのもの。
- キャンセル UI の外観、文言、レイアウト。

## 期待する効果

- キャンセル操作と実際の編集・アップロード停止が一致する。
- commit 前キャンセルでは元録画、commit 後キャンセルでは編集済みファイルが残り、再試行可能な入力を失わない。
- commit 済み編集成果物がある場合に元録画を不要に残さず、重複編集の原因を減らす。
- アップロード中も `16 MiB` チャンクの境界でキャンセルを観測できる。
- キャンセル直後に `added_during_run` が同じ処理系列を再起動する挙動を防ぐ。
- UI が停止未確認の処理を完了済みと誤表示しない。

## 受け入れる欠点・リスク

- アップロードの停止は即時ではなく、実行中の最大一チャンクの送信完了まで遅れる場合がある。実際の停止時間は回線状況に依存し、未確認である。
- `16 MiB` は今回の明示選択であり、回線品質や API 制約の変化に対する最適値であることまでは確認していない。
- 編集成果物 commit とキャンセル観測が競合するため、どちらの境界を越えたかを実装上で一意に判定する必要がある。
- 外部成功確認とキャンセル観測が競合した場合、成功確認済みの一件は完了扱いとなり、キャンセル要求でその外部副作用を取り消すことはできない。
- キャンセルされた実行からの再走査を抑止するため、その実行中に追加されたファイルは、次の独立した正規開始契機まで滞留する場合がある。
- 一時成果物の除去に失敗した場合の回復方法は未確認であり、元録画を保持しても不要な一時ファイルが残る可能性がある。

## 再検討条件

- 実測で `16 MiB` ごとの停止遅延が許容できない、またはリクエスト負荷が過大と判明した場合。
- YouTube API の resumable upload 契約または推奨チャンク条件が変わった場合。
- 外部側の取消、冪等性キー、または確実なアップロード照合手段を利用できるようになった場合。
- 編集成果物 commit を原子的かつ一意に判定できず、キャンセル競合で入力消失または重複編集が発生する場合。
- キャンセル後も処理中追加ファイルを自動処理すべきというユーザー要件へ変更された場合。
- 一時成果物 cleanup の失敗が運用上無視できない頻度で発生した場合。

## 置換・追補関係

本 ADR は、ADR `20260813-200649` の判断 6 にある「成功確定後だけ入力を削除する」「失敗・キャンセル・成否不明時は入力を残す」を、編集成果物 commit 前後とアップロード成功確認前後の境界へ具体化して追補する。同 ADR の判断 4・5 にある完了時再走査と lost-wakeup 防止については、キャンセルされた実行から `added_during_run` を根拠とする再走査を発火しない例外を追加する。常駐サービス、単一 worker、snapshot、将来の独立した開始要求を失わない目的は維持する。

本 ADR は、ADR `20260903-072808` の判断 4 にある「キャンセル時は入力を保持する」を部分的に具体化する。commit 前は元録画を保持し、commit 後は元録画を cleanup して編集済みファイルを保持するため、「再試行可能な入力を保持する」という目的は維持する。また、同 ADR が定める後続の Switch 電源 OFF 確定または手動開始からの新しい実行は維持し、キャンセルされた同一実行からの自動再開だけを禁止する。
