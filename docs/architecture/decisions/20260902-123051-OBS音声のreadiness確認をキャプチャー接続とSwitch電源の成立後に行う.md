# OBS音声のreadiness確認をキャプチャー接続とSwitch電源の成立後に行う

- ID: 20260902-123051
- 状態: accepted
- 日時: 2026-09-02T12:30:51+09:00
- 判断者: 共同

## 目的・問題

Switch 電源 OFF やキャプチャーボード未接続の状態では、OBS 音声が観測できないことは故障を意味しない。OBS 音声を先に検査すると、復旧の再起動を安全ゲートで抑止できても、`silent` 警告だけが画面へ残り、ユーザーへ誤った異常を示す。

さらに、Switch 電源状態はキャプチャー映像から判定するため、キャプチャーボード未接続時には Switch 電源状態を先に確認できない。readiness の物理的な依存関係に合わせて検査順序を定め、観測不能を音声故障として扱わないようにする。

## 前提・制約

- Switch 電源状態はキャプチャー映像から判定する。キャプチャーボード未接続時に Switch 電源状態を確定する別経路はない。
- Switch 電源状態の所有者は既存の `AutoRecordingUseCase` のままとし、新しい状態所有者や常駐音声監視を追加しない。
- 非 `ARMED`、キャプチャーボード未接続、または接続・電源状態の確認失敗は、音声故障ではなく音声を評価できない readiness 未成立として扱う。
- `20260901-213726` が定めた、2 回連続 `silent`、アプリ所有 OBS、非録画中、一呼び出し一回の再起動、再検査、外部 OBS 非操作、replay `skipped`、fail-open は維持する。
- 音声検査または通知に失敗しても、Switch 電源監視と録画開始を停止しない。
- 実機での Switch ON 後の音声再検査と復旧は未確認である。

## 判断

1. live の OBS 音声 readiness は、必ず「キャプチャーボード接続 → Switch 電源状態 → OBS 音声」の順に確認する。
2. キャプチャーボードが未接続、または接続確認に失敗した場合は、Switch 電源状態を参照せず、OBS 音声も検査しない。`healthy=True`、`status=skipped` を返す。
3. キャプチャーボード接続済みの場合だけ Switch 電源状態を確認する。非 `ARMED` または電源状態確認失敗では OBS 音声を検査せず、`healthy=True`、`status=skipped` を返す。
4. `skipped/healthy` の結果も既存の音声ヘルス通知経路へ発行し、以前の `silent` 警告を画面から消す。
5. `ARMED` へ遷移した時点で共有音声ヘルス経路を呼び、readiness 成立後の OBS 音声を実検査する。必要な場合だけ `20260901-213726` の安全条件で復旧する。
6. `ARMED` 遷移後に発生する故障も扱うため、録画開始直前の同じ共有経路による再検査を維持する。
7. 電源状態遷移時の検査・通知は best-effort の fail-open とし、失敗をログへ残して Switch 電源監視を継続する。

## 検討した選択肢と棄却理由

### Switch電源状態 → キャプチャー接続 → OBS音声

前ターンで一度採用した順序。しかし Switch 電源状態自体をキャプチャー映像から判定するため、キャプチャーボード未接続時には最初の確認を実行できない。ユーザーの明示的な指摘を受け、依存関係と逆であるとして撤回した。

### キャプチャー接続 → Switch電源状態 → OBS音声

前段の観測可能性が成立した場合だけ後段を確認できる。未接続時は Switch 状態の参照と OBS 音声検査の両方を避けられ、ユーザーが求める誤警告防止を満たすため採用した。

### OBS音声を先に検査し、readiness未成立なら復旧だけ抑止する

復旧の誤作動は防げても、`silent` 警告が画面へ出る。ユーザーが明示した「Switch の電源が入っていない時に音声入力のチェックをしない」を満たさず、観測不能を故障として扱う根本原因が残るため棄却した。

### 録画開始直前だけ検査する

Switch 電源 ON 時点で改めて音声入力を確認するというユーザー要件を満たさず、録画前に警告・復旧する時間も失うため棄却した。

### frontendからARMEDを見て再準備する

バックエンドの電源状態遷移に伴う効果がブラウザの存在やポーリングへ依存し、既存の状態所有権と責務境界を崩すため棄却した。

### 独立したRecordingReadiness状態機械を追加する

音声・映像・デバイスを統合する将来案にはなり得るが、現時点では既存状態と重複し、今回の依存順序と検査ゲートを解く範囲を超えるため採用しない。

## 適用範囲

- live 実行プロファイルの録画準備、Switch 電源状態遷移、録画開始直前に行う OBS 音声ヘルス確認。
- キャプチャー接続、Switch `ARMED`、OBS 音声の readiness ゲートと確認順序。
- readiness 未成立時の `skipped/healthy` 通知による既存警告のクリア。
- `ARMED` 遷移時と録画開始直前の共有音声ヘルス経路。

## 適用しない範囲

- キャプチャー映像以外から Switch 電源状態を判定する新しい仕組み。
- Switch 電源状態やキャプチャー接続状態の判定条件そのもの。
- OBS 音声の常駐監視、新しい readiness 状態機械、frontend 起点の再準備。
- `20260901-213726` が定めた復旧対象、OBS プロセス所有権、録画中ガード、再起動回数、replay 境界の変更。
- 音声不良を理由に録画開始を拒否する仕様変更。

## 期待する効果

- キャプチャーボード未接続時に、判定不能な Switch 電源状態を参照せず、OBS 音声も検査しない。
- Switch 電源 OFF や readiness 未成立を OBS 音声故障として警告しない。
- Switch 電源 ON が `ARMED` として確定した時点で音声を改めて確認し、録画前に既存の安全条件で復旧できる。
- readiness の確認順序が観測データの依存関係と一致し、入口ごとの判定ずれを避ける。

## 受け入れる欠点・リスク

- キャプチャー接続済みでも Switch 電源状態が `ARMED` と確定するまでは、OBS 音声故障が存在しても検出しない。
- `ARMED` 遷移時と録画開始直前が近い場合、音声検査が近接して実行され得る。
- fail-open のため、検査自体に失敗した場合は音声なしの録画が作成される可能性を引き続き受け入れる。
- `skipped/healthy` は「音声が正常」という実測ではなく、「現在は評価対象外で警告しない」という意味を持つ。利用側がこの意味を混同しない必要がある。

## 再検討条件

- キャプチャー映像以外から信頼できる Switch 電源状態を取得できるようになり、依存順序の前提が変わった場合。
- `ARMED` 確定前にも OBS 音声故障を検出する必要が生じた場合。
- `ARMED` 遷移時と録画開始直前の重複検査が許容できない遅延または負荷を生じた場合。
- 音声・映像・デバイスを横断する恒常的な readiness 管理が必要になり、独立状態機械の費用に見合う場合。
- 実機確認で、Switch ON 後の検査が実行されない、古い警告が消えない、または録画開始へ影響することが判明した場合。

## ユーザー発言の原文

当初の復旧目的と誤作動防止条件:

> obsが音声出力できていないとき、obsを再起動する等の対策を講じるようにしたい。基本的にはobs再起動したら音声出力される。再起動以外にも解決法があれば、それでもいいです。そもそもキャプチャボードが接続されていないとか、スイッチを起動してないとか、音声出力されない状況でも誤作動しないように気を付けてください。

Switch 電源 OFF 時は検査・警告せず、ON 時に再検査する要求:

> task deployした後にさっきアプリを起動しました。
> 今はスイッチの電源が入っていない状態ですが、obs再起動がされたかをログから確認してください。
>
> また、スイッチの電源が入っていない時に音声入力があるかのチェックをしない(音声入力されていないエラーを画面表示しない)ようにしてください。
> スイッチの電源が入った時に改めて音声入力のチェックをしてください。

今回ユーザーが選択した先行回答の原文:

> 電源状態 → キャプチャー接続 → OBS音声の順に確認

その順序に対するユーザーの訂正原文:

> 電源状態ってスイッチのこと？だとしたら、キャプチャボード接続してないときはどうやって確認するの？先にキャプチャボードの接続確認した方がいいんじゃない？

訂正を受けてメインエージェントが確定した原文:

> はい、「電源状態」はSwitchの電源状態です。ご指摘どおり、これはキャプチャー映像から判定するため、キャプチャーボード未接続時には先に確定できません。順序は「キャプチャーボード接続 → Switch電源状態 → OBS音声」が正しいので修正します。

前ターンに確定し、本 ADR でも維持する原文:

> 電源状態が`UNKNOWN / WAITING_FOR_POWER_ON / CAPTURE_DISCONNECTED / STOPPED`なら、OBS音量イベントを購読せず`skipped + healthy`として画面警告を消します。`ARMED`へ遷移した瞬間だけ実検査を行い、その後の録画開始直前チェックも安全網として維持する想定です。

> 非`ARMED`時はOBSへ問い合わせず`skipped`通知だけで古い警告を消し、`ARMED`時は実検査します。録画開始直前の再検査は維持します。
