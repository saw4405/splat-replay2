# Windows共有違反はcommit後cleanupで有界再試行しサムネイル一時名を分離する

- ID: 20260920-153305
- 状態: accepted
- 日時: 2026-09-20T15:33:05+09:00
- 判断者: ユーザー

## 目的・問題

2026-09-18 のデスクトップ版では、編集済み動画の commit 後に元録画を削除する際、Windows の `WinError 32` によって編集・アップロード実行が失敗した。親セッションの調査では、進捗ダイアログのフレーム抽出が FFmpeg で同じ元録画を開いていた可能性が最も高いが、ロックした PID 自体はログに記録されておらず未確認である。

別の時刻には、複数のサムネイル生成経路が共有する固定の `*.thumb.png` でも `WinError 32` が発生していた。プレビューやサムネイル生成という付随処理の一時的なファイル競合で、確定済み編集成果物を持つ編集・アップロード全体を不要に失敗させないことを目的とする。同時に、永続的なロックや別種の削除失敗を成功扱いにせず、元録画の重複編集・重複アップロードを防ぐ既存の commit/cleanup 境界を維持する。

## 前提・制約

- 編集成果物 commit 後の元録画 cleanup が完了しない場合はアップロードへ進まず、commit 済み成果物と source manifest を保持して次回 cleanup から再開する既存挙動を維持する。
- 一般的な編集失敗は成功扱いにせず、アップロードと成功通知を止める ADR `20260913-013343` を維持する。
- 進捗プレビューは編集処理の成否から分離し、共通ロックや元動画リースで編集と直列化しない既存設計を維持する。
- 現行のフレーム抽出タイムアウトは 8 秒である。再試行上限 10 秒はこれを覆いつつ、動画プレイヤー等による永続ロックを無期限に待たない具体値としてユーザーが承認した。
- ロック主体が FFmpeg であることは未確認である。`WinError 32` が一時的に解消する場合だけを修復対象とし、主体の推測を実装条件にしない。
- frontend、API 契約、一般的な repository の削除契約は変更しない。

## 判断

1. `AutoEditor` の編集成果物 commit 後に元録画を削除する三つの経路を、一つの非同期 helper に集約する。対象は、通常編集直後の cleanup、既存の確定済み編集動画を検出した場合の cleanup 再開、source manifest からの cleanup 回復である。
2. helper は `PermissionError` のうち Windows の `winerror == 32` だけを、0.5 秒間隔、最大 10 秒で有界再試行する。待機は非同期に行い、repository 内でイベントループを同期的に停止させない。
3. 10 秒以内に削除できた場合は、既存の commit/cleanup 境界を満たしたものとして後続処理を継続する。
4. 10 秒を使い切った `WinError 32`、`WinError 5` を含む他のエラー、または repository が削除失敗を返した場合は `EditedCommitCleanupError` として扱う。既存どおりアップロードと成功通知を止め、commit 済み成果物と source manifest による次回回復を維持する。
5. `ThumbnailGenerator` が生成する一時サムネイルは、固定の `*.thumb.png` を共有せず、Python 標準ライブラリ `tempfile` を用いて呼び出し単位の一意な一時パスを割り当てる。各呼び出しは自分が生成した一時ファイルだけを既存の cleanup 経路で削除する。
6. frontend からの fetch 中断、プレビューと編集の共有ロック、全 `OSError` の一律再試行、cleanup 失敗を無視したアップロード継続は導入しない。

## 検討した選択肢と棄却理由

### commit後cleanupでWinError 32だけを有界再試行し、一時サムネイル名を分離する

採用した。実際に観測された一時的な共有違反だけを最小範囲で吸収し、永続ロックや別原因では既存の失敗・回復境界へ戻せる。サムネイル生成は共有調停を増やさず、競合する一時パス自体をなくせる。

### プレビューと編集を共通ロックまたは元動画リースで直列化する

進捗プレビューのために編集処理を待たせず、画像 API の失敗を編集ジョブへ反映しない既存設計と衝突する。画面状態、ジョブ識別、キャンセル、リース解放等の新しい責務も増えるため、今回の局所的な共有違反対策としては採用しない。

### cleanup失敗を無視してアップロードを継続する

編集済み成果物がアップロード後に削除される一方、元録画が残って source manifest による回復根拠を失うと、後続実行で重複編集・重複アップロードを招き得る。既存のデータ保全と cleanup 境界を破るため採用しない。

### frontendのfetch中断だけで対応する

開始済みの backend FFmpeg プロセスが終了し、Windows のファイルハンドルが解放されたことを保証できない。cleanup の正しさを frontend の通信中断へ依存させるため採用しない。

### repository内で同期的に待機する

汎用 repository の責務を特定 UI 競合へ広げ、イベントループをブロックし得る。commit 後 cleanup を所有する `AutoEditor` の非同期境界で扱う案を採用した。

### 全OSErrorを再試行する

権限不足、パス不整合、ストレージ障害等の非一時的な原因まで遅延させ、異常を隠す。観測された Windows 共有違反だけへ限定するため採用しない。

### 固定サムネイル名を共有したまま生成処理をロックする

別インスタンス・別経路をまたぐロック所有権が必要になり、一時ファイル名を呼び出しごとに分離するより複雑である。競合資源を共有しない案を採用した。

## 適用範囲

- `AutoEditor` の commit 後に行う元録画 cleanup の三経路。
- Windows `WinError 32` の一時的な共有違反に対する 0.5 秒間隔・最大 10 秒の非同期再試行。
- `ThumbnailGenerator` の呼び出し単位の一意な一時サムネイルパスと、その所有呼び出しによる cleanup。
- これらの競合が解消した場合に、既存の編集・アップロード実行を継続すること。

## 適用しない範囲

- frontend の画像要求、fetch 中断、進捗表示、API schema の変更。
- `FramePreviewPort`、FFmpeg の共有モード、共通ロック、元動画リースの追加。
- 手動削除を含む repository 全般の削除再試行。
- `WinError 32` 以外の権限・I/O エラーの再試行。
- cleanup が完了していない状態でのアップロード継続。
- 自動再試行の開始条件、起動時処理、キャンセル前後の commit 境界、外部アップロードの exactly-once 保証の変更。
- 一時ファイルの一般的な名前付け規約への拡張。

## 期待する効果

- 進捗プレビューが一時的に元録画を開いていても、ハンドル解放後に cleanup を完了し、不要な編集・アップロード失敗を減らせる。
- 永続ロックや別種の削除失敗ではアップロードを止め、commit 済み成果物と manifest による次回回復を維持できる。
- 同じ録画グループに対する並行サムネイル生成が互いの一時ファイルを上書き・削除せず、`*.thumb.png` の共有競合を解消できる。
- frontend、API、汎用 repository の契約を増やさず、変更を競合の根本箇所へ限定できる。

## 受け入れる欠点・リスク

- `WinError 32` が続く場合、cleanup と後続処理は最大 10 秒遅延する。
- 0.5 秒間隔と 10 秒上限は、現行の 8 秒フレーム抽出タイムアウトを前提にした具体値である。抽出タイムアウトや利用形態が変わると再調整が必要になり得る。
- 10 秒を超える一時ロックでも、その実行は失敗し、次回回復へ持ち越される。
- `WinError 32` 以外の一時的な OS エラーが将来確認されても、自動的には再試行されない。
- プロセス強制終了時には、呼び出し単位の一時サムネイルが残る可能性がある。今回、一般的な孤児一時ファイル回収機構は追加しない。
- ロック主体が FFmpeg であること自体は本判断によって証明されない。

## 再検討条件

- 正常なプレビュー処理でも 10 秒を超える `WinError 32` が継続して観測された場合。
- フレーム抽出タイムアウトを 10 秒以上へ変更する場合。
- 有界再試行による待ち時間が利用者体験または処理スループット上の問題になる場合。
- cleanup とプレビューの競合が複数種類・複数箇所へ広がり、個別の一時名分離と限定再試行では整合性を保証できなくなった場合。
- frontend 中断で backend FFmpeg の終了まで保証できる契約を導入する場合。
- 呼び出し単位の一時ファイル残留が運用上の問題として確認された場合。

## 関連する設計指針

登録済みの設計指針はない。本判断は個別の Windows ファイル競合と既存 commit/cleanup 境界を具体化するものであり、一般則への昇格は行わない。

## 置換・追補関係

- ADR `20260913-013343` の「編集失敗はアップロードと成功通知を止める」判断を変更しない。commit 後 cleanup の `WinError 32` は、0.5 秒間隔・最大 10 秒の再試行を使い切るまでは一時競合として扱い、使い切った時点または他エラーで `EditedCommitCleanupError` とする具体化を追補する。
- ADR `20260904-071101` の commit 前後、キャンセル、入力保全の境界を変更しない。commit 後 cleanup を完了してから後続へ進む既存判断を維持する。
- ADR `20260903-072808` の開始条件、自動再試行方針、失敗時の入力保持を変更しない。
- `docs/superpowers/specs/2026-07-19-progress-dialog-prioritized-image-loading-design.md` の、プレビューを編集成否から分離し、共通ロック・元動画リースを設けない判断を維持する。同文書の「画像の待機を理由に編集処理を待機させない」「元動画削除が先に成功し 404 へ収束する」という記述に対し、Windows で既に開かれたハンドルが削除を一時的に阻む場合だけ、commit 後 cleanup が最大 10 秒の有界再試行を行う例外を追補する。

### 外部一次情報

>
> - 最初の削除が `WinError 32`、次が成功する回帰テストを1件追加
> - 永続的なcleanup失敗でアップロードを止める既存テストを維持
> - 並行サムネイル生成が異なる一時パスを使うテストを追加

> - frontend/API契約は変えないためcomponent・contractテストは省略
> - 最終的にはWindows配布版で、進捗ダイアログを開いたまま編集・元録画削除・アップロード完了まで確認が必要
