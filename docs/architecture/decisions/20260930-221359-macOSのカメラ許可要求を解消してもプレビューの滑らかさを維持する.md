# macOS のカメラ許可要求を解消してもプレビューの滑らかさを維持する

- ID: 20260930-221359
- 状態: accepted
- 日時: 2026-09-30T22:13:59+09:00
- 判断者: ユーザー

## 目的・問題

macOS アプリを起動するたびに WebView のカメラ許可要求が表示される問題を解消する際、プレビューの滑らかさを維持するかを決めます。既存の backend JPEG API を使う案は許可要求の原因となる WebView のカメラ利用を外せますが、会話で示された見込みではプレビューが約 1～2 FPS になります。

ユーザーは、毎起動の許可要求と OBS が閉じる事象を同じ報告で挙げています。この ADR が判断するのは、カメラ許可問題を解消する際のプレビュー品質です。OBS の終了原因・対策は判断しません。

## 前提・制約

- ユーザーの macOS 対応範囲は、先行 ADR `20260929-080336` で Apple Silicon 向け全機能同等と記録されています。
- 親セッションの ADVISE 報告では、配布 WebView における再要求の直接原因、現在のプレビューの実測 FPS・遅延、許容可能な具体的品質は未確認です。
- 同報告によると、既存 JPEG 経路は GPU で最大約 2 FPS、CPU で最大約 0.83 FPS の周期で取得し、処理中は次の取得を省略します。これはコードの実測値や本 ADR による独立検証ではありません。ユーザーへの質問では約 1～2 FPS と要約されています。
- `docs/architecture/principles/README.md` に現在有効な設計指針はありません。

## 判断

1. カメラ許可要求を解消する際も、現在のプレビューの滑らかさを維持します。
2. その目的で既存の JPEG API に切り替え、約 1～2 FPS のプレビューにする案は採用しません。
3. メインエージェントは、毎回の許可要求が出る原因を WebView 側で調べると回答しています。具体的な根本原因や修正方式は、この回答およびユーザーの選択では確定していません。

## 検討した選択肢と棄却理由

### 配布 macOS WebView を既存 JPEG API に切り替える

許可要求を生む WebView のカメラ利用を外せる最小案として ADVISE で提示されました。既存の画像 API は取得周期により約 0.83～2 FPS が上限となり得て、JPEG の追加圧縮や backend の映像受信が止まったときに更新されない点も指摘されています。ユーザーは「滑らかさを維持する」を選んだため、この案を採用しません。

### WebView のカメラ利用を維持して許可要求の原因を調べる

現在のプレビュー品質を保ちやすい案です。ADVISE では、配布 WebView の origin、許可状態の保存、メディア許可 delegate を調査対象として挙げました。直接原因と pywebview/Cocoa 統合の変更量は未確認です。メインエージェントは WebView 側の原因を調査すると回答しましたが、具体的な実装修正までは選ばれていません。

ADVISE は、必要な鮮度・更新頻度を満たす backend 配信や既存 FrameHub の再利用も上位候補として挙げています。必要 FPS が未定のため方式は確定せず、今回の判断にも含めません。

## 適用範囲

- macOS 配布アプリの WebView で毎起動表示されるカメラ許可要求への対応方針。
- 対応に伴うプレビュー表示品質の優先順位。

## 適用しない範囲

- OBS がアプリ起動時に閉じる事象の原因・対策。
- 自動判定用の映像入力方式。先行 ADR `20260929-080336` の DistroAV / NDI 判断を変更しません。
- 許可する origin・frame・メディア種別、許可状態の保存方法、WebView API や backend 配信の具体的実装。
- 数値で定める最低 FPS、遅延、鮮度の受け入れ基準。今回、数値基準は決めていません。

## 期待する効果

- カメラ許可要求への対応で、ユーザーが維持を選んだプレビューの滑らかさを低下させない方針が明確になります。
- WebView 側の原因調査を続けられます。許可要求自体が解消したことは、この ADR では保証しません。

## 受け入れる欠点・リスク

- WebView 側の原因と修正方法は未確認です。調査・修正が完了するまで許可要求が毎回表示される可能性があります。
- 原因が WebView の origin、許可状態、ネイティブ delegate のいずれにあるかは未確認であり、調査後の変更量も未確認です。
- 約 1～2 FPS の案を選ばない判断は、代替の修正が成立することを保証しません。

## 再検討条件

- WebView 側の調査で毎回の許可要求を解消できる方法が見つからない場合。
- 解決案が現在の滑らかさを保てず、JPEG API を含む品質低下案の採用が必要になった場合。

この場合は、実測した FPS・遅延と代替案の影響を示してユーザーに再確認します。今回、許容可能な最低 FPS は定めていません。

## 関連する設計指針

現在有効な設計指針はありません。今回の選択は個別のプレビュー品質判断であり、一般化した設計指針は追加しません。

## ユーザー発言の原文

### 問題報告（親トランスクリプト ordinal 17459）

> アプリ起動するたびに`Allow “127.0.0.1” to use your camera?`が表示されるし、OBSを閉じてしまう

### 質問と選択肢（親トランスクリプト ordinal 17778）

メインエージェントの質問:

> 毎起動のカメラ許可をなくす方法を選びます。既存の画像APIへ切り替えるとプレビューは約1～2 FPSになります。プレビューの滑らかさを維持しますか？
> - 滑らかさを維持する（推奨）
> - 1～2 FPSの状態確認でよい

ユーザーの回答（親トランスクリプト ordinal 17800）:

> 滑らかさを維持する（推奨）

### 選択後のメインエージェントの方針（親トランスクリプト ordinal 17807）

> プレビューは滑らかさを維持する方針で進めます。約1～2 FPS の画像APIへの切替は採用しません。カメラ許可が毎回出る原因を WebView 側で調べます。
