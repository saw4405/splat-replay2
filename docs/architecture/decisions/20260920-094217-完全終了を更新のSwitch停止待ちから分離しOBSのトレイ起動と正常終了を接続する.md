# 完全終了を更新のSwitch停止待ちから分離しOBSのトレイ起動と正常終了を接続する

- ID: 20260920-094217
- 状態: accepted
- 日時: 2026-09-20T09:42:17+09:00
- 判断者: メインエージェント（OBS のトレイ起動要求はユーザー）

## 目的・問題

通知領域の「完全終了」を選んでも終了しない問題を解消し、OBS も通知領域へ起動する。ユーザーが要求した終了について、録画などの実行中処理を保護しながら、Switch の電源状態を理由に待ち続けないようにする。

親セッションの調査報告では、監視状態は「キャプチャーデバイス切断」であり、完全終了にも更新予約と同じ Switch 停止待ちを課していた。また、OBS の非表示ウィンドウを検出しないため、トレイ起動を失敗扱いする問題が報告された。本 RECORD が実機で再観測した事実ではない。

## 前提・制約

- 既存仕様の「通知領域の完全終了は処理を破棄せず終了する」と「更新予約は Switch OFF と後処理完了を待つ」の違いを回復する修正である。
- 更新予約後も録画を優先する既存判断、OBS の起動由来と終了所有権を維持する。
- 取得できた親原文と今回の明示的な確定判断を記録する。過去の助言本文は暗号化され取得不能であり、過去の検討経緯を完全取得したとは扱わない。
- 技術詳細をユーザーが一つずつ選択したとは扱わない。今回メインエージェントが確定した実装判断として記録する。

## 判断

1. 通知領域の `quit` と更新予約を区別し、`quit` では Switch 電源状態の待機条件を外す。更新予約の Switch OFF 待ちと録画優先は維持する。
2. 完全終了でも、録画 `STOPPED`、後処理 idle、未消化の PowerOff イベントの消化、実行中 API の完了を必要条件として保持する。電源待ちを外すことを、処理破棄や強制終了の許可にしない。
3. 稼働中の判定は frame 境界に置く。初期化失敗後は teardown 完了後の再試行入口で判定する。停止済みの監視経路では、自動録画ユースケースの status が `stopped` のときだけ判定する。`idle` を停止済みとみなさず、`start_background` との競合を避ける。
4. SplatReplay が OBS を起動する際は `--minimize-to-tray` を付ける。非表示の OBS 本体ウィンドウも検出し、起動確認および `WM_CLOSE` による既存の正常終了経路へ接続する。
5. アプリ起動前から存在した OBS を終了時に残す所有権方針を維持する。非表示であることを理由に別プロセスを終了対象へ広げない。

## 検討した選択肢と棄却理由

取得できた原文・今回の確定判断から確認できる比較だけを示す。暗号化された ADVISE の理想案・比較・外部調査の詳細は未確認であり、補作しない。

| 選択肢 | 採否と理由 |
| --- | --- |
| 完全終了と更新予約で Switch 停止待ちを共用する | 不採用。切断状態などでは明示した完全終了が進まず、既存仕様の操作の違いを失う。 |
| 完全終了だけ電源待ちを外し、処理完了条件を共有する | 採用。既存の処理保護を維持して終了不能の原因を解消する。 |
| 停止済み判定を `idle` にも広げる | 不採用。`start_background` と競合させないため、status `stopped` に限定する。 |
| OBS に引数だけ追加し、可視ウィンドウだけを検出する | 不採用。トレイ起動を失敗扱いする既存の問題を残す。 |
| OBS のトレイ起動と非表示本体の検出を合わせて扱う | 採用。起動確認と正常終了を同じ対象へ接続できる。 |

## 適用範囲

Windows 常駐デスクトップ版の明示的な完全終了、更新予約との待機条件の分離、SplatReplay による OBS 起動と本体ウィンドウの検出・正常終了。

## 適用しない範囲

更新の録画優先順位、強制終了方針、OBS の所有権、音声復旧条件、Android の接続方式、永続データ、一般的な並行制御基盤の変更。配布や実機確認の成功を本 ADR で認定しない。

## 期待する効果

キャプチャ切断や Switch 電源状態に妨げられず、実行中処理の完了後に完全終了できる。OBS のトレイ起動を起動失敗と誤認せず、非表示でも従来の正常終了経路を利用できる。

## 受け入れる欠点・リスク

- 録画・後処理・API などが完了しない間は完全終了も待つ。無条件の即時終了は保証しない。
- frame 境界、初期化失敗後、停止済みの判定入口を取り違えると、処理開始や teardown と競合する。`idle` と `stopped` の区別を保つ必要がある。
- 非表示ウィンドウも扱うため、本体と対象プロセスの識別を保つ必要がある。
- 対象テストの成功報告は親セッションにあるが、今回の変更を配布した実環境での完全終了、OBS 終了、次回起動の通し確認は記録時点で未確認である。

## 再検討条件

処理完了後も終了が進まない、初期化・開始・停止の競合が発生する、OBS のバージョン変更で起動引数や本体識別が成立しない、または即時終了や待機期限の新しい要件が提示された場合。これらは再検討の契機であり、新しい強制終了の承認ではない。

## ユーザー発言の原文

ユーザー要求全文（親トランスクリプト 1674 行）:

> タスクトレイのアイコンから完全終了を選択したのに終了されなかった。
>
> OBSもシステムトレイに起動するようにしたい。
> "C:\Program Files\obs-studio\bin\64bit\obs64.exe" --minimize-to-tray

原因報告（メインエージェント、1737 行）:

> 現在の監視状態は「キャプチャーデバイス切断」でした。実装では「完全終了」にも更新予約と同じSwitch停止待ちの条件を課しており、この状態では終了に進めません。また、OBSは非表示のウィンドウを検出しないため、トレイ起動を失敗扱いする問題も確認しました。

修正方針（メインエージェント、1773 行）:

> 「完全終了」はSwitchの電源状態ではなく、録画・編集・アップロードなどの処理完了を待って終了するよう修正しています。更新予約の録画優先は維持します。OBSはトレイ起動に加え、非表示の本体ウィンドウでも起動確認・正常終了できるようにします。

今回の RECORD 呼び出しから確定判断・記録範囲の原文（メインエージェント）:

> メイン確定判断: quitは更新予約と分離しSwitch電源状態の待機を外す。ただし録画STOPPED・後処理idle・PowerOff消化・実行中API完了は保持。進行中はframe境界、初期化失敗後はteardown完了後の再試行入口、停止済みはUC status stopped時だけ終了判定。更新予約の録画優先は維持する。OBSは指定引数で起動、非表示の本体ウィンドウも検出し起動成功・WM_CLOSE正常終了へ接続。既存所有権は保持。これはdocs/superpowers/specs/2026-09-13-resident-desktop-android-design.md の完全終了と更新の違いを回復する修正。既存ADRは書き換えず追補、他コード/docs/resident-desktop.mdは触らない。
