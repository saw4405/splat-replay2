# Switch電源ON待機時の実キャプチャを1秒間隔の単一ゲートにする

- ID: 20260814-095458
- 状態: accepted
- 日時: 2026-08-14T09:54:58+09:00
- 判断者: 共同

## 目的・問題

Switch 電源 ON 待機中のバックエンド CPU 使用率が実測で約 40% となった。ON 判定自体の頻度を下げても、実キャプチャ、色変換、キュー投入が全速で継続していたため、待機状態として不要な処理負荷が残っていた。

録画開始を取り逃がさない範囲で待機中の実キャプチャを減らし、ON 確定後は従来の無制限な取得頻度へ即時復帰させる。既存 ADR が定めた、ON 候補 3 フレームによる確定、確定フレームの後段リプレイ、連続自動処理、未処理ファイル再走査の保証は維持する。

## 前提・制約

- ユーザーの実利用では、Switch の電源を ON にしてからバトル開始、すなわち録画開始まで約 10 秒かかる。
- ON 確定には、取得された ON 候補 3 フレームを使う。
- `ARMED` 中のバトル検出と録画に必要な取得頻度は低下させない。
- `UNKNOWN`、`WAITING_FOR_POWER_ON`、`CAPTURE_DISCONNECTED` は、バトル検出・録画を行わず、電源 ON またはキャプチャ再接続を待つ状態である。
- 時間ゲートを複数箇所へ置くと、時計の位相差で取得済みフレームを判定側が飛ばし、復帰遅延が増える可能性がある。
- OS スケジューリング、キャプチャ API の待ち時間、フレーム供給遅延は、理論上の約 2～3 秒に追加され得る。

## 判断

1. `UNKNOWN` と `WAITING_FOR_POWER_ON` の実キャプチャ開始間隔を 1.0 秒とする。`CAPTURE_DISCONNECTED` から再接続を確認する実キャプチャ開始間隔も 1.0 秒とする。
2. `ARMED` の実キャプチャ開始間隔は 0.0 秒、すなわち追加の時間制限なしとし、従来の取得頻度を維持する。
3. 時間ゲートは producer の一箇所だけに置く。非 `ARMED` 状態では、producer が 1 秒ごとに取得した全フレームを状態判定へ渡し、判定側に別の 1 秒ゲートを重ねない。
4. application の UseCase が電源状態から取得間隔ポリシーを決める。`FrameCaptureProducer` は任意の非負間隔を動的に受け取り、実キャプチャ開始を thread-safe に制御する汎用機構だけを持つ。NDI adapter は Switch 電源状態を持たない。
5. ON 候補 3 フレームを連続取得した場合、取得開始を `t=0, 1, 2秒` とみなせるため、最初の候補取得から通常約 2 秒で `ARMED` へ復帰する。Switch ON と最初の取得の位相差を最大 1 秒とすると、Switch ON からは通常最長約 3 秒で復帰する。ただし、OS・キャプチャ・供給遅延はこの時間へ追加され得る。
6. ON 確定に使った 3 フレームを古い順に後段へ渡す既存処理順を維持し、ON 判定中に現れたバトル開始兆候を捨てない。
7. `recorded/`・`edited/` の再走査、snapshot、generation、成功確定後の入力削除等、既存 ADR の未処理ファイル回収保証は変更しない。

## 検討した選択肢と棄却理由

### ON待機中を0.5秒間隔、約2fpsにする

CPU 高負荷の原因診断後にメインエージェントが最初に提示した案。ON 候補 3 回なら約 1.5 秒で復帰できるが、ユーザーは Switch ON からバトル開始まで約 10 秒あるため 1 秒ごとで十分と判断した。必要以上の取得回数を残すため棄却した。

### producerと判定側の両方に1秒ゲートを置く

二つの時計の位相差により、producer が 1 秒間隔で取得した 2 枚目を判定側が早すぎるとみなして飛ばす可能性がある。その場合、ON 候補 3 回の確定が約 4 秒以上へ延び得る。単一ゲートの方が取得回数と判定回数の対応が明確なため棄却した。

### NDI adapterが電源状態と間隔を所有する

NDI 固有処理へアプリケーションの Switch 状態を持ち込み、adapter の再利用性と責務分離を損なう。状態から方針を決める責務は UseCase、間隔を実行する汎用責務は producer とするため棄却した。

### ARMED中も取得を1秒間隔にする

バトル開始検出や録画に必要な短い画面変化を取り逃がす。今回の目的は待機中の負荷削減であり、録画中・バトル監視中の精度を変えないため棄却した。

### 判定だけを1秒間隔にして実キャプチャは全速のままにする

高負荷の主体である実キャプチャ、RGBA→BGR 変換、キュー投入が継続し、観測された CPU 問題を解決しないため棄却した。

## 適用範囲

- `UNKNOWN`、`WAITING_FOR_POWER_ON` における実キャプチャ開始頻度。
- `CAPTURE_DISCONNECTED` におけるキャプチャ再接続確認頻度。
- `ARMED` 遷移時の無制限取得への復帰。
- UseCase、`FrameCaptureProducer`、NDI adapter 間の取得間隔ポリシーと実行責務の境界。
- 非 `ARMED` 状態で取得したフレームの状態判定への引き渡し。
- ON 確定に使った 3 フレームの後段リプレイ。

## 適用しない範囲

- `ARMED` 中のバトル検出・録画フレームレート。
- ON 候補・OFF 候補の画像判定条件そのもの。
- OFF 確定の既存判定間隔。
- 実キャプチャ以外の OBS、OS、GPU、編集、アップロードの性能最適化。
- CPU 使用率の固定値保証。CPU 率はハードウェア、ドライバー、入力映像、同時処理に依存する。
- `recorded/`・`edited/` の未処理キュー、再走査、snapshot、generation、成果物 commit の設計変更。

## 期待する効果

- 電源 ON 待機とキャプチャ再接続待機で、不要な実キャプチャ、色変換、キュー投入を毎秒 1 回へ抑える。
- ユーザーの約 10 秒の操作余裕に対し、通常約 2 秒、取得位相差込みで通常最長約 3 秒という十分短い ON 復帰を維持する。
- `ARMED` 遷移直後から従来の取得頻度へ戻り、バトル開始検出と録画精度への影響を避ける。
- 取得と判定の時間ゲートを一つにし、フレーム取りこぼしとタイミング依存の復帰遅延を防ぐ。
- adapter を無状態に保ち、電源状態ポリシーとキャプチャ技術の責務を分離する。

## 受け入れる欠点・リスク

- Switch ON から最初の候補取得まで最大約 1 秒待つため、0.5 秒案より復帰が遅い。
- OS やキャプチャ API の遅延により、実際の復帰は理論上の約 3 秒を超える場合がある。
- 1 秒ごとの実キャプチャにしても、環境によっては期待した CPU 率まで下がらない可能性がある。
- 動的間隔を producer と UseCase の間で更新するため、スレッド間の可視性と停止時の安全性を維持する必要がある。

## 再検討条件

- 実機で Switch ON から `ARMED` 復帰または録画開始がバトル開始に間に合わない場合。
- 電源 ON 待機中の実測 CPU 使用率が、1 秒間隔でも許容範囲へ下がらない場合。
- キャプチャ再接続の検出に 1 秒より短い応答時間が必要になった場合。
- ON 候補数または ON 判定条件を変更し、復帰時間の計算前提が変わった場合。
- producer の時間ゲートでは制御できないブロッキングまたは adapter 固有の CPU 消費が主要因と判明した場合。

## ユーザー発言の原文

問題提起:

> 電源on待機中、cpu負荷を約40%も使ってる

0.5 秒案に対するユーザーの選択と理由:

> 1秒ごとに取得・判定でいいです
> Switch電源onしてからバトル開始(録画開始)まで約10秒はかかるためです。

受諾対象となったメインエージェントの直前提案:

> 修正方針は、`waiting_for_power_on` 中だけキャプチャを約2fpsへ間引きます。
>
> - 0.5秒ごとに1フレームだけ取得・判定
> - 3回連続でON候補なら約1.5秒で録画待受へ復帰
> - `armed` へ戻ったら通常フレームレートへ復帰
> - 録画中やバトル検知精度には影響させない
> - CPU使用率を性能回帰テストで固定する

ユーザー判断を受けたメインエージェントの確認:

> 承知しました。ON待機中は1秒に1フレームだけ取得・判定し、3回連続確認なら約3秒で通常監視へ戻す設計にします。Switch ONからバトル開始まで約10秒あるため、この遅延なら録画開始に十分間に合います。

責務配置と既存保証を維持する提案:

> 実装方式は、NDIアダプターへ電源状態を持ち込まず、既存の `FrameCaptureProducer` に「次の実キャプチャまでの最小間隔」を動的設定できる機能を追加します。初期・OFF待機・切断中は1秒、`ARMED` 遷移時は制限なしへ即時切替します。ON確定に使った3フレームを後段へ渡す既存処理順は維持します。

単一ゲートを採用したメインエージェントの原文:

> 設計助言の結論は、1秒ゲートをキャプチャ側だけに置くべき、というものです。判定側にも1秒制限を重ねると時計差で2枚目を飛ばし、復帰が約4秒以上になる可能性があります。この助言に従い、非`ARMED`では「1秒ごとに取得された全フレームを判定」、`ARMED`では従来の5秒間隔OFF判定、という単一ゲート設計へ修正します。
