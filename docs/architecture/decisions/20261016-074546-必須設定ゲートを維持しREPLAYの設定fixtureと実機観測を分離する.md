# 必須設定ゲートを維持しREPLAYの設定fixtureと実機観測を分離する

- ID: 20261016-074546
- 状態: accepted
- 日時: 2026-10-16T07:45:46+09:00
- 判断者: 共同（検証の目的・品質はユーザー、構成とデータ保全境界はメインエージェント）

## 目的・問題

必須設定ゲートを導入した後、既存REPLAY workflow fixtureは完了履歴だけを持ち、保存設定が不足して通常画面前に停止する、と会話で説明されました。REPLAYの一部検査が実OBS保存構成も参照していました。記録依頼で共有された原因内訳は、capture/OBS保存設定とYouTube `client_secret`の不足、実OBS保存構成との不一致です。この詳細はユーザーの直接発言ではなく、メインエージェントからの原因情報であり、記録役は実装・実機で独立確認していません。

ユーザーは、各検査の保証範囲と実行可能範囲を整理し、意味のある検証を続けるよう求めました。必須条件を緩めず、REPLAYを実利用者データから隔離したうえでsetup検査と後続workflowを実経路で確認する境界を定めます。

## 前提・制約

- `20261013-174839`の必須設定・必要ソフトの検査基準とLIVE checker登録を維持します。
- `docs/test_strategy.md`の分類・保証方針を維持します。REPLAY workflowはfixture観測を既存ポートで供給し、その後の状態遷移・保存・API・UIを実経路で検査します。
- `20260827-041653`のとおり、`live`/`replay`のアダプタ構成はComposition Rootで分けます。
- REPLAYがユーザー設定、Keychain、実OBS保存データ、実動画へfallbackせず、実利用者データを扱わないことを受け入れ条件とします。実装確認は未完了です。
- 架空OAuth JSONは構造とsetup判定を検査するfixtureであり、実Google認証やYouTube送信の証明ではありません。
- 実OBS/NDI/DistroAV、キャプチャ機器およびFFmpeg/OCR/フォント等の実処理は、REPLAY外部観測fixtureの保証対象ではありません。不足・未確認を隠しません。

## 判断

1. LIVEの保存先、必須gate、判定基準、外部checker登録は変更しません。
2. REPLAYの起動前に、絶対パスのE2E root、そのroot内の`settings_path`、明示的な`NoOpUpload=1`を要求します。不足・不正なら起動を拒否します。
3. 設定読込後、repository/adapter利用前に、`storage.base_dir`が同じE2E root内にある絶対パスであることと、OAuth configの解決済みpathがsymlink経由でも同じroot内にあることを検査します。逸脱は拒否します。
4. 上記境界を通った隔離fixtureの保存設定と構造上有効な架空OAuth JSONを、実際の`SetupService`/APIへ通します。REPLAYではOBS/NDI/DistroAVやOBS保存構成など実機固有の外部観測だけを既存ポートで差し替え、LIVE/REPLAYの組立てをComposition Rootに置きます。
5. 完了履歴の注入、setup/API/UIの成功mock、ユーザー設定・動画へのfallback、skip、期待値・閾値の緩和で通しません。有効fixtureでは代表的な後続workflowを実行し、欠落fixture・root逸脱・symlink逸脱を拒否することを検証条件とします。LIVE checker登録とREPLAYから個人設定・Keychain・実OBSへ到達しないことも確認対象です。
6. NoOpUploadが実Google認証を保証しないこと、FFmpeg/OCR/フォント等の実処理が不足・未確認なら対応保証がないことを結果に明示します。

この記録時点では親セッションで実装を修正中のため、上記の検証結果は未確認です。

## 検討した選択肢と棄却理由

### 必須gateを無効化する、または完了履歴だけを注入する

現在の保存設定を検査する契約を通らないため採用しません。

### setup/API/UIを一括mockする、またはworkflowをskip・緩和する

設定保存・読戻しと主要導線を検査せず、失敗を隠すため採用しません。

### REPLAYから実OBS設定を読む、またはユーザーデータへfallbackする

環境依存と利用者データへの到達を残すため採用しません。E2E root境界の検査より先にrepository/adapterを利用する構成も採用しません。

### データを隔離し、setupを実経路で通して外部観測だけをport経由で置き換える

実利用者データを隔離しながら必須判定と後続アプリ経路を検査でき、既存のREPLAY構成・port境界に沿うため採用します。

## 適用範囲

- 必須セットアップ検査を含むREPLAY workflowと、その設定・保存先・OAuth configの隔離境界。
- 実際の`SetupService`/APIを通す保存設定検査、repository/adapter利用前のパス検査、および実機固有外部観測のREPLAY差し替え。
- 有効fixture、欠落fixture、root外パス・symlink逸脱の拒否を含む検証条件。

## 適用しない範囲

- LIVEの保存先、必須条件、合格基準、checker登録。
- 実OBS/NDI/DistroAV、実機器、実Google認証、YouTube送信の成功保証。
- FFmpeg/OCR/フォント等の実処理のmock化、またはその不足をREPLAY成功で補ったとする扱い。
- テスト分類、CIや全リリース検査入口の再設計。

## 期待する効果

- 必須gateを維持して、現在の保存設定から通常画面へ進む判定と後続workflowをREPLAYで検査できます。
- 設定・実動画がユーザーデータへfallbackせず、実OBS保存先やKeychainへ触れない境界を明示できます。
- REPLAYが保証するアプリ経路と、LIVE checker・実環境に残る保証を分けて報告できます。

## 受け入れる欠点・リスク

- REPLAYの外部観測fixtureでは実機OBS/NDI/DistroAVの不具合を検出できず、別のLIVEまたは実機検査が必要です。
- `NoOpUpload=1`と架空OAuth JSONは、実Google認証やYouTube送信を保証しません。
- fixtureと実設定形式が乖離すれば主要導線の代表性が下がります。実`SetupService`/APIとroot逸脱拒否の検査を維持します。
- FFmpeg/OCR/フォント等が利用できない場合、その処理の保証は未確認または不足として扱います。

## 再検討条件

- 必須設定・checker、REPLAYの保存形式、外部観測ポートが変わったとき。
- root外パスやsymlink経由の逸脱、利用者データへの到達、LIVE checker登録欠落が見つかったとき。
- 実機・Google認証・YouTube送信の保証をREPLAYまたはrelease gateへ含める必要が生じたとき。
