# 変更分類と保証対象から最小の検証範囲を選ぶ

- ID: 20260812-132848
- 状態: accepted
- 日時: 2026-08-12T13:28:48+09:00
- 判断者: 共同

## 目的・問題

デプロイスクリプトとその回帰テストに限定された変更で、backend 全体を含む全テストを実行したため、変更が守るべき保証に対して検証範囲が過大になりました。さらに、`AGENTS.md` の旧来の最低入口と `docs/test_strategy.md` の変更分類による選定が衝突し、別セッションでも同じ過剰検証を繰り返す余地がありました。

会話上の約束や案件専用の Task 追加に依存せず、変更分類と保証対象から必要十分な検証範囲を毎回選べる運用境界を確定します。

## 前提・制約

- テスト選定の SSoT は `docs/test_strategy.md` とします。
- `AGENTS.md` は常時適用する薄いルータ、`docs/DEVELOPMENT.md` は how-to とし、テスト選定の詳細判断を重複させません。
- Windows の統合窓口では `task.exe` を使います。
- 既存の意味ベース Task を優先しますが、保証対象より過広い Task の実行を義務にはしません。
- 今回は専用 Taskfile 入口を追加せず、`Taskfile.yml` を変更しません。

## 判断

1. 検証前に、変更分類、保証対象、保証を満たす最小対象、必要な静的検証を決めます。
2. コミット、完了、振る舞い変更という事実だけを、`task.exe test` または `task.exe verify` の実行根拠にしません。
3. 広い入口は、狭い対象では守れない保証を実行前に説明できる場合だけ追加します。
4. `task.exe verify` は、次のいずれかに該当する場合だけ使います。
   - リリース前の確認である。
   - 複数層・複数の保証分類にまたがり、個別入口の組み合わせでは不足する。
   - 調査しても影響範囲を安全に絞れない。
   - ユーザーが全体検証を明示的に依頼した。
5. 保証対象に合う既存 Task があれば、それを優先します。既存 Task が過広い場合は、repo 管理ラッパーまたは package script に対象ファイルや node ID を渡します。生の runner は、それらでも表現できない低レベルの切り分けに限定します。
6. 個別案件ごとの専用 Taskfile 入口を、過剰検証を防ぐための必須手段にはしません。今回のデプロイスクリプト専用入口も追加しません。
7. 別セッションでの適用は、`docs/test_strategy.md` を SSoT とし、`AGENTS.md` と `docs/DEVELOPMENT.md` がそこへ誘導する構造で担保します。

## 検討した選択肢と棄却理由

### `task.exe verify` を完了時の最低入口として維持する

完了条件は単純になりますが、変更が守る保証と無関係に全体 gate を実行し、今回と同じ過剰検証を再発させます。変更分類による選定とも衝突するため採用しません。

### デプロイスクリプト専用の Taskfile 入口を追加する

今回の対象実行は容易になりますが、案件ごとの入口を増やすことが運用判断の根本原因を解くわけではありません。ユーザーがこの案以外の対応を明示したため採用せず、既存の repo 管理ラッパーまたは package script への対象指定を使います。

### 変更分類と保証対象から最小範囲を選ぶ

判断内容を実行前に言語化する必要がありますが、検証コストを守る保証へ対応付け、広い入口が必要な場合も根拠を明示できます。この案を採用します。

### 生の runner を常用する

対象指定は柔軟ですが、repo が管理する環境・オプション・意味ベース入口を迂回しやすくなります。既存 Task と repo 管理ラッパーで表現できない低レベル切り分けに限定します。

## 適用範囲

- 日常のコード、スクリプト、テスト、文書変更に対するテスト・静的検証の選定。
- `task.exe test`、`task.exe verify`、個別 Task、repo 管理ラッパー、package script、生 runner の使い分け。
- 別セッションのエージェントが参照するテスト選定文書の責務分担。

## 適用しない範囲

- リリース時に必要な総合確認の具体的な手順。
- 個々のテスト分類、テスト実装方法、具体的なコマンド一覧。
- CI の gate、依存関係、Taskfile のタスク定義そのもの。
- 個別変更で実際にどのテストが保証を満たすかという都度の判断。

## 期待する効果

- 変更が守る保証と検証コストを対応付け、無関係な全テスト実行を避けられます。
- 広い検証を行う場合の理由が実行前に明確になります。
- 会話上の約束ではなく、別セッションでも参照される SSoT と薄いルータによって同じ運用を継続できます。
- 案件専用 Task の増殖を避けつつ、対象ファイルや node ID による狭い検証を選べます。

## 受け入れる欠点・リスク

- 実行前に変更分類と保証対象を判断する負担が増えます。
- 影響範囲の見積りを誤ると、必要な検証を狭めすぎる可能性があります。この場合は、調査しても安全に絞れない条件として `task.exe verify` を使います。
- repo 管理ラッパーや package script が対象指定を受け付けない場合、生 runner による低レベル切り分けが必要になります。
- 文書間の誘導が将来ドリフトすると、旧来の無条件な全体検証が再導入される可能性があります。

## 再検討条件

- CI やリリース契約により、すべての変更で同一の全体 gate が必須になった場合。
- 個別入口の組み合わせでは複数層・複数保証分類を十分に検証できない事例が反復した場合。
- 対象指定を repo 管理入口で表現できず、生 runner の常用が増えた場合。
- `AGENTS.md`、`docs/test_strategy.md`、`docs/DEVELOPMENT.md` の責務が再編された場合。
- 検証を狭めたことによる回帰漏れが確認され、分類または `task.exe verify` の適用条件を見直す必要が生じた場合。

## ユーザー発言の原文

過剰な全テスト実行について、ユーザーは次のように述べました。

> デプロイ改善だけなのに、全テスト実行は明らかに過剰過ぎるでしょう。バックエンドを変更していて、影響範囲が不明確とかなら分かるけど。

エージェントが次の方針を回答しました。

> 全テスト実行は過剰でした。今後は変更分類に基づき、対象テストと必要な静的検証に限定します。

これに対してユーザーは、セッションをまたいだ継続性を求めました。

> 別セッションでもどうやって守る？

エージェントは対応案の一つとして次を提示しました。

> 今回のデプロイスクリプト用に、対象テストだけを実行するTaskfile入口を用意する。これにより、test:backend が全640件を実行する事故を防げます。

これに対してユーザーは次のように指示しました。

> これ以外の対応して

この指示を、専用 Taskfile 入口を除外し、SSoT と文書責務を整合させる対応を求めるものとして反映しました。対象指定方法、`task.exe verify` の四つの適用条件、文書の責務分担は会話内で具体化された確定内容であり、ユーザーの直接引用とは扱っていません。
