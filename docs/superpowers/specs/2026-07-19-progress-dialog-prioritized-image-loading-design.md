# 進捗ダイアログの画像優先読み込み設計

## 背景

編集進捗ダイアログでは、メインの動画枠とクリップのシークバーに動画フレーム画像を表示する。現状は次の理由により、画像が表示されない、または表示可否がタイミングに左右される。

- フロントエンドは画像 URL を組み立てた時点で画像が利用可能と扱い、`<img>` と `new Image()` に同じ URL の読み込みを委ねている。読み込み順、重複、再試行、破棄を制御していない。
- 読み込み失敗時は画像を透明にするだけで、最後に成功したメイン画像の保持や再試行がない。
- バックエンドは `.progress_frames` のファイルキャッシュを読み書きし、キャッシュ生成を編集処理内で待機している。表示の正しさがキャッシュ生成と元動画削除のタイミングに依存する。
- API は生成物へ長期キャッシュを許可しているため、失敗や古い応答をブラウザー側の状態から切り離しにくい。

この設計では、画像を編集処理の付随情報として扱い、表示のための取得を編集処理から完全に分離する。

## 目的

進捗ダイアログを開いている間、必要な動画フレームを明示的な優先順で段階表示する。画像取得に失敗しても編集処理は継続し、表示の正しさを永続キャッシュに依存させない。

## 受入条件

1. 画像要求は同時に1件だけ実行し、次の順で処理する。
   1. メイン動画枠の現在フレーム
   2. 操作中クリップのシークバー画像
   3. 操作中項目に属する残りのクリップ画像
   4. 次の編集項目の画像
   5. それ以降の編集項目の画像
2. 高優先度の要求が追加された場合、未開始の低優先度要求より先に実行する。実行中の1件は中断せず、完了後に優先度を再評価する。
3. 同じ画像への重複要求は1つの取得へまとめ、複数の表示箇所で結果を共有する。
4. 同じ表示枠の対象 URL が更新された場合、未開始の旧要求を捨てて最新要求だけを残す。実行中の旧要求が完了しても、新しい対象 URL と一致しなければ表示へ反映しない。
5. 画像の取得とデコードが成功してから表示画像を切り替える。メイン動画枠は新しい画像の準備中または失敗時にも最後に成功した画像を維持する。
6. まだ一度も成功していない表示箇所だけプレースホルダーを表示する。
7. 画像要求は合計3回まで試行し、失敗時は250ミリ秒、750ミリ秒の待機を挟む。
8. ダイアログを閉じた場合、または対象行が完了・破棄された場合、不要な待機中・実行中要求を中止し、生成済み Object URL を解放する。
9. 画像の待機、取得、デコード、再試行、失敗を理由に編集処理を待機・中断・失敗させない。
10. 動画フレーム API は要求ごとに元動画から対象フレームを抽出し、`.progress_frames` その他の永続キャッシュを参照・生成しない。
11. API 応答は `Cache-Control: no-store` とし、フロントエンドも `fetch` の `cache: "no-store"` を指定する。
12. 項目が画像取得より先に完了した場合は画像要求を中止し、通常の完了サムネイル表示へ移行する。元動画の保持期間や削除タイミングは変更しない。

## 非対象

- 進捗ダイアログのレイアウト、色、文言、アニメーションの再設計
- 編集品質、編集順、動画生成、アップロード処理の変更
- 元動画の削除タイミング変更や、プレビュー専用のファイル保持・リース機構の追加
- Service Worker、IndexedDB、HTTP キャッシュ、ディスクキャッシュによるフレーム再利用
- 既存 `.progress_frames` ディレクトリの一括削除。新実装では参照も新規生成もしない

フロントエンドの Object URL は、取得済み Blob を表示するためのダイアログ存続中だけのリソースである。永続化せず、所有者の破棄時に必ず解放するため、本設計で禁止するキャッシュには含めない。

## 検討した方式

### 採用: フロントエンドの明示キューとバックエンドのオンデマンド抽出

フロントエンドが表示上の優先度を持つキューを管理し、バックエンドは1要求につき1フレームだけを元動画から抽出する。表示順を最もよく知る層が優先順位を決められ、編集処理と画像処理の依存も切れる。変更範囲は進捗表示と既存フレーム API に限定できる。

### 不採用: バックエンド集中キューと元動画リース

バックエンドで全表示状態を管理すれば複数クライアントを横断して順序制御できるが、現在の要件には不要である。画面状態の同期、ジョブ識別、キャンセル API、元動画の保持契約が増え、編集ライフサイクルまで変更するため採用しない。

### 不採用: `<img loading>`、`fetchpriority`、ブラウザーキャッシュ制御だけで調整

ブラウザーのヒントだけでは同時実行数、動的な優先順位、重複排除、再試行、所有者単位の中止を保証できない。またバックエンドのキャッシュ依存と編集処理内の待機が残るため、根本解決にならない。

## アーキテクチャ

### 1. 画像ローダー

`frontend/src/main/components/progress/progressImageLoader.ts` に、進捗ダイアログ専用の画像ローダーを新設する。UI コンポーネントから取得制御を分離し、次の責務だけを持たせる。

- 優先度と投入順による待ち行列管理
- 同時実行数1の保証
- URL 単位の実行中・成功結果の重複排除
- 表示枠単位の最新要求への置換と、古い完了通知の抑止
- 所有者と購読者の管理
- `fetch(url, { cache: "no-store", signal })` による取得
- Blob から Object URL を生成し、DOM へ挿入しない `Image.decode()` による事前デコード
- 合計3試行の再試行制御
- 所有者破棄時の `AbortController.abort()` と `URL.revokeObjectURL()`

各要求は少なくとも次の値を持つ。

- `url`: 同一画像を識別する正規化済み URL
- `ownerId`: 行、クリップ、メイン表示などのライフサイクル所有者
- `slotId`: 所有者内の表示枠を識別し、同じ表示枠の旧要求を置換するキー
- `priority`: 表示上の優先度。小さい値ほど高優先度
- `sequence`: 同一優先度内の安定した投入順
- `onReady`: デコード済み Object URL の通知先
- `onError`: 最終失敗の通知先

同じ URL に複数の購読者がいる場合は1回だけ取得する。ある所有者が破棄されても別の購読者が残る間は取得を継続し、購読者が0件になった時点で待機要求を削除、または実行中要求を中止する。

同じ `ownerId` と `slotId` に新しい URL が登録された場合は、旧 URL への購読を解除して待機中の旧要求を除去する。旧要求がすでに実行中なら抽出自体は完了させてもよいが、その完了通知は破棄する。これにより、進捗イベントが短い間隔で届いても古いメインフレームが待ち行列へ蓄積せず、遅れて表示を巻き戻すこともない。

成功した Object URL の所有権はローダーが持つ。画面側は URL を表示状態として参照し、置換・行破棄・ダイアログ破棄をローダーへ通知する。ローダーは参照がなくなった URL を解放する。

### 2. `ProgressDialog.svelte` の統合

`ProgressDialog.svelte` は、既存の表示対象計算をローダー要求へ変換する。

- URL を組み立てただけでは「表示可能」と扱わない。
- 隠し `<img>` と `new Image()` による暗黙のプリロードを廃止する。
- メイン表示、操作中クリップ、同一項目の残り、次の項目、それ以降の項目を明示的に分類し、受入条件どおり5段階の優先度を付ける。
- 表示中のメイン画像は、次の画像がデコード成功した時だけ差し替える。失敗時は最後に成功した画像を残す。
- シークバー画像の失敗は該当画像だけへ閉じ込め、他のクリップ画像やメイン表示へ波及させない。
- 完了サムネイルも読み込み成功後に差し替える。失敗時は最後に成功したゲームフレームを維持し、成功画像がない場合だけ既存プレースホルダーを使う。
- 行の完了・削除、クリップ構成の変更、ダイアログ終了時に、その所有者の要求と Object URL を解放する。

優先度は表示状態から毎回再計算する。操作対象が変わった場合、待機中要求は新しい優先度へ更新する。「次の項目」は操作中項目の直後の1項目だけとし、2項目目以降は「それ以降」とする。同一優先度内は画面上の項目順、クリップ順、最後に `sequence` の順で安定化する。実行中要求はそのまま完了させ、次の取り出し時に新しい順序を使う。

### 3. 動画フレーム API

既存の動画フレーム API は、クエリで指定された元動画、時刻、幅から1枚の PNG をオンデマンド抽出して返す。

- `.progress_frames` を含む既存ファイルキャッシュを探索しない。
- 要求された時刻と異なる「最初に見つかった PNG」への代替を行わない。
- 成功時は `image/png` と `Cache-Control: no-store` を返す。
- 元動画が存在しない、または許可されたパスとして解決できない場合は404を返す。
- FFmpeg 抽出失敗は500を返し、動画パス、要求時刻、幅、例外情報をバックエンドログへ残す。
- 画像 API の失敗は編集ジョブの状態へ反映しない。

同一プロセス内のプレビュー抽出には専用のセマフォを設け、並列数を1に制限する。これは複数画面や再接続が同時に要求した場合の FFmpeg 負荷を制限するもので、編集処理のロックとは共有しない。

### 4. 編集処理からの分離

FFmpeg 処理層から `.progress_frames` の読み書きと事前生成 API を削除する。自動編集処理からフレームの事前生成呼び出しとその `await` を削除する。

編集処理は従来どおり成果物保存と元動画削除を進める。プレビュー要求の有無、成否、進行状況を待たない。元動画が先に削除されたため画像 API が404を返す場合は許容された競合として扱い、画面は最後の成功画像または完了サムネイルへ収束する。

## データフロー

1. 進捗イベントにより行、操作中クリップ、現在時刻が更新される。
2. `ProgressDialog.svelte` が必要画像を分類し、優先度付き要求としてローダーへ登録・更新する。
3. ローダーは待ち行列から最高優先度かつ最古の要求を1件取り出す。
4. ローダーは `cache: "no-store"` と中止シグナルを指定して動画フレーム API を呼ぶ。
5. API は元動画から指定フレームを抽出し、`no-store` の PNG 応答を返す。
6. ローダーは応答 Blob の Object URL を作成し、画面外でデコードする。
7. デコード成功後、購読中かつ現在も同じ URL を要求している表示箇所へ Object URL を通知する。UI は最新要求の成功通知を受けた時だけ表示を差し替える。
8. 失敗時は規定の待機後に再試行する。3回目も失敗した場合は該当要求だけを失敗確定し、次の要求へ進む。
9. 所有者が消えた場合は要求を中止し、参照されない Object URL を解放する。

画像フローのどの段階からも、編集ジョブを待つ・止める・失敗へ変更する呼び出しは行わない。

## 失敗時の振る舞い

| 状況 | UI | 編集処理 |
| --- | --- | --- |
| 新しいメイン画像を取得中 | 最後に成功したメイン画像を維持。未成功ならプレースホルダー | 継続 |
| メイン画像が3回失敗 | 最後に成功したメイン画像を維持。未成功ならプレースホルダー | 継続 |
| シークバー画像が3回失敗 | 該当箇所だけ既存プレースホルダー | 継続 |
| 元動画が先に削除され404 | 最後の成功画像または完了サムネイルへ収束 | 継続 |
| ダイアログを閉じる | 取得を中止し Object URL を解放 | 継続 |
| 完了サムネイルが失敗 | 最後に成功したゲームフレームを維持。未成功ならプレースホルダー | 完了状態を維持 |

中止は失敗回数へ含めず、ユーザー向けエラーにも表示しない。HTTP エラー、ネットワークエラー、デコードエラーは同じ再試行上限を共有する。

## テスト方針

`docs/test_strategy.md` の分類と完了契約に従い、変更で増える優先制御、外部契約、主要導線、再発防止だけを検証する。

### Logic

- 優先度と投入順が指定順になる。
- 実行中要求を中断せず、完了後に更新後の優先度を再評価する。
- 同一 URL を重複排除し、購読者が0件になった場合だけ中止する。
- 表示枠の URL 更新で未開始の旧要求を捨て、実行中の旧要求が遅れて成功しても通知しない。
- 合計3回の試行と250ミリ秒、750ミリ秒の待機を行う。
- 解放対象の Object URL を一度だけ revoke する。

### Component

- URL 計算だけではメイン画像を切り替えず、デコード成功通知で切り替える。
- 新規取得中・失敗時に最後の成功画像を維持する。
- シークバーの失敗が他の画像表示を消さない。
- 行完了・ダイアログ破棄で所有者を解放する。

### Integration

- 進捗更新から優先要求が生成され、メイン、操作中クリップ、同一項目の残り、次の項目、それ以降の項目の順に API が呼ばれる。
- リクエストに `cache: "no-store"` が付く。
- API 失敗中も進捗イベントの受信と完了表示が継続する。

### Contract

- 動画フレーム API が指定時刻の PNG と `Cache-Control: no-store` を返す。
- `.progress_frames` が存在しても参照・更新しない。
- 元動画がない場合は404、抽出失敗は500となる。
- キャッシュ済み PNG だけが残り元動画がない場合でも成功扱いしない。

### Workflow

- 実際の進捗ダイアログで画像が優先順に段階表示される。
- 画像 API を意図的に失敗させても編集が最後まで完了する。
- 項目が短時間で完了した場合、不要要求を中止して完了サムネイルへ移行する。

実装時は対象テストを先に個別実行し、その後に次のリポジトリ入口を実行する。

```powershell
task.exe test:frontend:component
task.exe test:frontend:integration
task.exe test:workflow:smoke
task.exe test
task.exe verify
```

UI の主要導線とバックエンド契約を変更するため、component、integration、workflow、backend の対象テストを省略しない。`task.exe verify` の成功だけでなく、画像失敗時にも編集完了という保証が維持されていることを確認する。

- `frontend/src/main/components/ProgressDialog.svelte`
- `frontend/src/main/components/progress/progressImageLoader.ts`（新規）
