# Switch 電源サイクルをまたぐ連続自動処理 実装契約

- 状態: 連続自動処理とON待機中のキャプチャ負荷改善は実装・自動検証完了（実映像 fixture／実機での反復・CPU確認待ち）
- 作成日: 2026-08-13
- 最終更新日: 2026-08-14
- 対象: Splat Replay バックエンドの自動録画・自動編集・自動アップロードと、その状態を表示するフロントエンド

## 目的

アプリを起動したまま利用する限り、Switch の電源 ON/OFF を何度繰り返しても、各プレイの録画と、電源 OFF 後の編集・アップロードを継続できるようにする。

同時に、既存設計が持つ「録画済み・編集済みディレクトリを走査し、エラー終了やアプリ再起動後にも未処理ファイルを回収する」性質を失わない。

## 目標

1. Switch の電源状態を、ブラウザ画面や完了ダイアログの操作に依存せずバックエンドで監視する。
2. Switch の電源 OFF を確定した後も監視を終了せず、電源 ON を確定するまで待機し、自動録画を再び待受状態へ戻す。
3. 電源 OFF ごとに編集・アップロードを起動しつつ、処理中に追加された動画を失わず、現在の処理完了後、次の電源 OFF、または手動開始時に回収する。
4. 編集・アップロードの失敗が、Switch 監視と次回の録画を停止させない。
5. 未処理ファイルを成功確認前に削除しない。
6. Switch ON待機中の実キャプチャを1秒に1回へ抑え、バトル待受へ復帰した後の録画監視頻度は低下させない。

## 方針

### 1. バックエンドをライフサイクルの所有者にする

- アプリの lifespan と同じ寿命を持つ調整役を一つだけ置く。
- 調整役が Switch 電源状態、録画監視、編集・アップロードの再走査要求を単一所有する。
- フロントエンドは状態表示、明示的な開始・停止、キャンセル要求だけを担当する。
- 編集開始および録画再開を、ブラウザの生存、通知カードのタイマー、完了ダイアログを閉じる操作に依存させない。

### 2. Switch 電源状態を明示する

監視状態は少なくとも次を区別する。

- `unknown`: 起動直後など、電源状態が未確定。
- `armed`: Switch ON が確定し、バトル開始を監視している。
- `waiting_for_power_on`: Switch OFF が確定し、次の ON を待っている。
- `stopped`: アプリ終了または利用者の明示停止。
- `capture_disconnected`: Switch OFF ではなく、キャプチャーデバイス自体が切断されている。

電源 OFF は状態遷移一回につき一度だけ後処理要求を発行する。`waiting_for_power_on` 中に OFF フレームが続いても重複要求を発行しない。

### 3. ON/OFF を連続観測で確定する

- OFF は既存の電源 OFF 判定を連続観測して確定する。
- ON は単に一回 `power_off == false` になっただけでは確定しない。
- フレーム取得成功、信号なし画面ではないこと、電源 OFF 判定ではないことを複数回連続で確認して確定する。
- 回数・間隔は定数として集約し、実映像 fixture で検証可能にする。
- `image_matching.yaml` の matcher 参照名を検証し、未知の参照名を黙って false として扱わない。

ON待機中は判定間隔だけでなく、NDI受信・色変換を含む実キャプチャ自体を1秒に1回へ制限する。
`unknown`、`waiting_for_power_on`、`capture_disconnected` ではこの制限を適用し、
ON候補を3回連続確認して `armed` へ遷移した時点で制限を解除する。
取得側だけを1秒ゲートとし、待機中に届いた全フレームを電源判定へ渡す。
初回取得は直ちに行うためON確定は通常約2秒、電源ONとの位相差を含めても最長約3秒となるが、
Switch電源ONからバトル開始までは約10秒あるため、
録画開始には間に合うものとする。`armed` および録画中の取得頻度は変更しない。

実装時点では、既知の黒画面と電源 OFF テンプレートを OFF として除外し、
`detect_power_off() == false` の連続観測を ON 候補としている。したがって、
「OFF ではないが有効な Switch 映像でもない未知の画面」と ON の完全な区別は未確認である。
この区別が実映像で不十分な場合は、観測結果を `OFF / ON_VALID / INDETERMINATE`
の三値へ拡張する。

### 4. ファイルシステム上の未処理成果物を処理対象の SSoT とする

- `recorded` ディレクトリの確定済み動画を未編集キューとして扱う。
- `edited` ディレクトリの確定済み動画を未アップロードキューとして扱う。
- `cycle_id` やイベントは診断および再走査の契機に使うが、処理対象の唯一の根拠にはしない。
- アプリ起動時、後処理要求時、後処理完了時にディレクトリを再走査する。
- アプリ起動時の走査は未処理ファイルの再発見だけを行い、編集・アップロードを自動開始しない。
- 編集とアップロードは各実行開始時点の一覧を snapshot として処理し、実行中に追加されたファイルは次の snapshot で処理する。

### 5. 再走査要求を失わない

- 編集・アップロード実行中に新しい電源 OFF や録画保存が発生しても要求を破棄しない。
- 単調増加する generation または同等の lost-wakeup を防ぐ仕組みを使う。
- worker が idle へ移る直前に必ず再走査し、観測済み generation と現在値が一致し、未処理ファイルも存在しない場合だけ待機する。
- 編集・アップロードは単一 worker で直列実行し、多重起動させない。

### 6. 成功確定後にだけ入力を削除する

- 録画ファイルは保存完了前の一時領域から、関連ファイルを含む保存成功後に `recorded` へ公開する。
- 編集元録画は、編集済み動画と必要な関連ファイルが `edited` へ確定した後だけ削除する。
- 編集成果物の保存失敗を握りつぶさず、呼び出し元へ失敗として返す。
- アップロード元の編集済み動画は、アップロード成功を確認した後だけ削除する。
- 失敗、キャンセル、成否不明の場合は、再試行または確認に必要なローカルファイルを残す。

### 7. 冪等性と再起動回復

- アプリ起動時に `recorded` と `edited` を必ず走査する。
- 起動時に未処理ファイルを発見しても自動処理せず、電源 OFF 後または手動開始まで保持する。
- 編集成果物確定後・元録画削除前の異常終了で重複編集しないよう、安定した入力識別子または commit manifest を用いる。
- ローカルファイルが残っている限り、次の電源 OFF または手動開始時に未処理処理が少なくとも一度再試行される。
- 外部アップロードの成功後・ローカル成功記録前に終了した場合は結果不明として扱い、無条件な自動再送で重複を増やさない。

## 対象範囲

- Switch 電源 OFF 検出後も存続する自動録画監視ループ。
- Switch 電源 ON の確定条件と `waiting_for_power_on` からの復帰。
- `unknown` / `waiting_for_power_on` / `capture_disconnected` 中の実キャプチャ頻度制御と、`armed` 復帰時の制限解除。
- アプリ lifespan に連動するバックエンド常駐タスクの開始・停止。
- 電源 OFF 後の編集・アップロード開始猶予とキャンセル。
- `recorded` / `edited` の起動時・完了時再走査。
- 処理中に追加された未処理ファイルを次回走査へ確実に送る仕組み。
- 編集成果物確定前の録画削除防止。
- UI の状態表示と、UI依存の再有効化トリガーの撤去。
- 上記を保証する backend logic、contract、frontend component/integration、主要 workflow テスト。
- 外部仕様書、内部設計書、利用手順の必要箇所の更新。

## 範囲外

- YouTube API が冪等性キーや確実な照合手段を提供しない場合の、外部アップロードの完全な exactly-once 保証。
- ディスク破損、利用者による手動削除、保存先容量不足からの自動復旧。
- PC、OBS、キャプチャーデバイス自体の電源制御。
- アプリ終了後も処理を継続するOSサービス化。
- 複数編集 worker による並列処理。
- 既存動画のファイル形式やメタデータ形式の一括移行。
- unrelated な録画認識精度、OCR、UIデザインの変更。
- OBSやNDI SDK自体のCPU使用率改善、およびPC環境に依存するCPU使用率の固定上限保証。
